# 앱 결과를 외부 시스템으로 보내기 (2026-11-09, 0076)

입력형 앱이 실행을 마치면 그 **결과 글**을 기관이 승인한 외부 시스템(전자결재 연계·그룹웨어·업무 대시보드 등)으로 보낸다. 알리웍스의 '외부 시스템에 쓰기'에 대한 첫 단계이고, 범용 연계(임의 동작·임의 API)가 아니라 **승인한 주소 하나로 결과를 넣어 주는 일**만 한다.

## 누가 무엇을

| 사람 | 할 수 있는 일 | 곳 |
|---|---|---|
| 기관 전체 관리자(최상위 부서 소속 관리자) | 보낼 곳(이름·https 주소) 만들기·회수, 최근 보내기 50건 보기 | 관리자 '앱 예약·연동' 화면 아래 '앱 결과 보낼 곳'(`OutboundEndpointsPanel`, `GET`·`POST /api/admin/outbound-endpoints`, `DELETE /api/admin/outbound-endpoints/[id]`) |
| 앱을 만드는 직원 | 앱 빌더 '결과를 보낼 곳'에서 이 기관의 쓸 수 있는 보낼 곳을 고름(이름만 보임) | `GET /api/apps/outbound-endpoints`, 앱 정의 `deliverEndpointId` |

- 보낼 곳은 기관에 **10곳**까지. 만들 때 **서명 비밀값**(`wo_out_…`)이 그 응답에서 **한 번만** 보인다(받는 시스템에 넣어 둔다). DB에는 되돌릴 수 있게 암호화해 둔다(보낼 때 서명해야 해 해시로 둘 수 없다 — `crypto.ts`의 AES).
- 만들기·회수는 보안 로그 high(`app_outbound_endpoint_created`·`…_revoked` — 이름·주소·비밀값 앞부분·사유). 회수는 사유 5자 이상이고, 보내지 않은 기록은 그만둔다. 되돌릴 수 없다(새로 만든다).

## 무엇을 언제 보내나

- **끝까지 마친 실행만**(멈춘·실패한 단계가 없고 답이 저장됨, `shouldDeliver`). 손 실행·예약 실행·외부 연동 실행 모두. **시험 판 실행(0053)은 보내지 않는다**.
- 답변을 저장한 뒤 보내기 기록을 넣고(`enqueueOutbound` — 그 기관의 회수되지 않은 곳일 때만, 같은 답변·같은 곳은 한 벌), **앱 예약 실행기(pg_cron 5분마다)** 가 예약 실행과 나란히 보낸다(`dispatchDueDeliveries` — 한 번에 20개·60초). 그래서 결과는 **약 5분 안에** 간다.
- 보내는 몸(JSON): `event: "app.run.completed"`, `delivery_id`, `sent_at`, `app { id, name }`, `run { message_id, conversation_id, completed_at }`, `result { text, truncated }`(결과 글 50,000자까지). **입력값·중간 단계·첨부·직원 정보는 보내지 않는다.**
- **결과 한글 파일 함께**(2026-11-10, 마이그레이션 없음): 앱 빌더에서 보낼 곳 아래 '결과 한글 파일도 함께 보내기'를 켜면(앱 정의 `deliverFile` — 보낼 곳을 고른 앱에만 남음) 보내기 **직전에** 그 답을 결과 한글 파일로 만들어(예약 결과 한글 파일과 같은 양식 규칙 — 앱의 '결과 한글 파일 양식'이 쓸 수 있으면 그 양식, 아니면 표준 보고서, 모델 없음, `buildResultHwpxBytes`, 저장하지 않음) `result.file = { name, content_type: "application/hwp+zip", size, sha256, encoding: "base64", data }`로 싣는다. 5MB(`OUTBOUND_FILE_MAX_BYTES`)를 넘으면 글만 보내고 `result.file: null`·`file_omitted: "too_large"`. 만들지 못하면(저장소·DB 오류) 보내지 않고 다시 보낼 일로 센다(5번까지). 고르지 않은 앱의 몸은 옛 꼴 그대로(`file` 칸 없음). 설정은 보낼 때의 앱 정의를 따른다(넣을 때가 아니라). 서명은 파일이 든 본문 전체에 건다.
- 머리글: `X-Workon-Event`, `X-Workon-Delivery`(= `Idempotency-Key`, 기록 id — 다시 보내도 같다), `X-Workon-Timestamp`(초), `X-Workon-Signature: sha256=HMAC-SHA256(비밀값, "{시각}." + 본문)`.
- **받는 쪽 확인**: 서명이 같은지, 시각이 5분 안인지, 같은 `X-Workon-Delivery`는 한 번만 처리하는지.

## 보내기 전 사람 확인 (2026-11-10, 0078)

- 기관 전체 관리자가 보낼 곳마다 **'보내기 전 실행한 직원이 결과를 확인'**을 켠다(만들 때 — 화면 기본값은 켬, API 기본값은 끔 — 또는 목록의 켜기·끄기, `PATCH /api/admin/outbound-endpoints/[id] { require_approval }`, 보안 로그 high `app_outbound_endpoint_updated`). 켜면 그 뒤 넣는 기록부터, 꺼도 이미 확인을 기다리는 기록은 그대로 직원이 정한다.
- 확인을 받는 곳이면 실행을 마친 결과는 곧바로 보내지 않고 **확인 기다림**(`awaiting_approval`)으로 넣는다 — 손 실행·예약·연동·일괄 실행 모두. 보내기 실행기는 이 기록을 집지 않는다(보낼 차례는 `pending`·`sending`만).
- **그 결과를 실행한 직원만** 정한다(관리자도 남의 결과를 대신 정하거나 결과 글을 보지 않는다): 입력형 앱 실행 화면의 **'보내기 전 확인할 결과'**(`GET /api/apps/outbound-approvals?agent=` — 이 직원·이 기관·기한 안만, 결과 글은 그 직원의 대화에 있는 답변의 앞 600자, 전체는 대화 링크)에서 **보내기**(→ `pending`, 다음 실행기 차례에 보냄 — 보낼 곳이 아직 쓸 수 있는지 다시 봄) 또는 **보내지 않기**(→ `rejected`). `POST /api/apps/outbound-approvals/[id] { decision: 'approve' | 'reject' }`(`src/lib/apps/outbound/approval.ts`). 남의 기록·다른 기관은 404, 이미 정함·기한 지남·보낼 곳 회수는 409. 갱신은 조건부(이 직원·확인 기다림·기한 안)라 두 번 눌러도 한 번만 바뀐다. 누가·언제 정했는지(`decided_by`·`decided_at`)를 남기고 보안 로그 low(`app_outbound_result_approved`·`_rejected` — 기록 id·보낼 곳·앱만, 결과 글 없음).
- **7일 안에 정하지 않으면** 실행기 차례마다 그만둠(`gave_up`, '7일 안에 확인하지 않아 보내지 않았습니다.')으로 바꾼다. 보낼 곳을 회수하면 확인 기다림도 그만둔다.
- 앱 빌더의 '결과를 보낼 곳' 목록에 `(보내기 전 확인)`이 붙고, 관리자 화면의 최근 보내기에 '직원 확인 기다림'·'직원이 보내지 않음'과 확인한 때·사람이 보인다.
- 남은 것: 확인할 결과를 따로 메일로 알리지 않는다(실행 화면에서 본다). 일괄 실행은 마침 메일(2026-11-10 — [일괄 실행](APP_BATCHES.md))에 확인을 기다리는 결과 수가 실린다. 예약 결과는 그 앱의 실행 화면을 열어야 보인다. 결과 글을 고쳐서 보내지는 못한다(대화에서 고친 답은 보낼 결과가 아님).

## 실패와 다시 보내기

| 응답 | 처리 |
|---|---|
| 2xx | 보냄 |
| 3xx | 그만둠 — **리다이렉트는 따르지 않는다**(따라가면 승인한 주소 밖으로 결과가 간다) |
| 408·429·5xx·연결 실패·8초 넘음 | 1분·5분·30분·2시간 뒤 다시(첫 시도 포함 **5번**까지, 그다음 그만둠) |
| 그 밖 4xx | 그만둠(서명·주소 확인) |

- 보내기 **직전에** 보낼 곳·결과·앱을 다시 읽는다 — 회수됐거나 다른 기관이거나 대화를 지웠으면 보내지 않고 그만둔다. 읽기 자체가 실패하면 시도 수를 세지 않고 1분 뒤 다시.
- 차지는 조건부(`pending` → `sending`), `sending`이 10분 넘으면 실행기가 죽은 것으로 보고 다시 차지한다.
- 관리자 화면에는 상태·시도 수·마지막 응답 코드·이유만(결과 글은 없음).

## 사설 주소 막기(SSRF)

- 등록: https만, 아이디·비밀번호·443 밖 포트·`#` 없음, `localhost`·`.local`·`.internal` 등 내부망 이름·점 없는 이름 거절, IP 주소면 사설·되돌이·링크 로컬·멀티캐스트·문서용·CGNAT·클라우드 메타데이터(169.254.169.254)·IPv6 고유 로컬/링크 로컬/IPv4 품은 주소 거절(`isPrivateAddress` — 꼴을 모르면 막음). 이름이면 DNS로 풀어 **하나라도** 사설이면 거절.
- 보낼 때마다 다시 풀어 같은 검사(등록 뒤 DNS가 바뀌어도). 이름을 못 풀면 다시 보낼 일로 센다.
- **남은 위험**: 확인한 뒤 실제 연결 사이에 DNS 답이 바뀌는 경우(DNS rebinding)는 막지 못한다 — 보낼 곳은 기관 전체 관리자가 승인한 주소만이라 받아들인다.

## 데이터 흐름(보안 심사)

결과 글이 **기관 밖**(관리자가 승인한 주소)으로 나간다 — 서비스 정의서 6절(데이터 흐름)에 '앱 결과 보내기: 승인한 https 주소로 결과 글, 서명·5번까지 다시'를 더한다. 보낸 결과 글은 따로 저장하지 않는다(메시지에서 그때 읽는다). 대화를 지우면 보내지 않은 기록도 함께 지워진다(외래 키 연쇄).

## 남은 것

- 보내는 곳은 앱 하나에 하나, 결과 글과(고르면) 결과 한글 파일 하나뿐(첨부한 원자료·표·엑셀은 보내지 않음). 받는 쪽의 응답을 앱이 다시 받아 쓰지 않는다(쓰기 결과 확인·동작 고르기 같은 범용 연계는 아님 — 보내기 전 사람 확인은 0078로 넣었다).
- 즉시 보내지 않고 5분 주기다. 실패 메일 알림은 없다(관리자 화면에서 본다).
- 화면은 브라우저로 보지 않았다. 실제 외부 주소로 보내 보지 않았다(시험은 가짜 fetch·가짜 DNS). 함께 실은 한글 파일을 받는 쪽에서 한글로 열어 보지는 않았다(만든 바이트를 다시 읽어 글만 확인).
