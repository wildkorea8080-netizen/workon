# 웹사이트도 REA로 분석할 수 있는가

가능하다. 설치 파일이 있어야만 REA를 쓸 수 있다는 설명은 정확하지 않다. 다만 브라우저가 실제로 받은 것·관찰한 것과 서버 내부를 구분해야 한다.

## 가능한 분석

| 대상 | 알 수 있는 것 | 알 수 없는 것 |
|---|---|---|
| 공개 홈페이지·사용 문서 | 제품 기능·입출력·사용 흐름·공개 앱 목록 | 실제 계정의 기능 허용·성능·내부 구조 |
| 브라우저 화면·접근성 트리 | 메뉴·버튼·상태·폼·결과 화면 | 서버 코드·DB 스키마 |
| 내려온 JavaScript·공개 소스맵 | 클라이언트 모듈·라우트·상태 처리·호출 흔적 | 내려오지 않은 코드·원본 전체·비공개 프롬프트 |
| 선택한 브라우저 대상의 수동 동작 관찰 | 관찰 창 동안의 요청 경로·응답 형태·콘솔·실행 연계 | 과거 통신·다른 탭·보이지 않은 서버 동작 |
| 제공된 HAR | 저장 당시 요청·응답의 한정된 구조 | 현재 API 상태·현재 동작의 자동 입증 |

로그인할 수 있는 정식 계정에서 기능을 사용하면 공개 자료보다 구체적인 실험이 가능하다. 인증을 우회하거나 비공개 API를 임의로 호출할 필요는 없다. REA의 수동 관찰 기능은 스스로 클릭·탐색하지 않으며 UI 조작 도구와 역할이 다르다.

## 이번에 확인한 도구

설치된 REA CLI 버전: 6.4.0. 스킬 버전: 37.

- `rea doctor --client codex --json`: Node 사용 가능, Codex MCP 등록 `config_drift`.
- `rea analyze-web-bundle --help`와 `--schema`: 선택한 loopback CDP endpoint와 `list-browser-targets`에서 얻은 targetId로 페이지 번들을 수집·정적 분석하는 명령을 확인했다.
- `list-browser-targets`, `inspect-web-page`, `observe-web-session`, `inspect-web-network-capture`, source map 관련 명령이 CLI 도움말에 있다.
- 최초 조사 당시 MCP 연결이 없었으나, Codex 등록·재시작 후 실제 REA MCP 연결을 확인했다. 별도 임시 Edge 프로필을 열고 loopback CDP 대상에서 공개 페이지를 분석했다.

후속 실제 분석에서는 공개 Works 페이지의 DOM·접근성·스크립트를 수집하고 번들을 분석했다. Desktop 상세 링크, 문서 Q&A 탭, 인터넷 관련 FAQ를 controlled browser scenario로 조작했으며 일본어 앱 목록의 검색·분류 컨트롤을 관찰했다. [실행 분석 보고서](REA_PUBLIC_WEB_ANALYSIS.md)에 Evidence ID·확인 결과·실패·한계를 기록했다. 인증된 SaaS의 실제 업무 처리와 서버 구현은 여전히 미확인이다. 네이티브 디컴파일 엔진 설치는 이번 웹 분석에 필요하지 않았다.

## 향후 실제 계정에서 확인할 시나리오

1. 선택한 공식 앱 한 개를 실행하고 입력·결과·중간 상태를 기록한다.
2. 앱을 복제해 역할·입력 변수·자료 범위·출력 형식을 바꾼다.
3. 앱을 시험한 판과 공유한 판이 어떻게 달라지는지 확인한다.
4. 권한이 다른 두 정식 계정으로 앱·문서·실행 결과 접근을 비교한다.
5. 오류·취소·대용량 일부 실패·재실행에서 결과 중복과 보존을 본다.
6. 연결 도구의 읽기·쓰기·승인·예약·자격 증명 수명을 확인한다.

공개 사이트의 예시 애니메이션이 아니라 실제 계정 동작을 관찰해야 위 항목을 실행 확인으로 올릴 수 있다. 서버 구현은 여전히 미확인일 수 있다.
