# 입력값에 따른 선택적 단계 실행

2026-10-31. 앱 빌더의 단계 편집기에 **실행 조건**을 추가했다. 입력 폼의 ‘목록에서 선택’ 항목과 그 선택값을 고르면 일치할 때만 해당 중간 단계를 실행한다. 조건이 없으면 기존처럼 항상 실행한다.

## 직원 흐름

1. 입력 항목에 ‘검토 여부’ 같은 목록 선택을 추가하고 ‘예/아니오’ 값을 정한다.
2. 조건을 적용할 중간 단계에서 ‘검토 여부 값으로 결정 → 예’를 선택한다.
3. 마지막 결과 작성 단계는 ‘항상 실행’으로 둔다.
4. 앱 실행 시 입력 선택에 따라 단계가 실행되거나 ‘조건에 따라 건너뜀’으로 표시된다.

마지막 단계를 조건부로 만들 수 없다. 순서를 바꿔 조건부 단계가 마지막으로 이동하면 조건 해제를 안내하고 저장을 거절한다. 선택 항목을 삭제하거나 종류/선택값을 바꿔 조건이 더 이상 유효하지 않으면 다시 선택하거나 해제해야 저장할 수 있다.

## 서버·기록 계약

- 저장/실행/과거 판 복원에서 같은 앱 정의 검사를 사용한다. 실제 존재하는 선택형 필드·현재 선택값만 허용한다.
- 조건 비교는 서버가 검증·정규화한 입력값의 문자열 일치로 수행한다. 클라이언트가 전달하는 내부 단계 입력은 사용하지 않는다. 코드·수식·모델 분류로 조건을 평가하지 않는다.
- 조건 불일치 단계는 모델을 호출하지 않고 토큰을 추가하지 않는다. 비워 둔 선택적 항목도 불일치로 처리한다. 필수 입력은 기존처럼 먼저 검증한다.
- 건너뜀(skipped), 실행 전 실패 때문에 못 한 단계(not_run), 실패(failed)는 서로 다른 상태로 저장·표시한다.
- 다음 단계에는 완료된 결과만 전달한다. 모든 중간 단계가 생략돼도 마지막 단계는 원래 입력을 받아 실행한다.
- HWPX 내보내기는 정상 건너뜀을 허용하지만, 마지막 단계 완료와 나머지 단계의 정상 완료/건너뜀 여부를 검사한다. 실제 실패와 미실행이 섞인 결과는 거절한다.
- 기존 단계 없는 앱·무조건 단계 앱은 호환 유지. 조건은 기존 app_definition JSONB와 버전 사본에 함께 저장되므로 새 마이그레이션은 없다.

## 여러 조건·비교 (2026-11-01)

알리웍스 공개 가이드의 조건 노드(옵션 안 조건은 AND)를 참고해 단계 조건을 넓혔다. 마이그레이션 없음(app_definition JSONB 그대로).

- **꼴**: `when: { all: [{ field, op, value? }] }` — 규칙이 **모두** 맞을 때 실행(AND), 단계마다 1~3개(`APP_MAX_RULES`). OR·그래프 분기는 여전히 없다.
- **항목 종류별 비교**(`APP_CONDITION_OPS` — 화면 선택지와 서버 검사가 같은 표):

  | 종류 | 비교 |
  | --- | --- |
  | 목록 선택 | 같음 · 같지 않음 · 입력됨 · 비어 있음 |
  | 짧은 글·긴 글 | 포함 · 포함하지 않음 · 입력됨 · 비어 있음 (대소문자 무시, 값 1~80자 한 줄) |
  | 숫자 | 같음 · 같지 않음 · 보다 큼 · 이상 · 보다 작음 · 이하 · 입력됨 · 비어 있음 (숫자로 비교 — `30.0` = `30`) |
  | 날짜 | 같음 · 이전 · 이후 · 입력됨 · 비어 있음 (YYYY-MM-DD 달력 순) |

- **비운 입력은 ‘비어 있음’에만 맞는다.** ‘같지 않음’·‘포함하지 않음’·숫자 비교도 거짓이다 — 입력하지 않은 값을 실행 근거로 쓰지 않는다(기존 ‘빈 선택은 불일치’와 같은 원칙).
- 판정은 `definition.ts`의 `conditionHolds` 한 곳이고 실행기(`pipeline.ts`)와 재개 검사(`resume.ts`)가 함께 쓴다. 서버가 검사한 입력값만 보고 코드·수식·모델로 평가하지 않는다. 검사에 걸리는 값(목록 밖 선택값·숫자 아닌 값·없는 날짜·종류에 맞지 않는 비교·`filled`에 값)은 저장 거절.
- **옛 조건 호환**: 저장된 `{ field, equals }`는 검사(`validateAppDefinition`)가 `{ all: [{ field, op: 'equals', value }] }`로 바꾼다 — 실행·재개·복사·과거 판 복원이 모두 이 검사를 거친다. 편집 화면은 불러올 때 `upgradeAppConditions`로 꼴만 바꾼다(지워진 항목을 가리키는 조건도 보여 고치게 한다). 다음 저장부터 새 꼴로 남는다.
- **화면**: 단계마다 ‘항상 실행 / 아래 조건이 모두 맞을 때만 실행’, 규칙 줄(항목·비교·값 — 목록이면 선택값, 숫자·날짜는 그 입력칸), ‘+ 조건 추가 (그리고)’, ‘조건 삭제’. 이제 목록 선택이 없어도 조건을 쓸 수 있다.

검증:

## 갈래 — 선택지 여럿 중 위에서부터 처음 맞는 하나 (2026-11-02)

알리웍스 조건 노드의 '옵션을 위에서 아래로 판정해 처음 맞는 옵션으로 간다'를 우리 1~3단계 구조 안에서 받았다. 그래프 분기·병합이 아니라 **단계 하나가 입력값에 따라 다른 지시로 처리**된다. 마이그레이션 없음(`app_definition` JSONB 그대로, 옛 정의는 갈래가 없을 뿐).

- **꼴**: `steps[].branches?: [{ name, when: { all: [규칙 1~3] }, instruction }]` — 단계마다 1~3개(`APP_MAX_BRANCHES`). 갈래마다 조건이 꼭 있고(없으면 저장 거절), 이름은 40자·한 단계 안에서 서로 다름, 지시는 2,000자. 규칙은 단계 조건과 같은 표(`APP_CONDITION_OPS`)·같은 검사(`normalizeRule`).
- **판정**(`definition.ts` `chooseBranch`): 단계가 건너뛰어지지 않을 때, 갈래를 **위에서부터** 보고 규칙이 모두 맞는 **첫 갈래** 하나를 고른다. 맞는 갈래가 없으면 단계의 **기본 지시**로 처리한다(갈래는 기본 지시를 대신하는 것이지 단계를 건너뛰는 것이 아니다). `when`(건너뛰기)과 갈래는 따로다 — 건너뛴 단계는 갈래를 보지 않는다.
- **마지막 단계도 갈래를 둘 수 있다**(조건으로 건너뛸 수는 없어도) — 민원 종류에 따라 최종 회신 꼴을 달리하는 데 쓴다.
- **실행**(`pipeline.ts`): 고른 갈래의 지시가 `현재 처리 단계: {단계} — {갈래}` 아래 들어간다. 단계 기록(`app_steps[]`)에 `branch`(갈래 이름)를 남긴다 — 기본 지시로 돌았으면 칸이 없다. 사용량 계산은 그대로(단계 하나에 모델 호출 하나).
- **재개**(`resume.ts`): 완료 단계를 재사용할 때 **기록의 `branch`와 지금 정의·입력으로 고를 갈래가 같아야** 한다. 갈래를 고치거나 없앤 뒤 재개하면 '단계의 갈래가 기록과 다릅니다'로 거절한다 — 다른 지시로 만든 결과를 잇지 않는다.
- **화면**: 단계 카드 아래 '갈래 (선택)' — 갈래마다 이름·조건 줄(항목·비교·값, `+ 조건 추가 (그리고)`)·이 갈래일 때의 지시·'갈래 삭제', `+ 갈래 추가`(3개까지). 새 갈래는 첫 항목의 기본 규칙 하나와 빈 지시로 시작하고 지시를 넣어야 저장된다. 갈래의 마지막 조건은 지우지 못한다(갈래를 지운다). 실행 결과·실행 기록에는 `N. 단계 · 갈래: 이름`으로 보인다.
- **관리자 실행 현황**(`app_run_states`)은 단계 이름·상태만 돌려주므로 갈래 이름은 거기 안 간다.

검증: `app-pipeline.test.ts`(검사 허용·거절 9가지, `chooseBranch` 순서, 갈래 지시·기록·마지막 단계 갈래·기본 지시 되돌아감, 건너뛴 단계는 갈래 없음), `app-resume.test.ts`(갈래 일치할 때만 재사용), `app-step-editor.test.ts`(갈래 렌더링·3개 상한·새 갈래 기본값), `app-history.test.ts`(갈래 이름만 실리고 결과 글은 안 실림). 실제 모델 실행·브라우저 확인·운영 배포는 하지 않았다. 여전히 없는 것: 그래프 분기/병합, 반복, OR 조건, 갈래마다 다른 다음 단계로 건너뛰기.

## 또는(OR) 조건 (2026-11-04)

단계 실행 조건과 갈래 조건에서 규칙을 **하나라도** 맞을 때로 묶을 수 있다. 마이그레이션 없음(app_definition JSONB 그대로).

- **꼴**: `when: { any: [{ field, op, value? }] }` — 규칙 중 하나라도 맞으면 실행. `all`(모두)과 `any`(하나라도) 중 **하나만** 둔다(둘 다·둘 다 없음은 거절). 규칙 수·종류별 비교·값 검사는 `all`과 같다(1~3개).
- **판정**: `conditionHolds`가 `any`면 `some`, `all`이면 `every`. 규칙 하나의 판정(`ruleHolds`)은 그대로라 **비운 입력은 여전히 '비어 있음'에만 맞는다** — `any`라도 입력하지 않은 값이 '같지 않음'으로 실행 근거가 되지 않는다.
- 꼴을 직접 들여다보지 않도록 `conditionRules`·`conditionMode`·`makeCondition`을 둔다(편집 화면이 쓴다). 실행기·재개 검사·복사·과거 판 복원은 `conditionHolds`·`validateAppDefinition`을 거치므로 그대로 따라온다. 옛 `{ field, equals }` 꼴은 지금처럼 `all`로 바뀐다.
- **화면**: 단계 실행 조건 고르기에 '아래 조건 중 하나라도 맞을 때 실행'을 더했고, 갈래마다 '모두 맞을 때(그리고) / 하나라도 맞을 때(또는)' 고르기를 두었다. '+ 조건 추가' 단추는 고른 방식을 따라 '(그리고)'·'(또는)'으로 바뀐다. 마지막 단계는 여전히 조건을 둘 수 없다.
- AND와 OR을 섞는 묶음(`(가 그리고 나) 또는 다`)은 없다 — 갈래를 둘로 나눠 쓴다(갈래는 위에서부터 처음 맞는 하나).

검증: `tests/app-pipeline.test.ts`(any 허용·정규화, 거절 5가지, 하나라도 맞음/아무것도 안 맞음, 비운 입력, 갈래 고르기, 옛 꼴 변환이 any를 건드리지 않음, 마지막 단계 거절, 실행기의 건너뜀·모델 호출 수), `tests/app-step-editor.test.ts`(단계·갈래의 묶음 고르기와 단추 글). 전체 141파일 2,440개 통과, tsc 0, `next build` 통과. 브라우저 확인·실제 모델 실행은 하지 않았다.

## 분류 단계 — 앞 단계 AI의 판단으로 가르기 (2026-11-05)

지금까지 조건·갈래는 **직원이 넣은 입력값**만 봤다. 민원 종류처럼 입력 글을 읽어야 알 수 있는 것으로는 가를 수 없었다. 중간 단계 하나를 **분류 단계**로 두면 그 단계의 AI가 정해 둔 선택지 **하나만** 고르고, 뒤 단계의 실행 조건·갈래가 그 결과로 가른다(알리웍스 대화형 앱의 'LLM이 고른 값으로 조건 노드' 꼴을 우리 1~3단계 안에서). 마이그레이션 없음(`app_definition` JSONB 그대로).

- **꼴**: `steps[].classify: { options: string[] }` — 서로 다른 2~6개, 하나에 30자·한 줄(저장 때 앞뒤 공백을 뗀다). 단계 지시는 '고르는 기준'이다. AI 처리 중간 단계만 — 마지막 단계·공공 데이터 조회 단계는 분류 단계가 될 수 없고, 분류 단계에는 갈래를 두지 않는다(다음 단계에서 결과로 가른다). 분류 단계 자신도 입력값 조건으로 건너뛸 수 있다.
- **조건 항목 `@N`**: N번째 단계의 분류 결과(`classifyKey`). 그 단계보다 **뒤** 단계의 실행 조건·갈래에서만 쓸 수 있고(`conditionFields` — 화면 항목 고르기와 저장 검사가 같은 목록), 비교는 **같음·같지 않음**만, 값은 그 단계의 선택지만. 앞·자기 단계를 가리키거나 분류 단계가 아닌 단계를 가리키면 저장 거절. 입력 항목 키는 영문 소문자로 시작하므로 겹치지 않는다.
- **실행**(`pipeline.ts`): 분류 단계는 `classifySystem`(기준 + '선택지 글자 그대로 한 줄만, 이유·설명 없이' + 선택지 목록)으로 모델을 한 번, 출력 상한 60토큰(`APP_CLASSIFY_TOKENS`)으로 부른다. 답은 `classifyAnswer`가 읽는다 — 앞뒤 따옴표·괄호·별표·마침표를 떼고 선택지와 같으면 그것, 아니면 답 안에 선택지가 **정확히 하나** 들었을 때 그것(짧은 선택지가 긴 선택지 안에 든 경우는 긴 쪽). **둘 이상이거나 없으면 단계를 멈춘다**(`분류 결과가 선택지(…)에 없습니다`) — 지어낸 분류로 다음 단계를 가르지 않는다. 쓴 토큰은 멈춰도 사용량에 든다. 고른 값은 기록 `app_steps[]`에 `kind: 'classify'`·`output`으로 남고, 조건 판정 값(`evaluationInputs` — 입력값 + 끝난 분류 결과)에 `@N`으로 들어간다. 분류 결과는 다음 단계의 '이전 단계 작업 결과'로도 실린다.
- **비운 값 원칙 그대로**: 분류 단계가 건너뛰어졌거나 아직 안 돌았으면 `@N`은 비어 있어 '같음'·'같지 않음' 모두 거짓이다.
- **재개**(`resume.ts`): 재사용할 분류 기록은 `kind: 'classify'`이고 값이 **지금 선택지 안**이어야 한다(선택지를 고쳤으면 새로 실행). 분류였던 단계가 지금은 보통 단계면 거절. 재사용한 분류 결과로 뒤 단계의 건너뛰기·갈래를 실행기와 같은 값으로 맞춰 본다.
- **화면**: 단계 카드의 '분류 단계로 쓰기' 체크(마지막 단계는 막힘)와 선택지 칸(쉼표로 구분), 켜면 그 단계의 갈래 칸이 사라진다. 뒤 단계의 조건·갈래 항목 고르기에 'N단계 분류 결과(단계 이름)'가 생긴다. 실행 결과에는 `N. 단계 · 분류: 질의`. 단계 순서를 바꿔 분류 결과를 앞 단계가 가리키게 되면 그 조건은 '삭제된 항목'으로 보이고 저장이 거절된다.

검증: `tests/app-classify-step.test.ts`(13개 — 정의 허용·거절 14가지, 조건 항목·비교, 답 읽기, 실행 두 갈래·멈춤·사용량, 분류 지시 글, 재개 재사용·거절 4가지, 편집기·실행 결과 렌더링). 전체 2,743개 통과·tsc 0. **실제 모델로 분류가 잘 되는지는 재지 않았다**(비용 — 사용자 결정), 브라우저 확인·운영 배포 없음. 여전히 없는 것: 반복, 갈래마다 다른 다음 단계로 건너뛰기(분류 결과로 단계 조건을 걸어 대신한다), 프로세스 종료 후 자동 복구.

## 반복 단계 — 목록의 줄마다 (2026-11-06)

같은 처리를 여러 항목에 하는 앱(질의 목록마다 답 초안, 사업 목록마다 요약)을 위해 중간 AI 단계를 **긴 글 입력의 줄마다 한 번씩** 돌린다. 마이그레이션 없음(`app_definition` JSONB 그대로).

- **꼴**: `steps[].repeat: { field }` — `field`는 **긴 글(textarea) 입력 항목**만. AI 처리 중간 단계만(조회·분류 단계·마지막 단계는 안 됨). 갈래·실행 조건과 함께 쓸 수 있다(갈래는 단계에 한 번 고르고 모든 줄에 같은 지시).
- **줄**(`repeatItems`): 앞뒤 공백을 떼고 빈 줄은 뺀다. 한 줄은 300자에서 자른다. **8줄까지**(`APP_REPEAT_MAX`) — 줄이 없거나 넘으면 모델을 부르지 않고 직원이 고칠 안내로 멈춘다(`AppInputError`).
- **실행**(`pipeline.ts`): 줄마다 정책 확인(`guard`) → 모델 한 번(지시 끝에 `이번 항목(2/3): …` + '이 항목에 대한 결과만'). 이전 단계 결과는 모든 줄에 같이 간다. 결과는 줄 순서대로 `### 1. 항목` 머리를 달아 이어 붙이고(합쳐 12,000자까지 — 넘으면 멈춤), 기록에 `repeated`(줄 수)를 남긴다. **줄마다 사용량이 든다** — 중간 줄이 비거나 길이 상한에 닿으면 그 자리에서 멈추고 앞 줄까지 쓴 토큰은 사용량에 남는다. 체크포인트는 단계 단위다(재개하면 반복 단계를 처음부터 다시 돈다 — 줄 단위 재사용은 없음).
- **재개**: 끝난 반복 단계는 다른 단계처럼 재사용하고 `repeated`를 그대로 남긴다(입력이 같아야 재개되므로 줄도 같다).
- **화면**: 단계 카드의 '목록의 줄마다 반복' 체크와 반복할 항목(긴 글 항목만 — 없으면 막힘, 마지막 단계도 막힘). 분류 단계로 바꾸거나 조회로 바꾸면 반복을 뗀다. 실행 결과에는 `N. 단계 · 반복 3줄`.

검증: `tests/app-repeat-step.test.ts`(8개 — 정의 허용·거절 6가지, 줄 나누기, 실행 세 줄·지시·이어 붙이기·사용량, 줄 없음·너무 많음, 중간 실패·토큰 보존, 재개, 편집기·결과 렌더링). 전체 2,795개 통과·tsc 0. 실제 모델 실행·브라우저 확인·운영 배포 없음. 여전히 없는 것: 반복 안 줄 단위 재사용, 프로세스 종료 후 자동 복구(파일마다 반복은 아래 절 — 2026-11-07).

## 반복 단계 — 첨부 파일마다 (2026-11-07)

'목록의 줄마다'에 이어 **파일마다**를 받았다. 부서별 보고서 세 개를 하나씩 요약한 뒤 마지막 단계에서 종합하는 앱처럼, 같은 처리를 파일마다 한다. 마이그레이션 없음.

- **정의**(`definition.ts`): `steps[].repeat = { files: true }`(`repeatsFiles`). 줄마다(`{ field }`)와 같은 규칙 — AI 처리 중간 단계만(조회·분류·마지막 단계 아님). **앱이 파일 첨부 받기를 켰을 때만** 받는다(꺼진 앱은 '파일마다 반복하려면 앱 설정에서 파일 첨부 받기를 켜 주세요'). `{ files: true, field }`처럼 둘 다 적은 값은 거절.
- **반복하는 것**: 이번 실행의 원자료 파일 — 올린 파일 다음 문서함에서 고른 문서, 원자료 자리와 같은 순서(`prepare.ts`가 `appFileNames`로 넘기고 실행기가 `files`로 싣는다). 예약·연동이 저장한 문서함 문서도 같은 길이라 함께 센다. 앱 파일 상한이 3개라 반복도 3번까지다.
- **실행**(`pipeline.ts`): 파일마다 정책 확인 → 모델 한 번(지시 끝에 `이번 파일(2/3): 이름` + '첨부 원자료 가운데 이 파일의 내용에 대한 결과만, 다른 파일은 다루지 말고, 찾지 못하면 찾지 못했다고만'). **원자료는 매번 전부 간다**(파일만 떼어 보내지 않음 — 줄마다와 같은 꼴, 입력 토큰이 파일 수만큼 든다). 결과는 `### 1. 파일 이름` 머리로 이어 붙이고 기록에 `repeated`(파일 수)·`repeatedFiles: true`. 파일이 없으면 모델 없이 '반복할 파일이 없습니다' 안내로 멈춘다. 중간 실패·토큰 보존·12,000자 상한은 줄마다와 같다.
- **긴 첨부**: 나눠 추릴 때(맵·리듀스) 지시에 '어느 파일에서 온 내용인지 파일 이름을 함께'를 더했다 — 추린 글에서 파일을 가려 찾게. 다만 추린 글은 모델이 쓴 글이라 파일 구분이 흐려질 수 있다.
- **화면**: 단계 카드의 '반복' 체크 아래 고르기에 '○○의 줄마다'(긴 글 항목)와 '첨부 파일마다 (문서함에서 고른 문서 포함)'(파일 받기를 켠 앱만). 실행 결과는 `· 반복 2개 파일`. 파일 앱은 전처럼 이어 실행 대상이 아니다.

검증: `tests/app-repeat-files.test.ts`(8개 — 정의 허용·거절(파일 받기 꺼짐·마지막·조회·분류·이상한 값), 실행 세 파일·지시·원자료 그대로·이어 붙이기, 파일 없음, 중간 실패·토큰 보존, 준비·실행기 연결, 추리기 지시, 편집기·결과 렌더링). 전체 2,912개 통과·tsc 0. **실제 모델로 파일을 잘 가려 쓰는지는 재지 않았다**(비용), 브라우저 확인 없음, 2026-11-07 운영 배포(`dpl_8yP1r9js9VX6VXry6oxbsfvYUZrT`). 여전히 없는 것: 반복 안 파일 단위 재사용(줄 단위는 아래 절), 파일만 떼어 보내기, 프로세스 종료 후 자동 복구.

## 반복 단계 — 줄 단위 이어 실행 (2026-11-07)

줄마다 반복이 도중에 멈추면(줄 결과가 비거나 길이 상한·사용량 한도·모델 오류) 전에는 이어 실행해도 반복 단계를 처음부터 다시 돌아 **끝난 줄의 사용량이 또 들었고**, 반복이 첫 단계면 '재사용할 완료 단계가 없다'로 **아예 이어 실행할 수 없었다**. 마이그레이션 없음.

- **기록**(`pipeline.ts`): 줄 하나가 끝날 때마다 그 줄의 결과 글을 단계 기록 `partial`(줄 순서)에 쌓는다. 단계가 다 끝나면 지운다. 멈추면 이 기록이 답변 행 `source_references.app_steps`에 그대로 저장된다(직원 본인의 대화 기록 — 관리자 실행 현황(0046)은 단계 이름·상태만 읽고, 앱 실행 기록 목록도 결과 글을 싣지 않는다).
- **재개**(`resume.ts` `reusablePartial`): 멈춘 반복 단계의 `partial`은 다음일 때만 다시 쓴다 — 줄마다 반복(파일마다는 아님 — 파일 앱은 원래 이어 실행 대상이 아님)·지금 입력의 줄 수보다 적음·글이 모두 비지 않은 글자·합쳐 12,000자 안·갈래가 지금 고를 갈래와 같음·실행 조건이 지금도 맞음. 하나라도 아니면 그 단계를 처음부터 돈다(재개 자체는 다른 완료 단계가 있으면 된다). **끝난 줄이 있으면 완료 단계가 없어도 이어 실행할 수 있다.** 입력이 같아야 재개되는 규칙(원래 입력과 글이 같음)·앱 판 일치·본인 기록은 그대로다.
- **이어 실행**: 끝난 줄은 모델을 부르지 않고 그 글로 `### N. 항목` 머리를 다시 달아 잇고, 남은 줄만 부른다. 또 멈추면 새로 끝난 줄까지 더해 남는다. 기록에 `reusedItems`(다시 쓴 줄 수).
- **화면**: 멈춘 단계는 `· 2줄까지 끝남 — 이어 실행하면 다음 줄부터`, 이어 실행한 단계는 `· 반복 3줄 (앞 2줄은 이전 결과)`. 이어 실행 미리 채우기(`resume-client.ts`)도 멈춘 단계의 끝난 줄을 싣는다.

검증: `tests/app-repeat-resume.test.ts`(9개 — 멈추면 앞 줄 기록, 다 끝나면 지움·이어 실행은 남은 줄만·같은 꼴로 잇기, 또 멈추면 더하기, 줄 수 이상이면 처음부터, 첫 단계 반복의 이어 실행, 다시 쓰지 않는 7가지, 앞 단계 완료 + 끝난 줄, 파일마다 기록은 안 씀, 결과 화면 두 표시). 전체 2,921개 통과·tsc 0. 실제 모델·브라우저 확인 없음. 여전히 없는 것: 파일마다 반복의 파일 단위 이어 실행(파일 앱은 이어 실행 대상이 아님), 프로세스 종료 후 자동 복구(지금도 직원이 '이어 실행'을 눌러야 한다).

## 앱 실행의 시간 예산 (2026-11-07)

긴 첨부 추리기(조각 6개 + 합치기)와 8줄 반복, 마지막 단계가 겹치면 한 번의 실행이 함수 시간 제한을 넘길 수 있다. 함수가 끊기면 실패 처리(`catch`)도 돌지 못해 **끝난 단계·줄이 하나도 저장되지 않고**, 이어 실행할 기록도 남지 않는다(직원 화면에는 끊긴 응답만). 마이그레이션 없음.

- **예산**(`stream.ts` `APP_STEP_TIME_BUDGET_MS` 180초): 턴을 시작하고 3분이 지나면 긴 첨부 추리기·중간 단계가 **새** 모델 호출을 시작하지 않는다 — 호출 전 검사(`guard`, 기관 한도·모델 정책을 보던 곳)가 시간을 먼저 본다(DB를 부르지 않음). 멈추면 직원이 고칠 수 있는 안내(`APP_TIME_BUDGET_MESSAGE` — '처리 시간이 길어 여기서 멈췄습니다. 끝난 단계·줄은 기록에 남았습니다 — 이어 실행하거나, 입력·첨부를 줄여 다시 실행해 주세요.')를 보내고 멈춘 기록을 저장한다. 줄마다 반복이면 끝난 줄부터 이어 실행된다(위 절). 진행 중이던 호출 하나와 마지막 단계·저장이 끝날 몫(약 2분)이 남는다. 마지막 단계는 예산으로 끊지 않는다.
- **함수 시간 제한**: `/api/chat`에 `maxDuration = 300`을 적었다(전에는 설정이 없어 플랫폼 기본값). 연동(`/api/apps/webhook`)·예약(`/api/cron/app-schedules`)은 원래 300초.
- **예약 실행기**: 한 번 불릴 때 예약을 3개까지 차례로 돌리므로(시작은 180초 안에서만), 실행마다 3분이면 셋째 실행이 300초를 넘길 수 있다. 그래서 실행기 호출 전체의 마감(호출 시작 + `SCHEDULE_TURN_DEADLINE_MS` 200초)을 실행마다 넘긴다(`execute(row, deadlineAt)` → `executeSchedule` → `runAppAs` `deadlineAt` → `streamTurn` `deadlineAt`). 실행의 마감은 '턴 시작 + 3분'과 이 값 중 이른 쪽이다. 마감에 걸린 실행은 예약 기록에 실패로 남는다(연속 3회면 멈춤 — 기존 규칙). 연동은 한 호출에 실행 하나라 턴 예산만 쓴다.
- **알려진 한계**: 모델 호출 하나가 오래 걸리면(마지막 단계의 긴 답) 여전히 300초를 넘길 수 있다 — 끊기면 전처럼 기록이 남지 않는다. 예산·마감 값은 실제 모델 시간으로 재지 않고 상한에서 거꾸로 잡았다.

검증: `tests/stream-turn.test.ts`(예산을 넘기면 다음 호출을 안 하고 끝난 줄·안내·사용량을 남김, 넘겨받은 마감이 더 이르면 그것을 따름, 예산 안이면 평소처럼, 라우트의 300초), `tests/app-schedules.test.ts`(실행기가 예약마다 같은 마감을 넘김, `executeSchedule`이 마감을 실행기에 넘기고 없으면 안 넘김). 전체 2,927개 통과·tsc 0. 실제 긴 실행으로 함수 시간을 잰 확인·브라우저 확인 없음.
