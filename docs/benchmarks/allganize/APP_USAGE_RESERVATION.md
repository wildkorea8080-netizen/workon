# 입력형 앱 실행의 사용량 예약 (2026-11-26, 0122)

## 왜

입력형 앱 실행은 모델을 여러 번 부른다(중간 단계·분류·반복·긴 첨부 추리기·되돌아가기). 예전엔 시작할 때 한도가 **아직 남았는지**만 보고, 단계마다 다시 봐서 도중에 한도에 닿으면 멈췄다.

- 그때까지 쓴 금액은 결과 없이 사라졌다.
- 거의 동시에 시작한 실행·대화가 같은 여유를 함께 썼다. 일괄 실행은 두 줄씩, 예약은 같은 시각에 여럿 돈다.

실행 전 예상 AI 호출 수 표시(2026-11-07)는 있었지만 예약은 아니었다.

## 무엇을 하나

1. **시작하기 전에 예약한다.** 대화 준비(`prepareTurn`)의 맨 끝에서 이 실행이 많으면 쓸 금액을 어림한다(`estimateRunCostKrw`).
   - 예상 호출 수는 실행 화면과 같은 `estimateAppCalls`의 '많으면' 값을 쓴다.
   - 입력은 글자 하나를 토큰 하나로 센다(넉넉히). 단계마다 앞 결과가 입력에 쌓인다(출력 상한 1,400).
   - 출력은 중간 단계 1,400 토큰, 마지막 단계 4,096 토큰으로 센다. 긴 첨부를 나눠 추리면 조각마다 한 번 더 센다.
   - 금액은 비서 모델의 단가로 매긴다. 적어도 1원, 많아야 1,000만 원이다.
2. **어디에 예약하나.** 금액 한도에만 예약한다(`amountHeadroom` — 판정과 같은 규칙). 금액 한도는 부서 월 한도, 개인 월 한도(개인 값이 없으면 부서 기본값), 연간 정액 계약 금액이다. 종량제의 월 토큰 한도는 금액이 아니라 예약하지 않는다. 금액 한도가 없는 기관은 예약 없이 예전처럼 돈다.
3. **모자라면 시작하지 않는다.** DB 함수 `usage_reserve`가 기관마다 잠금(트랜잭션 advisory lock)을 잡는다.
   - 범위마다(부서·개인·기관) **남은 금액 − 살아 있는 다른 예약 < 이번 금액**이면 넣지 않는다.
   - 그때 대화 준비는 만든 새 대화를 지우고 429로 답한다(`reason: 'usage_reservation'`). 안내 예: '이 앱 실행은 많으면 약 N원이 들 수 있는데 부서의 이번 달 남은 한도가 M원(실행 중인 다른 앱이 예약한 K원을 빼고)이라 도중에 멈추지 않도록 시작하지 않았습니다…'.
   - 거의 동시에 시작한 두 실행이 같은 여유를 두 번 예약하지 못한다.
4. **다른 판정도 예약을 센다.** `checkTokenLimit`은 금액 한도가 있을 때만 살아 있는 예약을 한 번 읽는다. 부서·개인·연간 판정은 **쓴 금액 + 예약**으로 막고, 막힌 안내에 '+ 실행 중인 앱이 예약한 N원'을 덧붙인다. 그래서 예약한 실행이 마칠 몫을 다른 대화가 먼저 쓰지 않는다.
5. **실행 중에는 자기 예약을 뺀다.** 실행 중 단계마다 다시 볼 때(guard)는 자기 예약을 빼고 본다(`excludeReservationId`).
6. **마치면 푼다.** 실행이 끝나면(실패해도) 예약을 지운다(`streamTurn`의 finally). 끊긴 실행의 예약은 기한(10분)이 지나면 세지 않고, 다음 예약 때 지운다.

손 실행·앱 예약·외부 연동·일괄 실행이 모두 같은 대화 준비를 타므로 함께 적용된다. 연동은 429를 받으면 예전 한도 초과처럼 멈춘다. 예약 실행기는 429를 실패로 센다. 일괄 실행은 2026-11-26부터 다른 실행이 쥔 예약이 풀리면 될 거절(`reservationWaitable` — 대화 준비가 거절 `details.waitable`로 싣고 `runAppAs`가 넘김)이면 묶음을 멈추지 않고 그 줄을 다음 차례에 다시 돌린다(시도 횟수 그대로 — [일괄 실행](APP_BATCHES.md)). 기다려도 안 될 거절은 예전처럼 멈춘다.

## 열림 규칙

한도 확인과 같다 — 과금 집계 오류로 서비스가 멈추면 안 된다.

- 남은 금액을 못 읽거나 예약을 못 쓰면 예약 없이 실행하고 운영 기록(`payment` warning)에 남긴다.
- 판정이 예약을 못 읽으면 예약 없이 판정하고, 확인하지 못한 단계(`unverified`)에 `reservations`를 적는다.
- 예약을 못 풀면 운영 기록에 남긴다. 기한이 지나면 세지 않는다.

## 한계

- 어림은 넉넉하다. 실제로는 다 쓰지 않을 금액을 잠깐 잡아 두므로, 한도 끝자락에서는 실제로는 마칠 수 있는 실행도 시작하지 않을 수 있다(도중에 멈추는 쪽보다 낫다고 판단).
- 조회 결과·되돌아가 다시 하는 단계의 늘어난 입력은 어림에 넣지 않는다.
- 이어 실행도 처음부터의 호출 수로 어림한다.
- 사진 첨부 바이트는 세지 않는다.
- 실행 화면에 예약 금액을 미리 보이지는 않는다. 거절될 때만 안내한다.

## 마이그레이션 0122

- `usage_reservations` 표: 기관·부서·직원·금액(0 초과 1,000만 원 이하)·기한(만든 때 뒤 1시간 안). 부서·직원·기관을 지우면 함께 지워진다. RLS를 켜고 정책을 두지 않았고, 공개 키 권한도 없다.
- `usage_reserve(uuid, uuid, uuid, numeric, jsonb, timestamptz)` 함수: 실행 권한은 service_role만.
- 추가만이라 여러 번 적용해도 안전하다.
- 코드 배포 전에 적용한다. 없으면 예약을 못 해 예약 없이 실행하고(운영 기록), 판정은 예약 없이 돈다 — 예전과 같다.
- 시험: `tests/batch-0308.test.ts`, `tests/prepare-preflight.test.ts`·`tests/stream-turn.test.ts`의 '사용량 예약' 묶음.
