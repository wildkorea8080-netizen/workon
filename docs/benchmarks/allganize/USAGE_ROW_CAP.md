# API 1,000행 상한 — 한도·통계·감사 자료가 조용히 덜 세던 문제 (2026-11-05)

## 무엇이 문제였나

Supabase API(PostgREST)는 한 번에 최대 행 수까지만 돌려준다. 기본값은 1,000이다. 그보다 많으면 **오류 없이 앞부분만** 온다.

여러 곳이 사용 기록(`usage_logs`)을 한도 없이 앱으로 읽어 합계를 냈다. 그래서 기간 안 기록이 1,000건을 넘는 순간 숫자가 더 늘지 않았다.

| 어디 | 무엇이 틀렸나 |
| --- | --- |
| **종량제 월 토큰 한도 판정**(`checkTokenLimit`, 모든 대화 앞) | 기관이 한 달에 대화 1,000번을 넘기면 토큰 합이 멈춰 **한도가 걸리지 않는다** |
| 예산 알림의 종량제 사용률 | 같은 이유로 덜 세어 80·90·100% 메일이 늦거나 안 간다 |
| 관리자 이용통계(`usage-summary`)·사용량 차트(`stats/usage`)·부서 통계(`stats`) | 합계·횟수가 덜 나온다 |
| 슈퍼관리자 대시보드·사용량·매출·기관 상세·기관 사용량·경보·실시간·API 키 사용량 | 같음 |

운영에는 아직 1,000건을 넘는 표가 없어(사용 기록 34건) 실제로 덜 센 적은 없다. 운영의 상한 값은 1,000행을 넘는 표가 없어 직접 확인하지 못했다. 그래도 Supabase 기본값이 1,000이라 고쳤다.

## 고친 것

- **한도·예산 판정은 DB가 센다**(0057 `organization_chat_tokens(기관, 시작)`).
  - 셈은 예전 식과 같다: `chat_message`의 `input_tokens + output_tokens`이고, 숫자가 아니면 0이다.
  - 매 대화마다 한 달 치 기록을 끌어오던 비용도 없앴다. 기관·활동·시각 색인을 하나 더했다.
  - `usage-limit.ts`의 두 곳(한도 판정·예산 알림 사용률)이 이 함수를 부른다.
- **화면용 합계는 쪽마다 끝까지 읽는다**(`src/lib/paged-select.ts`의 `pagedRows`).
  - 첫 쪽에서 전체 수를 받고, 남은 쪽을 4개씩 동시에 읽는다. 쪽이 겹치거나 빠지지 않게 id로 정렬한다.
  - 상한 50,000행에서 멈추고 `truncated`를 돌려준다. 이용통계 화면은 잘렸을 때 '앞의 50,000건만 셌습니다 — 기간을 줄여 보세요'를 보인다.
  - 한 쪽이라도 실패하면 일부만 센 합계를 내지 않고 오류를 돌려준다.
  - 바꾼 곳: 이용통계, 사용량 차트(문서·대화·기록 셋), 부서 통계, 슈퍼관리자의 대시보드 여섯 곳·사용량·매출·기관 상세·기관 사용량·경보·실시간·API 키 둘.
- **다시 생기지 않게** — `tests/paged-select.test.ts`가 `src` 전체에서 `usage_logs`를 읽는 select를 찾는다. 다음 셋 중 하나가 아니면 실패한다.
  - 쪽 읽기(`pagedRows`)
  - 개수만(`head: true`)
  - 줄 수 제한(`.limit`·`.range`)

  화면 없이 정리 예정인 `api/reports`는 뺐다.

## 확인

- 단위 시험: `tests/paged-select.test.ts` 8개.
  - 3,500행 끝까지, 1,000행 딱, 상한 잘림, 쪽 실패, 전체 수 모를 때를 다룬다.
  - 원본 검사(한도 없는 읽기 없음, 한도 판정은 DB 함수, 이용통계 잘림 표시)도 한다.
  - `budget-alerts.test.ts`는 종량제 사용률이 DB 함수를 부르고 기록을 읽지 않는지 본다.
- 로컬 시험 Postgres(54329)에 0057을 두 번 적용했다.
  - 실행 권한은 service_role만, 색인 하나를 확인했다.
  - **대화 기록 1,500건**(+ 토큰 없는 기록, 글자 토큰, 다른 활동, 지난달)을 넣고 이번 달 합을 냈다. **22,500**으로 기대값과 같았다. 앱으로 읽었으면 15,000에서 멈췄을 양이다.
- 실제 PostgREST로 1,000행을 넘겨 읽는 시험은 하지 않았다. 로컬 Supabase가 꺼져 있고, 운영 표가 작다.

## 둘째 묶음 — 다른 표 (2026-11-05)

`src` 전체에서 줄 수 제한 없는 조회 108곳을 뽑았다. 대부분은 기관의 부서·비서·금지어·설정처럼 작게 머무는 표라 그대로 두었다. **계속 커지는 표**와 **1,000을 넘는 `.limit`**을 골라 고쳤다.

| 어디 | 무엇이 틀렸나 | 고친 것 |
| --- | --- | --- |
| **감사 자료 CSV**(`audit-logs`, 정보공개 대응) | `.limit(50000)`이라 '최대 5만 건'이라 했지만 API가 1,000건에서 잘랐다. '5만 건 넘음' 경고는 5만이 기준이라 **경고 없이 덜 찬 감사 자료가 나갔다** | 쪽마다 끝까지(5만 건 상한), 정렬에 id를 더해 쪽이 겹치지 않게. 5만 건 넘음 경고는 실제 전체 수로 |
| 감사·이용통계의 직원 이름 사전 | 직원 1,000명이 넘는 기관에서 뒤쪽 직원이 '(삭제된 계정)'으로 보인다 | 쪽 읽기 |
| 업무 현황(`workStats`) | `.limit(10000)`도 1,000에서 잘려 작업·실패 수가 덜 나온다 | 쪽 읽기 |
| 내 사용현황(`my/stats`) | 대화·메시지 수가 덜 나오고, 대화 id 수백 개를 `in()`으로 넘겨 주소가 길어진다 | 대화를 끼워(`conversations!inner`) 걸러 쪽마다. `in('conversation_id', …)`을 쓰지 않는다 |
| 관리자 사용자 목록·슈퍼관리자 기관 사용자 목록 | 직원 1,000명 넘으면 목록이 잘린다 | 쪽 읽기 |
| 부서 목록의 인원·비서 수 | 큰 기관에서 0으로 보일 수 있다(삭제 판단은 `[id]` 라우트가 정확한 수로 다시 봐서 안전) | 쪽 읽기 |
| 관리자 문서 목록·비서 삭제 때 문서 치우기·올리기의 비서당 문서 수·규정 확인 업무의 기관 문서 | 문서가 1,000개를 넘으면 목록이 잘리고, 비서를 지워도 행이 남는다 | 쪽 읽기 |

문서 찾기의 비서 문서 조회는 비서당 50개 상한(`MAX_AGENT_DOCUMENTS`)이라 1,000에 닿지 않는다. 매 대화마다 도는 길이라 쪽 읽기의 개수 조회를 더하지 않았다(`.limit(1000)`만 명시).

**검사도 넓혔다**(`tests/paged-select.test.ts` 10개). `src` 어디서든 `.limit(N)`이 1,000을 넘으면 실패한다. 숫자로 쓰든 같은 파일의 상수로 쓰든 잡는다. 이 검사는 고치는 중에 실제로 남은 두 곳을 잡았다. 감사 CSV·업무 현황·사용자·문서 목록·내 통계가 쪽 읽기인지도 원본으로 본다.

## 셋째 묶음 — 이용통계를 DB에서 (2026-11-05, 0058)

이용통계(비서별·직원별·부서별)는 둘째 묶음 뒤에도 기록을 앱으로 읽어 묶어 **50,000행에서 멈췄다**. 큰 기관이 몇 달을 보면 앞부분만 셌다.

- `usage_summary`(0058)가 (묶음 · 활동 · 모델)마다 횟수·입력/출력 토큰·원가를 DB에서 세어 **jsonb 값 하나**로 돌려준다(행이 아니라 값이라 1,000행 상한에 안 걸린다).
- 이름 붙이기·합치기·정렬은 `src/lib/usage-summary.ts`가 한다. CSV 모양은 그대로다. 이름 사전은 보는 축의 것만 읽는다.
- 셈은 예전 앱과 같다. 다른 점 하나: 숫자로 읽히지 않는 토큰·원가 글자는 0이다(예전 `Number()`는 NaN을 만들어 그 묶음의 합계를 망가뜨렸다).
- 화면의 '앞의 50,000건만 셌습니다' 안내는 지웠다.
- 확인: 시험 Postgres에 두 번 적용, 실행 권한 service_role만. 1,505건(옛 모델 없음·글자 토큰·읽지 못하는 글자·비서 없는 기록·빈 비서 id·범위 밖 부서·기간 밖)을 넣고 세 축 모두 **예전 앱 셈과 묶음이 똑같은 것**을 봤다.
- 순서: **0058을 운영에 적용한 뒤 코드 배포.** 없으면 이용통계 화면만 실패한다. 운영 DB 적용 2026-11-05(함수·권한·PostgREST 호출 확인), 코드는 아직 미배포.

## 남은 것

- 작게 머무는 표(부서·비서·카테고리·금지어·설정·양식)의 한도 없는 조회는 그대로다. 기관당 1,000을 넘기 어려운 표라 두었다.
- 로그 보기 화면(접속·시스템·보안 로그)은 최근 순 목록이라 최근 1,000건만 보인다. 쪽 넘기기 화면은 따로 만들어야 한다.
- `api/reports`(화면 없음, 정리 예정)는 그대로다.


## 사용 기록 밖의 목록 (2026-11-06)

`usage_logs` 밖에서도 한 번에 다 읽는 조회를 훑어(`.from(…).select(…)`에 `limit`·`range`·`single`·`head`·`pagedRows`가 없는 곳) 커질 수 있는 둘을 고쳤다.

- **대화 목록의 첫 메시지 미리보기**(`GET /api/conversations`) — 쪽(20개)의 모든 대화에서 사용자 메시지를 한 번에 읽어, 합쳐 1,000개를 넘으면 뒤 대화의 미리보기가 조용히 빠졌다. 이제 대화마다 첫 사용자 메시지 하나만(`limit(1)`, 200자). 쪽 크기·시작은 1~100·0 이상으로 맞춘다(숫자가 아니면 범위 조회가 깨졌다)
- **슈퍼관리자 직원 목록**(`GET /api/super/accounts/users`) — 모든 기관의 부서·기관을 한 번에 읽어, 부서가 1,000개를 넘으면 뒤 부서의 이름이 '—'가 되고 **기관으로 거를 때 그 기관 부서가 빠져 직원이 목록에서 사라졌다**. 이제 `pagedRows`로 끝까지
- 보안 기록 개수(`GET /api/security-logs`)는 개수만 세도록 `head: true`(전에는 개수를 세며 최대 1,000행을 함께 받았다)

나머지 결과(부서·비서·초대·공지·대화 하나의 메시지 등)는 기관·사람·대화 하나 안의 작은 목록이라 그대로 두었다. `tests/row-cap-lists.test.ts`.
