# 알리웍스 앱 빌더·업무 흐름·연동 분석

조사: 2026-10-28 · 공개 공식 문서 기준 · WORKON SaaS 벤치마크용

## 조사 범위와 판정

- **D(문서 확인)**: 공식 가이드에 구성·행동이 구체적으로 설명됨. 제품을 직접 실행해 확인했다는 뜻은 아니다.
- **P(제품 소개)**: 공식 제품·마케팅 페이지의 소개 또는 시나리오. 실제 지원 범위·제공 플랜·수치 미검증.
- **H(과거 문서)**: 과거 공식 가이드. 설계 참고는 가능하지만 현재 UI/정책으로 확정하지 않음.
- **제안**: WORKON 독자 설계이며 경쟁 제품의 내부 구현을 관찰했다는 주장이 아니다.

로그인된 콘솔·실행·API 요청은 관찰하지 않았다. 문서의 스크린샷은 존재를 확인했으나 모든 이미지의 세부 문구를 판독하지 않았다. 특히 앱 입력 6종 중 본문에 설명된 3종만 이름을 확정했다. 공식 문서 사이에도 세대 차이가 있다. 아래는 기능 추출이지 공급자 소스·프롬프트·브랜드 UI 복제안이 아니다.

## 핵심 결론

알리웍스의 앱은 단순히 프롬프트를 붙인 카드 하나를 뜻하지 않는다. **입력 폼 중심 단발 실행, 여러 노드로 구성하는 대화형 흐름, 도구를 선택해 쓰는 에이전트**를 담는 배포 단위다. 단순한 비서 역시 앱으로 제공할 수 있어 WORKON의 비서와 개념이 겹친다. 핵심 차이는 명칭이 아니라 설정 가능한 실행 방식·입력·데이터·배포 권한·버전이다.

또한 **도구를 AI가 선택하는 실행**과 **지정한 도구를 고정된 단계에서 한 번 호출하는 실행**을 모두 제공한다. 공공기관 업무에서는 자료 추출·계산·검증·승인 같은 고정 단계와 자연어 해석을 분리할 수 있다는 점이 유용하다.

## 1. 제품·기능의 경계

| 영역 | 공개 설명에서 확인 | 판정 | WORKON 해석 |
|---|---|---|---|
| Works | 기업 검색·준비된 앱·앱 빌더·문서 기반 작업 | P, S01 | 직원이 찾아 실행하는 업무 카탈로그와 작업 화면 |
| Works의 기존 빌더 | 답변형·대화형·에이전트형 앱, 프로젝트별 설정 | D, S02~S10 | 기존 비서를 확장하는 설정형 앱 정의 |
| Coworker | 자연어로 앱·에이전트·사내 도구 구성, 웹 또는 협업 채널에서 사용 | P, S11 | 장기적으로 쉬운 제작 경험 참고. 일반 자연어 앱 생성 전체를 첫 구현 범위로 확정하지 않음 |
| Desktop | 로컬 파일 접근·스킬·예약 실행과 웹 자산 공유 | P, S12 | 후순위. 웹 SaaS에 로컬 실행 능력이 이미 있다고 계산하지 않음 |

## 2. 앱 유형별 구성

### 2-1. 답변형 앱 — 입력을 받아 한 번 생성

공식 본문에서 확인한 요소(S02, D): 앱 이름·설명, 입력 항목, 실행 모델, 시스템/사용자 프롬프트, Markdown 출력 설정, 긴 입력 처리 방식, 시험 후 공개. 결과는 복사·문서 다운로드로 활용한다.

확인한 입력 유형은 문서, 문단 텍스트, 단일 선택이다. 문서 입력은 직접 업로드 또는 지식 베이스의 허용된 문서 선택을 받는다. 텍스트에는 안내 예시를 둘 수 있고 입력은 이름 있는 변수로 전달한다. 문서가 6종의 입력 유형을 언급하나 나머지 세 유형은 본문에서 확정하지 않았다.

긴 입력은 한 번에 처리, 조각별 처리 후 연결(Map), 조각별 처리 후 합성(Map-Reduce)을 선택한다. 이는 **입력 처리 선택이 공개돼 있다는 사실**이며, 모든 형식에서 누락 없이 처리됨을 검증한 결과는 아니다.

WORKON 제안: 요약·번역·공문 초안·문서 비교 같은 단발 작업은 가벼운 입력 화면에서 시작한다. 첫 결과를 얻기 전에 복잡한 작업실을 모두 거칠 필요는 없다. 결과가 파일이면 기존 작업·판·파일 보관에 연결한다.

### 2-2. 에이전트형 앱 — 역할과 도구를 저장

공식 본문에서 확인한 요소(S03, D): 이름·아이콘·설명, 모델·지시문, 사용자 입력/시스템 변수, 허용 도구, 시작·오류·입력 요청 메시지, 미리보기·공개. 변수는 지시문에 대입할 수 있다.

MCP 서버에서 필요한 도구를 선택하며 서버에 따라 API Key 또는 OAuth로 인증한다. 도구 인자는 에이전트가 문맥에서 채우거나 설정값으로 고정할 수 있다. 도구의 실제 사용 순서는 요청에 따라 에이전트가 결정한다.

에이전트를 사용자용 앱으로 공개할 수도 있고 **에이전트만 공개해 다른 대화형 앱의 LLM 단계에서 재사용**할 수도 있다. 따라서 앱과 재사용 가능한 실행 능력은 완전히 같은 객체로만 보기는 어렵다.

WORKON 제안: 현재 `agents`의 역할·자료·능력·승인 체계를 우선 확장하고, 같은 기능을 가진 별도 비서 테이블을 중복 생성하지 않는다. 입력 스키마·출력 계약·도구 허용 목록과 실행 방식이 추가 설계 대상이다.

## 3. 자료 처리·RAG와 즉시 첨부의 구분

S09(D)는 지식 저장소의 문서를 파이프라인으로 정리해 RAG에 사용하는 방식과, 대화 중 첨부를 모델에 직접 전달하는 방식을 구분한다. 후자는 다른 대화에서 재사용되지 않으며 같은 RAG 경로라고 설명하지 않는다. 파일 생성 형식은 해당 가이드 기준 PDF·XLSX·DOCX·PPTX이고, HWPX 입력과 HWPX 출력은 구분해야 한다.

WORKON 제안: `knowledge`(비서·기관의 장기 참고 자료), `source`(실행 건 원자료), `template`(결과 양식), `artifact`(결과물)를 명확히 구분한다. 현재 ReadLayer 읽기/검색과 기존 첨부 읽기 경로도 이 구분에 맞게 설명한다. 공개 가이드의 파일 수·용량 상한을 WORKON 상한으로 그대로 복사하지 않는다.

## 4. 재사용·버전·공개·승인

| 확인 항목 | 행동 | 판정·출처 |
|---|---|---|
| 앱 버전 | 공개된 판을 유지하면서 새 판 작성·미리보기, 과거 판 재공개 | D, S03 |
| 초안 상태 | 사용자용 앱 노출과 다른 앱에서 사용할 에이전트 노출을 구분 | D, S03 |
| 의존 관계 | 다른 앱에서 쓰는 에이전트는 단순히 초안으로 돌릴 수 없음 | D, S03 |
| 공개 권한 | 특정 구성원·그룹에 노출, Viewer/Editor 역할 | D, S15 |
| 공개 승인 | 승인자 지정·요청 사유·알림·승인함·승인/반려. 승인 완료와 실제 공개는 별도 단계 | D, S16 |
| 승인 판 고정 | 승인 요청 대상은 수정 제한. 에이전트는 다른 버전을 편집할 수 있음 | D, S16 |
| 프롬프트 재사용 | 앱 전용/프로젝트 공용 프롬프트, 복사와 동적 입력, 여러 프롬프트 묶음 | D, S17 |
| 운영·배포 | 스테이징·롤백·역할 통제 소개 | P, S11 |

S16은 공개 승인 기능을 제한 제공·담당자 문의 대상으로 설명한다. 모든 고객의 기본 기능이라 단정하지 않는다. S04의 옛 안내는 에이전트 자체 제작이 별도 제공되지 않는다고 하지만 S03에는 제작·공개가 설명돼 있어, 더 구체적인 S03을 우선하고 문서 세대 차이를 남긴다.

WORKON 제안: 기존 비서 승인·버전과 연결해 `definitionVersion`과 `publishedVersion`을 분리하고 실행 당시 판을 고정한다. 작업 판(document version)과 앱 정의 판(app version)은 다른 개념이다. 다른 앱이 참조하는 도구·비서의 변경 영향도 기록해야 한다.

## 5. 시작 조건·연동·API

### 문서 확인된 범위

- 사용자 버튼·메시지·폼으로 실행하는 흐름: S03~S06.
- 외부 서비스에서 앱 목록 조회·앱 실행 API: S18. 과거 명세는 도중 사용자 입력이 필요한 대화형 실행에 제한을 명시한다. 모든 앱을 같은 API로 끝까지 실행할 수 있다고 가정하면 안 된다.
- MCP: 에이전트의 선택형 도구 사용과 고정 MCP 노드가 병존(S03·S08).
- 프로젝트 프롬프트와 변수를 여러 앱에서 사용(S17).
- SharePoint 구조·문서/폴더 권한·메타데이터 연동, Box 문서 연동, Slack·Confluence·Box 검색 API RAG는 공식 업데이트에 설명돼 있다(S19). 이 중 문의가 필요한 기능이 있다.
- HTTP POST로 Slack 알림을 보내는 구성은 과거 공식 문서에 있다(S13). 현재 제공 인증/노드 UI를 그대로 보장하지 않는다.

### 제품 소개 수준

S01에는 RFP 메일 도착을 감지해 요구 추출→과거 답변 매칭→초안을 만드는 예시, REST API·MCP Bridge·Webhooks, SharePoint·Drive·Confluence·DB 연결과 웹·Slack·Teams 배포가 제시된다. **예시를 읽은 것과 실제 트리거 설정·권한 전파·실패 복구를 관찰한 것은 다르다.** Desktop 예약 기능(S12)을 Works 웹 전체 스케줄러의 세부 명세로 대체하지 않는다.

### 미확인

- 웹 SaaS의 정확한 트리거 종류, 타임존·예약 누락 처리, 이메일 이벤트의 커넥터별 지원.
- 임의 워크플로우 루프·병렬 단계·서브플로·중첩 한도.
- 작업 큐·재시도·백오프·체크포인트·멱등성의 서버 내부 구현.
- 조직 외부 전송 승인과 취소/되돌리기의 실제 처리.
- 커넥터별 OAuth 스코프·개인/기관 자격증명 분리·비밀값 저장 방식.
- API 플랜·호출 상한·최신 버전과 SDK 기능 동등성.

WORKON은 이 항목을 독자 요구사항으로 정해야 한다. 기존 업무 작업자의 lease·체크포인트·재시도는 별도의 장점이며 경쟁 제품이 같은 방식을 쓴다고 주장하지 않는다.

## 6. 시험·피드백·비용·이력

확인한 운영 패턴:

- 버전별 미리보기, 앱 실행 전 시험(S03).
- Deep Research의 조사 범위·질문 확인·진행 상태(S10). 해당 문서는 마지막 노드 제약을 명시하므로 일반 후속 파이프라인으로 단정하지 않는다.
- 멀티모달은 Works와 SDK 미리보기 지원 범위가 달라 제한 공개 후 시험하는 절차를 안내(S09).
- 실행 통계는 사용자 요청 수·실제 모델 호출 수·크레딧·활성 사용자·앱별 순위와 미리보기 실행을 구분하고 엑셀로 내보낸다(S20).
- 프로젝트 월 한도와 알림, 문서 업로드·색인도 비용 적용 대상으로 다루는 안내가 있다(S21).

WORKON 제안: 미리보기→시험 사례→승인→공개를 분리한다. 성공률·채택·재작업·전체 시간과 요청/모델 호출/문서 처리 비용을 별도로 측정한다. 모델 호출 1회와 사용자 업무 1건을 같은 지표로 세지 않는다. 평가는 실제 기관 자료와 기대 결과를 보유한 사례로 구성한다. 공개 문서만으로 경쟁 제품의 평가 자동화 품질을 입증할 수는 없다.

## 7. WORKON 앱 정의 설계로 옮길 수 있는 계약(제안)

아래 필드는 이번 관찰을 바탕으로 독자적으로 제안한 개념 모델이다. 공급자 스키마를 추출한 것이 아니다.

| 계약 | 최소 내용 |
|---|---|
| 정체성 | 안정적인 키, 기관, 이름·소개·카테고리·예시 요청 |
| 실행 방식 | `conversation`, `form`, `workflow`; 필요하면 같은 앱에 여러 입구 |
| 입력 | 타입·필수 여부·기본값·검증·실행 중 보완 가능 여부 |
| 자료 | 기관/비서 참고 범위, 업로드 원자료, 양식 판, 출처 정책 |
| 모델 | 어댑터·모델·예산·출력 형식·도구 사용 조건 |
| 도구 | 허용 목록, 읽기/쓰기, 입력·출력 계약, 인증 참조, 외부 전송 승인 |
| 흐름 | 단계·연결·조건·변수 매핑·오류 처리·사람에게 물을 지점 |
| 결과 | 텍스트·표·파일 종류, 필수 산출물, 검증 규칙 |
| 공개 | 소유자·편집자·실행자, 초안/승인/공개, 정의 판 고정 |
| 실행 건 | 요청자·정의 판·자료 판·단계 이력·결과 파일·사용량·실패 코드 |
| 시험 | 예시 입력·기대 결과·권한/근거/수치 회귀 사례·채택 기록 |

처음부터 자유로운 그래프 빌더를 만드는 대신, 기존 엔진을 사용하는 **설정형 앱 제작→검증된 단계 조합→시각적 흐름 편집** 순서가 가능하다. 공문·취합·대사의 기존 코드는 도구 구현으로 보존한다. 이 순서는 제안이며 본 문서는 구현 완료를 의미하지 않는다.
