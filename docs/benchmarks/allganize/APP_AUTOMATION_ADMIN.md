# 앱 예약·연동 관리자 통제 (2026-11-03)

[앱 예약](APP_SCHEDULES.md)과 [앱 연동(Webhook)](APP_WEBHOOKS.md)은 직원 본인만 보고 끌 수 있었다. 연동 토큰은 외부 시스템이 직원 권한으로 앱을 돌리게 하는 자격이라, 퇴사·토큰 유출·용도 종료 때 **기관 관리자가 누가 무엇을 갖고 있는지 보고 끊을 수 있어야** 보안성 검토를 통과한다. 이번에 관리자 화면과 탈퇴 처리 연결을 넣었다(마이그레이션 0050).

## 관리자가 보는 것

- **기관 관리자 메뉴 '앱 예약·연동'**(`/admin/app-automations`). 관리 범위(자기 부서 + 하위 부서, 최상위 부서 관리자는 기관 전체) 직원의 것만.
- 연동: 연동 이름·앱·직원·부서·토큰 앞부분(`wo_wh_…` 12자)·상태(쓰는 중·만료·회수함)·회수 사유·만료일·실행 횟수·마지막 실행과 실패 여부.
- 예약: 앱·직원·부서·일정(예: 매주 월요일 09:30)·상태(예약 중·멈춤·관리자가 멈춤·실패 N회)·멈춘 사유·다음 실행·실행 횟수·마지막 실행.
- (2026-11-04) 예약 실행기 상태: 문제가 있으면 위에 붉은 안내(실행기가 30분 넘게 안 불림·1시간 넘게 지난 예약·멈춘 차지, 마지막 호출 시각), 없으면 '예약 실행기 정상 · 마지막 호출'. 예약 줄은 예정 시각이 1시간 넘게 지나면 칩 '실행 지연'(`schedule-health.ts`, [앱 예약](APP_SCHEDULES.md)).
- 기본은 '쓰는 연동·켜진 예약만'(관리자가 멈춘 예약 포함)이고 체크를 풀면 전부.
- **보지 않는 것**: 예약에 저장한 입력값, 실행 결과·대화, 실패 원문(`last_error`), 토큰 해시. 개인 앱은 이름도 `개인 앱(이름 비공개)`로 가린다 — [앱 실행 현황](APP_RUN_OVERVIEW.md)과 같은 원칙(직원 작업은 관리자도 열람하지 않는다).

## 관리자가 할 수 있는 것

| 조치 | 결과 | 되돌리기 |
| --- | --- | --- |
| 연동 **회수** | 토큰이 곧바로 401. 직원 화면에 `관리자가 회수했습니다 — {사유}` | 없음(직원이 새로 만들어야 함) |
| 예약 **멈추기** | 다음 차례부터 돌지 않음(실행 중인 차례는 끝까지). 직원은 **다시 켜지 못하고** 멈춤 사유를 덮지도 못함(403 `관리자가 멈춘 예약입니다…`). 지우기는 됨(직원의 자료) | 관리자 '잠금 풀기' |
| 예약 **잠금 풀기** | 예약은 멈춘 채로 두고 잠금만 푼다 — 다시 켜는 것은 직원(관리자가 남의 예약을 대신 켜지 않는다) | — |

- 모든 조치는 **사유 5~200자**를 받는다(제어·서식 글자 지움). 사유는 직원 화면에 보인다.
- **보안 로그**(`security_logs`, severity medium)에 `app_webhook_revoked`·`app_schedule_paused`·`app_schedule_unlocked`로 남는다 — 대상 id·직원 id·앱 id·사유·대리 접근 여부. 감사 화면(`/admin/audit`, 보안 이벤트)에 한국어 이름으로 보인다.
- 바꾸기는 **조건부**다: 회수는 활성 연동만, 멈춤은 잠금이 없는 예약만, 풀기는 잠긴 예약만. 이미 처리된 것을 또 누르면 바꾸지 않고(기록도 안 남김) 현재 상태를 돌려준다.
- 범위 판정은 기관(`organization_id`)과 관리 부서(`department_id IN …`)를 **함께** 건다. 범위 밖 id는 404.

## 기관 전체 외부 연동 스위치 (2026-11-08, 0068)

보안 점검·사고 대응·기관 정책으로 **기관의 외부 호출을 한 번에 막아야** 할 때 토큰을 하나씩 회수하지 않고 끈다(`src/lib/apps/webhook-switch.ts`).

- **누가**: 기관 전체를 관리하는 관리자(최상위 부서 소속 관리자)만 — 화면 '앱 예약·연동'의 연동 표 위 '기관 전체 끄기'/'다시 켜기'. 그 밖의 관리자에게는 상태만 보이고 단추가 없다(서버도 403). 라우트 `PUT /api/admin/app-automations/webhook-switch` `{ enabled, reason }`.
- **사유 5~200자**(회수와 같은 `parseAdminReason`). 끌 때의 사유는 `organizations.app_webhooks_disabled_reason`에 저장해 관리자 화면에 보이고, 켤 때의 사유는 보안 로그에만. 보안 로그(`security_logs`, **high**) `app_webhooks_org_disabled`·`app_webhooks_org_enabled` — 기관 id·사유·대리 접근 여부, 감사 화면에 '기관 외부 연동 끄기(관리자)'·'켜기'. 바꾸기는 조건부라 이미 그 상태면 바꾸지 않고 기록도 없다.
- **끄면**: 외부 호출(`POST /api/apps/webhook`)은 **차지 전에** 403 `기관 관리자가 외부 연동(Webhook)을 꺼 두었습니다…` — 간격·하루 상한·사용 횟수·`Idempotency-Key` 기록을 쓰지 않아 다시 켜면 같은 키로 곧바로 돈다. 검사는 쓸 수 있는(활성·안 만료) 토큰만 기관을 보고, 무효 토큰은 지금처럼 같은 401(기관 상태를 알리지 않음). 새 연동 만들기 403. 직원의 '외부 연동' 목록에는 쓰는 중인 연동마다 같은 안내가 붙는다.
- **토큰은 회수하지 않는다** — 다시 켜면 그대로 쓴다. 영구히 막으려면 하나씩 회수.
- **닫힘**: 기관 칸을 읽지 못하면(0068 전 등) 외부 호출 500, 연동 만들기 503. 직원 목록의 안내만 열어 둔다(안내일 뿐이라). 관리자 목록은 스위치를 못 읽어도 연동·예약은 보인다(스위치 칸만 빠짐).
- **예약에는 걸지 않는다** — 예약은 기관 안에서 직원 권한으로 도는 일이라 외부 데이터 흐름이 아니다(멈추려면 0050의 예약 멈춤).
- **DB(0068)**: `organizations.app_webhooks_disabled_at timestamptz`·`app_webhooks_disabled_reason text`, 짝 CHECK(둘 다 있거나 둘 다 없음)·사유 1~300자. 추가만, 여러 번 적용해도 안전. **코드 배포 전에 적용**.
- 검증: `tests/app-webhook-switch.test.ts`(9개 — 끄기·켜기 조건부와 보안 로그, 이미 그 상태면 기록 없음, 권한 403·쓰기 실패 503, 읽기·적용 전 던짐, 호출 앞 검사는 활성·안 만료 토큰만, 직원·관리자 보기, PUT 인증·꼴, 관리자 화면, 0068·감사 이름), `tests/app-webhooks.test.ts`(꺼졌으면 차지·실행 전에 403, 토큰·본문이 틀리면 기관을 안 봄, 읽지 못하면 던짐), `tests/app-webhooks-route.test.ts`(만들기 403·503, 목록 안내·못 읽어도 목록). 시험 DB에 0068을 두 번 적용·짝 CHECK·길이 CHECK 확인. 브라우저 확인 없음.

## 계정 탈퇴와 연결

슈퍼관리자 '계정 삭제'(탈퇴 처리, `src/lib/user-withdrawal.ts`)가 대화·첨부를 지운 다음, 도장 전에:

- **앱 예약을 지운다** — 저장한 입력값이 개인 내용이라(대화와 같은 취급).
- **쓰는 앱 연동을 회수한다** — `계정 탈퇴로 회수했습니다.` 행은 남긴다(외부 호출 기록의 귀속).
- 둘 중 하나라도 실패하면 500으로 멈추고 도장을 찍지 않는다(다시 시도할 수 있게). 전에는 실행 때 계정 검사가 403으로 막을 뿐 토큰이 '쓰는 중'으로 남았다.
- 관리자가 계정을 **비활성**(되돌릴 수 있음)으로만 바꾸면 손대지 않는다 — 실행 때 계정 검사가 막고, 다시 활성화하면 이어 쓴다.

## DB (0050)

- `app_webhooks.revoked_reason text` — CHECK: 회수된 연동에만, 1~300자.
- `app_schedules.admin_paused_at timestamptz` — CHECK: 멈춘 예약에만. 그래서 코드가 잊어도 **DB가 잠긴 예약을 켜지 못하게** 막는다. 실행기 차지 조건(`status = 'active'`)에도 걸리지 않는다.
- 관리 목록용 색인 `(organization_id, department_id)` 둘. 추가만, 여러 번 적용해도 안전. **코드 배포 전에 적용** — 새 코드가 두 칸을 읽으므로 없으면 직원·관리자 예약·연동 화면이 503.

- **하지 않은 것**: 브라우저로 관리자 화면을 열어 보지 않았다— Docker를 켜니 다른 프로젝트 컨테이너도 함께 떠 이 PC 메모리가 모자라 `next dev`가 두 번 메모리 부족으로 죽었다(위 실측은 화면 없이 라우트만). 운영 DB 0050 적용·배포는 2026-11-03(`dpl_4cmoK59Heat6g1FTzD1t7r2CppVW`, `PRODUCTION_DEPLOYMENT.md`) — 로그인 화면 확인은 아직이다.

## 알려진 한계

- 관리자가 직원 대신 연동을 만들거나 예약을 켜지는 못한다(일부러).
- 회수·멈춤 때 직원에게 메일을 보내지 않는다 — 직원 화면의 사유로만 안다.
- 기관 전체 '연동 끄기' 스위치는 2026-11-08에 넣었다(위 절, 0068). 예약 전체를 한 번에 멈추는 스위치는 없다.
