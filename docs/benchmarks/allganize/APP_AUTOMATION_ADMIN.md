# 앱 예약·연동 관리자 통제 (2026-11-03)

[앱 예약](APP_SCHEDULES.md)과 [앱 연동(Webhook)](APP_WEBHOOKS.md)은 직원 본인만 보고 끌 수 있었다. 연동 토큰은 외부 시스템이 직원 권한으로 앱을 돌리게 하는 자격이라, 퇴사·토큰 유출·용도 종료 때 **기관 관리자가 누가 무엇을 갖고 있는지 보고 끊을 수 있어야** 보안성 검토를 통과한다. 이번에 관리자 화면과 탈퇴 처리 연결을 넣었다(마이그레이션 0050).

## 관리자가 보는 것

- **기관 관리자 메뉴 '앱 예약·연동'**(`/admin/app-automations`). 관리 범위(자기 부서 + 하위 부서, 최상위 부서 관리자는 기관 전체) 직원의 것만.
- 연동: 연동 이름·앱·직원·부서·토큰 앞부분(`wo_wh_…` 12자)·상태(쓰는 중·만료·회수함)·회수 사유·만료일·실행 횟수·마지막 실행과 실패 여부.
- 예약: 앱·직원·부서·일정(예: 매주 월요일 09:30)·상태(예약 중·멈춤·관리자가 멈춤·실패 N회)·멈춘 사유·다음 실행·실행 횟수·마지막 실행.
- (2026-11-04) 예약 실행기 상태: 문제가 있으면 위에 붉은 안내(실행기가 30분 넘게 안 불림·1시간 넘게 지난 예약·멈춘 차지, 마지막 호출 시각), 없으면 '예약 실행기 정상 · 마지막 호출'. 예약 줄은 예정 시각이 1시간 넘게 지나면 칩 '실행 지연'(`schedule-health.ts`, [앱 예약](APP_SCHEDULES.md)).
- 기본은 '쓰는 연동·켜진 예약만'(관리자가 멈춘 예약 포함)이고 체크를 풀면 전부.
- **보지 않는 것**: 예약에 저장한 입력값, 실행 결과·대화, 실패 원문(`last_error`), 토큰 해시. 개인 앱은 이름도 `개인 앱(이름 비공개)`로 가린다 — [앱 실행 현황](APP_RUN_OVERVIEW.md)과 같은 원칙(직원 작업은 관리자도 열람하지 않는다).

## 관리자가 할 수 있는 것

| 조치 | 결과 | 되돌리기 |
| --- | --- | --- |
| 연동 **회수** | 토큰이 곧바로 401. 직원 화면에 `관리자가 회수했습니다 — {사유}` | 없음(직원이 새로 만들어야 함) |
| 예약 **멈추기** | 다음 차례부터 돌지 않음(실행 중인 차례는 끝까지). 직원은 **다시 켜지 못하고** 멈춤 사유를 덮지도 못함(403 `관리자가 멈춘 예약입니다…`). 지우기는 됨(직원의 자료) | 관리자 '잠금 풀기' |
| 예약 **잠금 풀기** | 예약은 멈춘 채로 두고 잠금만 푼다 — 다시 켜는 것은 직원(관리자가 남의 예약을 대신 켜지 않는다) | — |

- 모든 조치는 **사유 5~200자**를 받는다(제어·서식 글자 지움). 사유는 직원 화면에 보인다.
- **보안 로그**(`security_logs`, severity medium)에 `app_webhook_revoked`·`app_schedule_paused`·`app_schedule_unlocked`로 남는다 — 대상 id·직원 id·앱 id·사유·대리 접근 여부. 감사 화면(`/admin/audit`, 보안 이벤트)에 한국어 이름으로 보인다.
- 바꾸기는 **조건부**다: 회수는 활성 연동만, 멈춤은 잠금이 없는 예약만, 풀기는 잠긴 예약만. 이미 처리된 것을 또 누르면 바꾸지 않고(기록도 안 남김) 현재 상태를 돌려준다.
- 범위 판정은 기관(`organization_id`)과 관리 부서(`department_id IN …`)를 **함께** 건다. 범위 밖 id는 404.

## 앱 일괄 실행 (2026-11-10, 마이그레이션 없음)

- 같은 화면 아래 **'앱 일괄 실행'** 표가 관리 범위(기관 + 관리 부서) 직원의 **최근 50개** 묶음(0077)을 보인다 — 이름·앱(개인 앱은 이름 가림)·직원·부서·상태(실행 중·마침·직원이 그만둠·멈춤과 사유)·줄 수(완료/전체·실패·건너뜀)·만든 때. **줄의 입력·결과·파일 이름은 싣지 않는다**(`adminBatchView`). 줄 상태는 1,000행 상한을 넘을 수 있어 쪽마다 끝까지 센다(`pagedRows`).
- **기관 상한**(0084): 표 위 '기관 상한: 한 번에 N줄' — 기관 전체 관리자만 '바꾸기'(1~100, 비우면 기본 100, 사유·보안 로그 high). 만들 때만 보고 이미 만든 것은 그대로([일괄 실행](APP_BATCHES.md)).
- **실행 중인 묶음 멈추기**(`PATCH /api/admin/app-automations/batches/[id] { action: 'stop', reason }`, `stopBatchByAdmin`): 사유 5~200자. `running`일 때만 조건부로 `stopped`·사유 `관리자가 멈췄습니다 — …`로 바꾸고, 기다리던 줄은 건너뜀(실행 중인 줄은 끝까지 간다), 파일마다 한 건의 사본을 지우고(`removeBatchFiles`), 보안 로그(`app_batch_stopped`, medium — 묶음·직원·앱·사유), 직원에게 메일('기관 관리자가 앱 일괄 실행을 멈췄습니다' — 사유·실행 화면 열기). 이미 끝났거나 그 사이 끝난 묶음은 그대로 돌려주고 기록·메일을 남기지 않는다. **되돌릴 수 없다**(직원이 새로 만든다). 마친 줄의 결과 엑셀은 직원이 그대로 받는다.

## 기관 전체 외부 연동 스위치 (2026-11-08, 0068)

보안 점검·사고 대응·기관 정책으로 **기관의 외부 호출을 한 번에 막아야** 할 때 토큰을 하나씩 회수하지 않고 끈다(`src/lib/apps/webhook-switch.ts`).

- **누가**: 기관 전체를 관리하는 관리자(최상위 부서 소속 관리자)만 — 화면 '앱 예약·연동'의 연동 표 위 '기관 전체 끄기'/'다시 켜기'. 그 밖의 관리자에게는 상태만 보이고 단추가 없다(서버도 403). 라우트 `PUT /api/admin/app-automations/webhook-switch` `{ enabled, reason }`.
- **사유 5~200자**(회수와 같은 `parseAdminReason`). 끌 때의 사유는 `organizations.app_webhooks_disabled_reason`에 저장해 관리자 화면에 보이고, 켤 때의 사유는 보안 로그에만. 보안 로그(`security_logs`, **high**) `app_webhooks_org_disabled`·`app_webhooks_org_enabled` — 기관 id·사유·대리 접근 여부, 감사 화면에 '기관 외부 연동 끄기(관리자)'·'켜기'. 바꾸기는 조건부라 이미 그 상태면 바꾸지 않고 기록도 없다.
- **끄면**: 외부 호출(`POST /api/apps/webhook`)은 **차지 전에** 403 `기관 관리자가 외부 연동(Webhook)을 꺼 두었습니다…` — 간격·하루 상한·사용 횟수·`Idempotency-Key` 기록을 쓰지 않아 다시 켜면 같은 키로 곧바로 돈다. 검사는 쓸 수 있는(활성·안 만료) 토큰만 기관을 보고, 무효 토큰은 지금처럼 같은 401(기관 상태를 알리지 않음). 새 연동 만들기 403. 직원의 '외부 연동' 목록에는 쓰는 중인 연동마다 같은 안내가 붙는다.
- **토큰은 회수하지 않는다** — 다시 켜면 그대로 쓴다. 영구히 막으려면 하나씩 회수.
- **닫힘**: 기관 칸을 읽지 못하면(0068 전 등) 외부 호출 500, 연동 만들기 503. 직원 목록의 안내만 열어 둔다(안내일 뿐이라). 관리자 목록은 스위치를 못 읽어도 연동·예약은 보인다(스위치 칸만 빠짐).
- **예약에는 걸지 않는다** — 예약은 기관 안에서 직원 권한으로 도는 일이라 외부 데이터 흐름이 아니다(멈추려면 0050의 예약 멈춤).
- **DB(0068)**: `organizations.app_webhooks_disabled_at timestamptz`·`app_webhooks_disabled_reason text`, 짝 CHECK(둘 다 있거나 둘 다 없음)·사유 1~300자. 추가만, 여러 번 적용해도 안전. **코드 배포 전에 적용** — 운영 DB 적용 2026-11-08(칸 둘·CHECK 확인), 코드 배포 `dpl_CJiXcrNHWRm9LReriozmHQCVgk5L`.
- 검증: `tests/app-webhook-switch.test.ts`(9개 — 끄기·켜기 조건부와 보안 로그, 이미 그 상태면 기록 없음, 권한 403·쓰기 실패 503, 읽기·적용 전 던짐, 호출 앞 검사는 활성·안 만료 토큰만, 직원·관리자 보기, PUT 인증·꼴, 관리자 화면, 0068·감사 이름), `tests/app-webhooks.test.ts`(꺼졌으면 차지·실행 전에 403, 토큰·본문이 틀리면 기관을 안 봄, 읽지 못하면 던짐), `tests/app-webhooks-route.test.ts`(만들기 403·503, 목록 안내·못 읽어도 목록). 시험 DB에 0068을 두 번 적용·짝 CHECK·길이 CHECK 확인. 브라우저 확인 없음.

## 기관 전체 앱 예약 스위치 (2026-11-08, 0070)

0068(연동)과 같은 꼴로, 기관 전체 관리자가 기관의 **입력형 앱 예약 실행**을 사유와 함께 한 번에 끄고 켠다 — 비용 점검·모델 장애·사고 대응 때.

- 관리자 '앱 예약·연동'의 앱 예약 표 위 스위치(`OrgAutomationSwitch kind="schedules"`), `PUT /api/admin/app-automations/schedule-switch`. 바꾸기 규칙(기관 전체 관리자만·사유 5~200자·조건부·바뀐 때만 보안 로그 high `app_schedules_org_disabled`/`app_schedules_org_enabled`, 감사 화면 '기관 앱 예약 끄기/켜기(관리자)')은 연동 스위치와 같은 함수(`webhook-switch.ts` `setOrgSwitch('schedules', …)`)다.
- **끄면 실행기**(`runDueSchedules`)가 그 기관의 차례를 **실행하지 않고** 차지한 뒤 다음 시각으로만 넘긴다(`heldPatch` — 실행 횟수·마지막 결과·실패 수는 그대로, 모델 호출·메일 없음, 결과의 `held`로 셈). 기관 스위치는 한 번 불릴 때 기관마다 한 번만 읽는다. **읽지 못하면** 실행도 넘기기도 하지 않고 차지하지 않아 다음 호출(5분 뒤)에 다시 본다(warning `기관 예약 스위치를 읽지 못함`).
- 새 예약은 403 `기관 관리자가 앱 예약 실행을 꺼 두어 새 예약을 만들 수 없습니다.`(읽지 못하면 503). 고치기·멈추기·다시 켜기·지우기는 그대로 된다(켜도 기관이 켤 때까지 돌지 않는다).
- 직원 예약 목록: 켜진 예약에 '기관이 멈춤' 칩과 안내(`SCHEDULE_ORG_DISABLED`), 그동안 '실행 지연'으로 보이지 않는다. 안내는 읽지 못하면 켜진 것으로 보인다(안내일 뿐이라).
- **예약은 지우지 않는다** — 다시 켜면 다음 차례부터 돈다(꺼 둔 동안의 차례를 몰아서 돌리지 않는다).
- DB(0070): `organizations.app_schedules_disabled_at`·`app_schedules_disabled_reason` + 짝 CHECK·사유 1~300자. 추가만, 여러 번 적용해도 안전. **코드 배포 전에 적용**.
- 검증: `tests/app-schedules.test.ts`(2개 — 꺼 둔 기관은 넘기기만·기관마다 한 번 읽기, 읽지 못하면 아무것도 안 함), `tests/app-webhook-switch.test.ts`(3개 — 예약 칸만 바꿈·예약 사건, 라우트, 화면·마이그레이션·감사 이름), `tests/app-schedules-route.test.ts`(1개 — 새 예약 403·503, 목록 표시·지연 숨김). 시험 DB에 두 번 적용·CHECK 두 가지 위반 확인.

## 직원에게 알림 메일 (2026-11-08)

관리자가 연동을 회수하거나 예약을 멈추·잠금을 풀면 그 연동·예약의 **주인 직원에게 메일**을 보낸다(전에는 직원이 자기 화면의 사유를 봐야 알았다). 마이그레이션 없음.

- 보낼 때: 조건부 바꾸기가 **실제로 행을 바꿨을 때만**(보안 로그와 같은 때 — 이미 처리된 것을 또 눌러도 메일은 다시 안 간다).
- 싣는 것: 앱 이름·대상(`연동 '이름'` 또는 `매주 월요일 09:30 예약`)·시각(한국)·**관리자가 적은 사유**·할 일(회수는 되돌릴 수 없음·새 연동이나 문의, 멈춤은 다시 켤 수 없음·지우기는 됨, 잠금 풀기는 다시 켜거나 고칠 수 있음)·앱 연동/앱 예약 화면 링크. **관리자 이름·입력값·결과·토큰은 싣지 않는다.**
- 받는 사람: 주인 직원 한 사람. 탈퇴(`deleted_at`)·비활성·주소 없음·메일 미설정이면 조용히 건너뛴다.
- **던지지 않는다**(`src/lib/apps/automation-notice.ts` `notifyAutomationOwner`) — 메일이 안 가도 관리자의 조치는 이미 끝났다. 실패는 운영 기록 warning `관리자 조치 알림 메일을 보내지 못함`(종류·대상 id만, 사유 글 없이). 메일 글은 `mailer.ts` `automationAdminNoticeMail`.
- 기관 전체 연동·예약 스위치(0068·0070)는 직원 한 사람의 일이 아니라 메일을 보내지 않는다(직원 연동 목록의 안내로 안다). 탈퇴 처리의 자동 회수도 보내지 않는다.
- 검증: `tests/app-automation-notice.test.ts`(4개 — 연동 회수 메일 내용·이스케이프·한국 시각·링크, 예약 멈춤·잠금 풀기의 대상·안내, 보내지 않는 경우, 실패는 warning만·사유 글 없음), `tests/app-automation-admin.test.ts`(바뀐 때만 알림 — 세 조치·이미 처리된 것은 안 보냄). 실제 메일 발송은 보지 않았다.

## 계정 탈퇴와 연결

슈퍼관리자 '계정 삭제'(탈퇴 처리, `src/lib/user-withdrawal.ts`)가 대화·첨부를 지운 다음, 도장 전에:

- **앱 예약을 지운다** — 저장한 입력값이 개인 내용이라(대화와 같은 취급).
- **쓰는 앱 연동을 회수한다** — `계정 탈퇴로 회수했습니다.` 행은 남긴다(외부 호출 기록의 귀속).
- 둘 중 하나라도 실패하면 500으로 멈추고 도장을 찍지 않는다(다시 시도할 수 있게). 전에는 실행 때 계정 검사가 403으로 막을 뿐 토큰이 '쓰는 중'으로 남았다.
- 관리자가 계정을 **비활성**(되돌릴 수 있음)으로만 바꾸면 손대지 않는다 — 실행 때 계정 검사가 막고, 다시 활성화하면 이어 쓴다.
