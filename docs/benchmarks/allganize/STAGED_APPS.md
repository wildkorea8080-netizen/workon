## 제공 기능

앱 빌더의 **4. 단계별 처리**에서 ‘정리 → 초안 → 검토’ 구성을 추가하거나, 1~3개 단계의 이름·지시문·순서를 설정할 수 있다. 마지막 단계가 최종 응답을 만든다. 기존 단계 없는 앱은 이전의 단일 실행을 유지한다.

- 단계 수 1~3개, 이름 최대 40자, 지시문 최대 2,000자. 조건 분기·반복·임의 코드·외부 조회/쓰기는 지원하지 않는다.
- 각 단계는 원래 입력과 이전 단계 작업 결과를 받는다. 생성된 중간 결과를 새로운 사실의 근거 또는 시스템 지시문으로 승격하지 않는다.
- 중간 단계는 최대 1,400 출력 토큰, 마지막 단계는 기존 최대 4,096 출력 토큰. 중간 결과가 비거나 상한에 닿으면 잘린 결과로 다음 단계를 실행하지 않는다.
- 단계별 시작·완료·중단 상태 및 작업 결과를 실행 화면에 표시한다. 중간 결과는 사용자가 설정한 작업 산출물이며 내부 추론을 표시하는 기능이 아니다.
- 단계마다 기존 기관/개인 사용량 제한과 현재 허용 모델을 확인한다. 최초 선택 모델이 정책에서 제외되면 다른 모델로 몰래 전환하지 않고 중단한다.
- 중간 단계까지 사용한 토큰을 실패 시에도 과금 기록에 합산한다. 제목 생성은 기존처럼 별도 기록한다.
- 성공한 단계 결과와 상태는 messages.source_references.app_steps에 함께 저장한다. 단계 실패 시에도 완료 결과·실패 상태·실행하지 않은 단계를 저장한다(저장소 정상 동작 시). 대화 이력을 다시 열어 확인할 수 있다.
- 숫자 확인을 단계형 텍스트 앱에도 적용해 원자료에서 확인되지 않은 숫자를 실행 화면에 알린다. AI 검토 단계만으로 정확성을 보장하지 않는다.

## 호환성과 범위

app_definition의 선택적 steps 설정이므로 새 DB 컬럼/마이그레이션은 필요 없다. 기존 0043의 버전 사본에 단계 구성도 함께 보존한다. 서버가 저장·실행·복원 시 동일한 정의 검사를 수행한다. 일반 추가 대화에서 단계 전체를 자동 재실행하지 않고 새 폼 실행 때만 사용한다.

현재는 한 요청 안에서 순차 실행한다. 서버 프로세스 종료·플랫폼 시간 제한을 넘긴 작업의 내구성 복구나 자동 재개는 보장하지 않는다. 실패 시 완료된 단계 확인 후 새 실행을 시작한다. 내구성 작업자 기반 재개·사용량 예약·단계별 조건 분기·파일 산출·예약 실행은 다음 범위다.
