# 입력형 앱 예약 실행 (2026-11-03)

알리웍스 Agent Builder는 에이전트에 **스케줄(시작 시각·빈도)** 과 Webhook 트리거를 건다([REA 재분석](REA_PUBLIC_WEB_ANALYSIS_2026-10-31.md), 한국어 가이드 '워크플로우 구축하기'). WORKON에는 내부 작업자·보정 cron만 있었고 직원이 스스로 자동 실행을 걸 길이 없었다. 이번에 **스케줄 트리거**를 넣었다. Webhook 트리거(멤버 토큰·수명·회수)는 아직 없다.

## 직원이 보는 것

- 입력형 앱 실행 화면(`/apps/run`)에서 입력을 채운 뒤 **'이 입력으로 예약 실행 걸기'** → 주기(매일·평일·매주 요일·매월 1~28일)와 시각(한국 시간, 00분·30분)을 고르면 저장된다. 지금 입력값이 그대로 저장돼 매번 같은 입력으로 돈다.
- **앱 예약**(`/apps/schedules`, 왼쪽 메뉴·앱 목록 머리): 내 예약마다 설명(`매주 월요일 09:00`), 다음 실행, 실행 횟수, 마지막 결과, 저장한 입력, 멈추기·다시 켜기·지우기. 마지막 결과는 대화로 열린다.
- 실행 결과는 **그 직원의 대화**로 저장되고 제목 앞에 `[예약] `이 붙어 앱 실행 기록(`/apps/history`)에 함께 보인다. 사용량은 그 직원의 기록으로 남는다.
- 한 사람당 예약 5개(`APP_MAX_SCHEDULES_PER_USER`, 멈춘 것 포함). 실행 화면에 붙인 **올린 파일은 예약에 사본으로 저장된다**(아래 '올린 파일', 0073 — 2026-11-08 전에는 쓸 수 없었다). 첨부가 선택인 앱은 파일 없이도 돈다. '문서함에서 고르기'를 허용한 앱은 고른 문서를 예약에 함께 저장한다(아래 '문서함 문서', 0062). 파일·문서는 합쳐 3개까지이고, 파일이 필수인 앱은 둘 중 하나가 있어야 예약할 수 있다.

## 문서함 문서 (2026-11-05, 0062)

- 실행 화면에서 문서함 문서를 고른 채 '이 입력으로 예약'을 누르면 문서 id가 `app_schedules.document_ids`(3개까지)에 저장된다. 만들 때 서버가 지금 고를 수 있는 문서(그 앱 비서의 읽힌 근거 판·볼 수 있는 것 — `selectableLibraryDocuments`)인지 다시 본다.
- **실행 때마다 지금 근거 판으로 읽는다**(`currentEditionIds`): 저장한 문서에서 판 사슬(`replaces_id`)을 앞으로 따라가 근거로 쓸 수 있는 마지막 판을 고른다. 새 판이 시행되면 새 판, 시행일 전이거나 읽는 중이면 옛 판 그대로. 새 판으로 따라갔으면 실행이 끝난 뒤 예약의 문서 id를 새 판으로 바꾼다. 어느 판을 썼는지는 결과 답의 `source_references.app_documents`에 남는다.
- **쓸 판이 없으면(지움·읽기 실패·지난 판만) 예약을 멈추고**(`PAUSED_DOCUMENTS_UNAVAILABLE`) 직원에게 알린다 — 문서 없이 조용히 돌지 않는다. 문서 행을 못 읽으면 '실패'(다음 차례에 다시).
- 볼 수 있는지·개수·앱 설정은 실행(`prepareTurn`의 `app_document_ids`)이 그 직원으로 다시 본다. 외부 연동(Webhook)은 아직 문서를 받지 않는다.
- 예약 목록에 '문서함 문서 N개'가 보인다.

## 예약 고치기 (2026-11-08)

예전에는 시각·입력을 바꾸려면 예약을 지우고 다시 만들어야 했고, 앱 설정이 바뀌거나(판 다름)·문서를 못 쓰거나·부서가 바뀌어 멈춘 예약도 지우고 새로 만들어야 했다. 마이그레이션 없음.

- 앱 예약 목록의 **'고치기'** → 실행 화면(`/apps/run?agent=…&schedule=…`)이 저장한 입력·고른 문서를 미리 채우고 예약 칸이 **'예약 고치기'**로 열린다(주기·요일·날·시각도 저장한 값). 화면 위 안내가 지금 앱 판이 예약 때와 다르면 알린다. '초안 만들기'는 그대로 지금 한 번 실행이다.
- `GET /api/apps/schedules/[id]`(내 예약 하나 — 입력·문서 id 포함)·`PUT /api/apps/schedules/[id]`(본문은 만들기와 같다). 검사는 만들기와 **같은 함수**(`src/lib/apps/schedule-request.ts` `checkScheduleRequest` — 지금 앱을 쓸 수 있는지·입력형 앱·화면이 본 판 = 지금 판·입력·문서함 문서·시각).
- 고치면: 입력·문서·시각·**앱 판을 지금 판으로**, 부서·기관을 **지금 소속으로** 다시 적고, 다음 실행 시각은 지금부터 다시 센다. 앱은 바꿀 수 없다(다른 앱은 새 예약 — 400).
- 상태(`editedStatus`): **직원이 멈춘 예약은 멈춘 채로** 고친다(다시 켜기는 목록에서). **실행기가 멈춘 예약**(앱 설정 바뀜·문서 못 씀·부서 바뀜·연속 실패)은 고친 것이 곧 해결이라 다시 켜고 실패 수를 지운다. 멈춤 안내 문구도 '고치기'를 가리키게 바꿨다.
- 막는 것: **관리자가 멈춘 예약**(0050)은 403(목록에 '고치기'도 없다 — 지우기만), **실행 중**(차지가 15분 안)은 409 `지금 실행 중인 예약입니다…`. 바꾸기는 `user_id`·`admin_paused_at IS NULL`·차지 없음(또는 15분 넘은 차지) 조건부라, 읽은 뒤 관리자가 멈췄거나 실행기가 잡았으면 409. 다음 실행 시각을 앞으로 미루므로 실행기가 목록을 읽은 직후·차지 직전에 고쳐도 그 차례는 차지되지 않는다(차지가 `next_run_at <= 지금`을 다시 본다) — 끝난 실행이 고친 값을 옛 값으로 덮지 않는다.
- 검증: `tests/app-schedules-route.test.ts`(4개 추가 — GET 내 것만·문서 id, 고치기 바꾸는 칸·조건·다시 켜기, 직원이 멈춘 예약은 멈춘 채로, 거절 7가지와 거절이면 안 바꿈). 브라우저로 보지 않았다(개발 서버가 운영 DB를 씀).

## 완료 메일 받기 (2026-11-08, 0069)

예약은 실패·멈춤 때만 메일을 보냈다. 주간 보고처럼 정기 결과를 받으려는 예약은 끝났는지 실행 기록을 열어 봐야 알았다.

- 예약 칸(만들기·고치기)의 **'실행을 마치면 메일로 알림 받기'**(기본 꺼짐) — `app_schedules.notify_on_success`(0069). 목록에 '완료 메일 받음'.
- 실행기가 완료한 예약 중 이 칸이 참인 것만 **예약한 직원 본인에게** 메일(`scheduleSuccessMail` — 앱·예약·마친 시각·다음 실행·'결과 보기' 링크(대화, 대화 id가 없으면 그 앱 실행 기록)). **결과 글·입력값은 메일에 싣지 않는다** — 메일은 기관 밖 메일함으로 갈 수 있고 결과는 로그인해 본다. 실패·멈춤 메일은 이 칸과 상관없이 그대로 간다.
- 메일이 설정돼 있지 않거나 주소가 없으면 조용히 건너뛴다. 보내기가 실패해도 실행 결과는 완료로 남고 운영 기록 warning(`앱 예약 완료 알림을 보내지 못함`)만 남긴다(다시 보내지 않음).
- 요청 본문 `notify_on_success`는 참·거짓만(그 밖은 400), 보내지 않으면 거짓.
- **0069는 코드 배포 전에 적용** — 예약 목록·만들기·고치기가 이 칸을 읽고 쓴다(없으면 예약 화면 503).
- 검증: `tests/app-schedules.test.ts`(3개 — 고른 예약만 알림·실패에는 없음, 알림 실패는 경고만, 메일 글에 결과 글 없음·이스케이프·한국 시각), `tests/app-schedules-route.test.ts`(1개 — 만들기·고치기 저장·기본 거짓·400). 시험 DB에 두 번 적용·칸 확인. 실제 메일 발송은 보지 않았다.

## 결과를 한글 파일로도 만들기 (2026-11-08, 0071)

주간 보고처럼 정기 결과를 한글 파일로 쓰는 예약은 매번 대화를 열어 '한글 파일 만들기'를 눌러야 했다.

- 예약 칸(만들기·고치기)의 **'결과를 한글(HWPX) 파일로도 만들기'**(기본 꺼짐) — `app_schedules.export_hwpx`(0071). 목록에 '한글 파일도 만듦'.
- 실행을 마치면 결과를 **표준 보고서 한글 파일**로 만들어 그 직원의 결과물 화면 '대화에서 만든 파일'에 둔다(`src/lib/apps/schedule-result-file.ts` `saveScheduledResultFile`). **손으로 내보내기와 같은 규칙·같은 중복 열쇠**(`app-result:{메시지}:{답 해시}`, `buildAppResultHwpx` — 모델 없음, AI 작성 초안 표시·확인 필요 안내·출처·한글 표) — 나중에 대화에서 '한글 파일 만들기'를 눌러도 새로 만들지 않고 이 파일을 돌려준다. 끝나지 않은 단계가 있는 결과·빈 답은 만들지 않는다.
- 완료 메일(0069)도 받는 예약이면 메일에 **'한글 파일 받기'** 단추가 붙는다(`/api/files/[id]` — 로그인한 주인만 받는다).
- 만들기가 실패해도 실행은 완료로 남고 운영 기록 warning(`앱 예약 결과 한글 파일을 만들지 못함`)만(다시 만들지 않음 — 대화에서 손으로 만들 수 있다). 예약 칸에서 양식을 고르지는 않는다 — 앱 빌더의 '결과 한글 파일 양식'이 있으면 그 기관 양식에, 없거나 쓸 수 없으면 표준 보고서에 담는다([결과 내보내기](APP_RESULT_EXPORT.md)).
- **0071은 코드 배포 전에 적용** — 예약 목록·만들기·고치기가 이 칸을 읽고 쓴다.
- 검증: `tests/app-schedule-result-file.test.ts`(4개 — 같은 열쇠·실제 한글 파일 글, 이미 있으면 그 파일, 끝나지 않은 결과·빈 답은 null, 동시 저장 진 쪽·읽기 오류), `tests/app-schedules.test.ts`(2개 — 고른 예약만·파일 id를 메일로·실패는 경고, 메일 단추), `tests/app-schedules-route.test.ts`(저장·400). 시험 DB에 두 번 적용·칸 확인.

## 올린 파일 (2026-11-08, 0073)

파일이 필요한 앱(엑셀 취합 정리·회의 자료 요약 등)은 문서함이 없으면 예약할 수 없었다. 채팅 첨부는 한 대화에 묶이고 보내지 않으면 24시간 뒤 정리되므로 첨부 id를 그대로 저장할 수 없다.

- **예약이 사본을 따로 갖는다**: 만들기·고치기 때 실행 화면에 붙인 **읽힌 첨부**(`attachment_ids` — 요청자의 것·`ready`만, 관리자도 남의 첨부를 못 가져옴)를 저장소 `app-schedule-files/{기관}/{직원}/{id}.{확장자}`로 복사하고 `app_schedules.files`(0073, `[{id,name,size,path}]`, 3개 CHECK)에 적는다(`src/lib/apps/schedule-files.ts` `copyAttachmentsForSchedule`). 하나라도 못 하면 만든 사본을 지우고 거절, 예약 저장이 실패해도 사본을 지운다. 원래 첨부·대화와 따로 산다(원래 대화를 지워도 예약 파일은 남는다).
- **실행할 때마다 사본을 새 첨부로 다시 올려** 그 실행의 대화에 붙인다(`attachScheduleFiles` → `attachStoredObject` — 직접 올리기·'지난 파일 다시 붙이기'와 같은 발급·확인 길이라 형식·크기·읽기·스캔 PDF(NODA `/parse`)·사용 기록 `file_attached`가 같다). 대화 실행기에는 손 실행과 같은 `attachment_ids`로 간다. 하나라도 못 올리거나 읽지 못하면 그 차례는 **실패**(만든 첨부는 묘비로 — 다음 차례에 다시, 연속 3회면 멈춤). 실행이 시작 전에 거절되면(한도·판 바뀜·계정) 올린 첨부를 묘비로 지운다(대화에 묶인 것은 건드리지 않음).
- **고치기**: `file_ids`로 남길 예약 파일(보내지 않으면 모두 남김), `attachment_ids`로 더할 파일. 저장한 **뒤에** 뺀 파일의 사본을 지운다(저장이 실패하거나 그 사이 바뀌면 새 사본만 지운다). 예약에 없는 id는 400.
- **지우기**: 예약을 지우면 행을 지운 뒤 사본을 지운다. 탈퇴 처리는 지운 예약 행에서 경로를 받아 DB 단계가 끝난 뒤 지운다(`user-withdrawal.ts` ⑤). 사본 삭제 실패는 운영 기록 warning(경로)만.
- 화면: 예약 칸에 '지금 붙인 파일 N개를 예약에 사본으로 저장합니다'(읽는 중인 파일은 저장되지 않는다고 안내), 고치기에서는 저장한 파일마다 체크(풀면 뺌). 목록에 '저장한 파일 N개'. 화면 응답에는 이름·크기만 싣고 저장소 경로는 내보내지 않는다(`scheduleView`).
- 한계: 저장한 사본은 원래 파일을 고쳐도 바뀌지 않는다(고치기로 다시 붙인다). 실행마다 다시 읽으므로 스캔 PDF는 매번 NODA로 간다. 외부 연동(Webhook)은 사본을 갖지 않고 외부 시스템이 호출마다 파일을 보낸다([앱 연동](APP_WEBHOOKS.md) '보내는 파일').
- **0073은 코드 배포 전에 적용** — 예약 목록·만들기·고치기·실행이 이 칸을 읽는다(없으면 예약 화면이 503, 실행기는 행을 못 읽는다).
- 검증: `tests/app-schedule-files.test.ts`(12 — 꼴·경로 접두사·보기에 경로 없음, 남길 파일, 복사는 요청자의 읽힌 첨부만·도중 실패 정리, 만들기 저장·실패 정리·거절, 고치기의 남기기·더하기·뺀 사본만 지움·모르는 id 400·0행이면 새 사본만 지움, 지우기, 실행 때 새 첨부·거절이면 묘비·못 올리면 실행 안 함, 탈퇴·화면 연결), `tests/app-webhook-documents.test.ts`(파일·문서 합쳐 3개·파일 필수 앱 문구). 시험 DB에 두 번 적용·CHECK 확인.

## 멈춘 실행 자동 이어 가기 (2026-11-08, 0074)

예약 실행은 실행기 한 번(200초) 안에 끝나야 하고, 넘으면 새 모델 호출을 시작하지 않고 멈춰 끝난 단계를 저장한다. 예전에는 이것이 '실패'로 세져 **다음 정해진 시각(내일)에 처음부터** 다시 했고, 늘 오래 걸리는 앱은 연속 3회 실패로 멈췄다.

- 멈춘 실행의 마지막 답변(그 직원의 대화)에 **이어 갈 진행**이 남았으면(`hasResumableProgress` — 재개용 입력 `app_inputs`가 있고 끝난 단계나 반복 도중 끝난 줄이 있음) 실패로 세지 않고 `resume_message_id`에 그 답변을 적어 **다음 실행기 차례(약 5분 뒤)**에 이어 간다(`next_run_at` = 지금). 실패 메일은 보내지 않고 운영 기록 info만, 목록의 마지막 결과 글은 '처리 시간이 길어 멈춘 실행을 몇 분 뒤 이어서 합니다'.
- 이어 가는 차례는 손 '이어 실행'과 **같은 길**이다 — `runAppAs`가 `resume_message_id`를 실어 대화 실행기가 그 직원의 기록인지·같은 입력·같은 앱 판인지 다시 보고 끝난 단계를 다시 쓴다(`restoreAppSteps`). 결과는 새 `[예약]` 대화로 남는다.
- **입력만 쓰는 예약만** — 올린 파일·고른 문서가 있는 예약은 대화 실행기가 이어 실행을 받지 않아(근거가 바뀔 수 있음) 이어 가지 않는다(`canAutoResume`). 자료·도구가 켜진 앱도 기록에 재개용 입력이 없어 이어 가지 않는다.
- 한 차례에 **2번까지**(`SCHEDULE_MAX_RESUMES`, `resume_count`). 넘으면 평소 실패로 센다. 완료·실패·멈춤·기관 스위치로 넘긴 차례·고치기·다시 켜기에서 칸을 비운다.
- 이어 실행이 거절되면(대화를 지워 기록이 없음 404·앱 판이 바뀜 409·한도 등) 실패로 세고 **곧(다음 실행기 차례) 처음부터** 다시 한다 — 앱이 바뀌었으면 그때 평소처럼 멈춘다. 앱을 쓸 수 없으면(403) 바로 멈춘다.
- 시험: `tests/app-schedule-resume.test.ts`(진행 판정·결과 반영·이어 감·이어 가는 차례의 본문·거절·실행기 집계·연결·0074). 시험 DB에 0074를 두 번 적용. 실제 실행기로 멈춤 → 이어 감을 끝까지 돌려 보지는 않았다(모델 비용·운영 DB).

## 지키는 것

- **실행은 예약한 직원의 권한·사용량으로 한다.** 실행기는 그 직원의 세션 꼴(id·역할·부서)을 만들어 대화 실행기(`prepareTurn`·`streamTurn`)를 손으로 실행할 때와 같은 본문(`agent_id`·`app_inputs`·`app_version`)으로 태운다. 앱 사용 권한(`canUseAgent`)·기관 한도·모델 정책·금지어 검사·사용 기록·대화 저장이 모두 같다. 직원 API는 `user_id = 요청자`라 남의 예약을 보거나 바꾸지 못한다. 기관 관리자는 따로 관리 범위 직원의 예약을 입력값 없이 보고 사유와 함께 멈출 수 있다 — 관리자가 멈춘 예약은 직원이 다시 켜지 못한다([관리자 통제](APP_AUTOMATION_ADMIN.md), 0050). 계정 탈퇴 때 예약은 지워진다.
- **중복 방지(DB 조건부 차지)**: 실행기는 `status='active' AND next_run_at <= now AND (claimed_at IS NULL OR claimed_at < now - 15분)`인 행만 `claimed_at`을 써서 차지하고, 한 행이 바뀐 호출만 실행한다. 두 실행기가 겹쳐 돌아도 한 번만. 끝나면 다음 시각을 **지금 뒤**로 세서 같은 시각이 두 번 돌지 않는다. 함수가 죽어 차지가 남으면 15분 뒤 다시 잡힌다(그 실행은 한 번 더 돌 수 있다 — 결과 저장 실패는 `system_logs` error).
- **멈춤·실패**
  - 바로 멈춤(이유를 적고 메일): 앱 설정이 바뀜(판 다름, 409) · 앱을 쓸 수 없음(권한·삭제, 403·404) · 직원 계정 비활성·탈퇴 · 소속 부서 바뀜.
  - 실패 뒤 다음 차례에 다시: 기관 한도(429)·입력 검사(400)·모델 오류·응답이 끝나지 않음. **연속 3회** 실패하면 멈춘다(`SCHEDULE_MAX_CONSECUTIVE_FAILURES`). 실패한 차례를 곧바로 다시 돌리지 않는다(같은 오류로 모델만 다시 부른다).
  - 실패·멈춤마다 예약한 직원에게 **메일**(`scheduleFailureMail` — 앱·예약·시각·이유·다음 실행, 입력값·결과 글은 싣지 않음). 메일이 설정돼 있지 않으면 화면의 상태 칩·이유만. 운영 기록(`system_logs` `api`)에는 예약 id·앱 id·이유만 남기고 받는 사람 주소·입력값은 남기지 않는다.
  - 화면의 **'실행 지연'**: 활성 예약의 예정 시각이 1시간 넘게 지났는데 실행되지 않았으면 표시한다(실행기가 안 도는 신호 — 관리자에게 알리라고 안내).
- **시간대는 한국 시간 고정**(직원이 고르지 않음). 날짜 계산은 UTC+9를 더한 뒤 UTC 성분을 읽는 방식이고 한국은 서머타임이 없다. 매월은 1~28일만(29~31은 건너뛰는 달이 생긴다).
- 다시 켜면 다음 시각을 **지금부터** 다시 세고 실패 수·차지를 지운다. 멈춘 사이의 차례는 돌지 않는다.
- 마이그레이션 0048(`app_schedules`) — 추가만, RLS 켜고 정책 없음(서비스 키만), 앱·사용자·부서·기관 삭제에 연쇄, `last_conversation_id`는 대화 삭제 때 NULL.

## 지금 한 번 실행 (2026-11-10, 마이그레이션 없음)

- 앱 예약 화면의 켜진 예약에 **'지금 한 번 실행'** — `PATCH /api/apps/schedules/[id] { action: 'run_now' }`가 다음 실행 시각을 지금으로 당긴다. 실행기(5분마다)가 다음 차례에 평소처럼(같은 권한·한도·사용 기록·완료 메일·한글 파일) 실행하고, 그 뒤로는 원래 일정대로 돈다.
- 내 예약·켜짐·관리자 잠금 없음·실행기가 잡지 않음일 때만(조건부 갱신 — 아니면 409, 잠금 403). 멈춘 예약은 먼저 다시 켜라고 409, 방금(마지막 실행 10분 안) 실행한 예약은 429, 이미 차례가 된 예약은 바꾸지 않고 그대로. 기관이 예약을 꺼 두었으면 단추를 보이지 않는다(실행기도 넘긴다).

## 실행기와 운영 설정

- 라우트 `GET|POST /api/cron/app-schedules`(`maxDuration` 300). 자격은 Bearer 비밀값 하나 — **업무 작업자와 같은 `WORK_WORKER_SECRET`**(pg_cron이 Vault `work_worker_secret`으로 이미 싣는 값) 또는 `CRON_SECRET`, 상수 시간 비교. 둘 다 없으면 503(2026-11-03에 작업자 비밀값을 더했다 — `CRON_SECRET`은 Vercel에만 있고 Vault·`.env.local`에 없어 pg_cron이 실을 수 없었다. 비밀값을 새로 만들어 돌리는 대신 이미 맞는 값을 쓴다). 한 번에 예약 3개(`SCHEDULE_BATCH`)까지, 시간 예산 180초(`SCHEDULE_RUN_BUDGET_MS`)를 넘기면 남은 것은 다음 호출에(`partial`). 응답 `{ checked, completed, failed, paused, skipped, partial }`.
- **Vercel 예약 작업에는 넣지 않는다** — Hobby 요금제는 예약 작업이 2개·하루 한 번이라(이미 NODA·예산 알림이 쓴다) 시각을 맞출 수 없다. 업무 작업자(`/api/work/worker`)처럼 **Supabase pg_cron**이 부른다. 운영 설정(2026-11-03 등록함 — Vault의 `work_worker_secret`을 그대로 쓴다):
  ```sql
  select cron.schedule('workon-app-schedules', '*/5 * * * *', $$
    select net.http_post(url := 'https://workon-ai.vercel.app/api/cron/app-schedules',
      headers := jsonb_build_object('Authorization', 'Bearer ' || (select decrypted_secret from vault.decrypted_secrets where name = 'work_worker_secret')),
      timeout_milliseconds := 290000);
  $$);
  ```
  5분마다 부르므로 실제 실행은 예정 시각에서 **최대 5분** 늦는다. 한 호출이 290초를 넘기면 pg_net이 끊지만 함수는 300초까지 이어 간다.
- 확인: `cron.job_run_details`(성공)와 `net._http_response`(`/api/cron/app-schedules` 응답 200)를 본다. 비밀값 없이 부르면 401, Vercel에 두 비밀값이 모두 없으면 503.

## 배포 순서

1. 운영 DB에 0048 적용(`npm run db:migrate -- 0048`) — **코드 배포 전**. 적용하지 않으면 예약 화면·API만 503이고 다른 기능에는 영향이 없다.
2. 코드 배포. `WORK_WORKER_SECRET`·`CRON_SECRET`은 이미 운영 환경 변수에 있다.
3. Supabase SQL 편집기에서 위 Vault·pg_cron을 건다(사용자). `cron.job_run_details`에서 5분마다 200이 찍히는지, 비밀값 없이 부른 요청이 401인지 본다.
4. 직원 계정으로 앱 하나에 '매일 (몇 분 뒤) 예약'을 걸어 다음 차례에 `[예약]` 대화가 생기는지, 예약 목록의 '실행 N회'·마지막 결과가 바뀌는지 본다.

- 결과 저장(`finish`)은 실패하면 한 번 더 해 본다(2026-11-12). 그래도 못 하면 `system_logs` error로 남고 차지가 남아 15분 뒤 다시 잡히는데, **끝까지 마친 실행은 다시 돌리지 않는다** — 마친 실행의 대화에 예약 도장(`conversations.metadata.app_schedule = { id, finished_at }` — `stampScheduleRun`, 마이그레이션 없음)을 남기고, 실행기가 멈춘 차지를 다시 잡으면 그 차지 이후의 도장을 찾아(`findCompletedScheduleRun` — 그 직원·그 앱·그 예약만) 있으면 마친 것으로 기록한다(결과 `recovered`, 완료 메일·한글 파일은 다시 하지 않음). 도장을 못 남겼거나 끝까지 못 간 실행(함수가 시간에 끊김)은 예전처럼 다시 돈다. 이어 가는 실행(0074)은 제 상태를 따로 가져 이 확인을 하지 않는다.
- 멈춘 실행 자동 이어 가기는 입력만 쓰는 예약만(위 절). 손으로 실행하다 멈춘 실행은 여전히 사람이 '이어 실행'을 누른다.
