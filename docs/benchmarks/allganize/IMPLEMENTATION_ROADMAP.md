# WORKON SaaS — 알리웍스 벤치마크 구현 순서

2026-10-28. 이 문서는 개발 제안과 현재 구현을 구분한다. 상세 벤치마크는 [플랫폼 분석](PLATFORM_FEATURES.md), [빌더 분석](BUILDER_AND_WORKFLOWS.md), [전체 앱 목록](APP_CATALOG.md), [전체 앱 구현 대응표](APP_IMPLEMENTATION_MAP.md)를 본다.

## 1. 먼저 합칠 개념

- **앱**: 역할·입력·자료·허용 도구·결과 형식·공개 판을 저장한 재사용 가능한 업무 수행 방식.
- **비서**: 대화를 입구로 사용하는 앱. 단순 프롬프트부터 도구 사용형까지 가능하다.
- **워크플로우**: 재현 가능한 단계·조건·변수 매핑. 필요한 단계에서 모델을 부를 수 있다.
- **작업**: 앱을 실행한 한 건. 요청자·자료·실행 판·단계·검토·파일·비용을 보관한다.
- **도구**: 문서 읽기·검색·표 계산·양식 채우기·승인된 외부 API 등의 구현 단위.

앱과 작업은 서로 대체하지 않는다. 앱 사용 권한은 남의 작업 파일 열람 권한이 아니다. 기관 관리자가 공식 앱을 관리하더라도 직원의 개인 작업 원문을 자동으로 열 수 있게 하지 않는다.

## 2. 현재 토대와 실제 간극

### 재사용

| 영역 | 기존 코드 | 유지할 것 |
|---|---|---|
| 앱 표시·설정 | agent-catalog·agent-form·AgentEditorModal | 이름·분류·역할·모델·사용 설명·예시 |
| 공유·승인·판 | agent-permissions·agent-store·save_agent | 개인/부서/공식·낙관적 버전·승인 도장·복구 |
| 읽기·검색 | noda·capabilities/doc-search·attachments | ReadLayer·보관함 경계·공통 자료실·숫자 확인 |
| 도구 | capabilities/*·table-engine·doc-fill | 허용 능력 레지스트리·계산과 모델 분리·파일 형식 검사 |
| 내구성 실행 | work/runs·store·services | 작업자 lease·체크포인트·재시도·중복 방지 |
| 결과·검토 | work/artifacts·review·documents·TaskWorkbench | 판·파일 해시·확인 사항·복구·다운로드 권한 |
| 기관 운영 | work/admin·usage_logs·super/admin | 업무 스위치·양식 승인·한도·감사 |

### 새로 연결할 것

현재 `agents`는 구성할 수 있지만 `workflows`는 열 개의 고정 구현이다. 후속 [설정 연결 1차](IMPLEMENTATION_APP_BINDING.md)에서 작업 생성 시 비서 지침·모델·버전을 보존하고 모델 호출에 반영했다(DB 0036 적용·배포 전). 문서함·능력·입력 스키마·공개 판 분리는 아직 연결하지 않았다. **목록 통합과 작성 설정 연결만으로 B 단계 전체가 완료된 것은 아니다.**

비서의 임의 프롬프트를 취합·정산 계산기에 덧붙이는 방식은 적절하지 않다. 워크플로우별 허용 지시·입력·계산·검수 규칙을 명시하고 모델에 맡길 단계만 연결해야 한다.

## 3. 공통 실행 기능

다음 여덟 기능을 조합해 많은 앱을 만든다. 경쟁사의 내부 모듈 구조가 아니라 WORKON 설계 제안이다.

| 기능 | 필요한 내용 | 현재 사용 가능한 토대 | 신규 작업 |
|---|---|---|---|
| 입력 | 텍스트·파일·선택·날짜·반복 항목·누락 확인 | FormFields·첨부·workflow JSON | 앱별 입력 스키마·검증·기본값 |
| 읽기·검색 | 문서 구조·쪽/셀·권한·자료 범위 | ReadLayer·NODA 근거 매칭 | 허용 문서 선택·메타데이터 필터 |
| 생성·변환 | 요약·번역·문체·목차·구조화 출력 | llm·agent 지시·도구 루프 | 입력 폼에서 실행·결과 계약 검증 |
| 추출·비교 | 항목·질문·계약 조건·판 차이와 근거 | items·qa·currentize·regulations | 범용 추출 스키마·대조표·누락 표시 |
| 계산 | 단위·그룹·집계·대사·비율 | table-engine·collection·settlement | 표 대응 UI·설문 규칙·원본 셀 연결 |
| 검토 | 필수값·근거·수치·사람 결정 | work/review·completion gate | 단계 중단·보완·동일 실행 재개 |
| 파일 | 양식 HWPX·DOCX·XLSX·검증 | doc-fill·work/documents·xlsx | 결과 계약·CSV·필요시 PPTX 별도 엔진 |
| 연결·반복 | 읽기 API·작업간 전달·예약·승인 쓰기 | 공공 커넥터·업무 worker | 자격증명 관리·트리거·예약·쓰기 승인 |

## 4. 구현 단계

### A. 앱을 찾고 다시 쓰는 입구 — 이번 1차

- `/apps`: 이미 허용된 비서와 구현된 업무를 한 목록에서 탐색한다.
- 이름·목적·능력·출력 형식 검색, 사용 방식·제공 범위 필터.
- 일반 비서는 대화, 업무는 작업 시작, 링크는 외부 사이트라는 차이를 표시.
- 기관에서 끈 업무·비활성 비서·잘못된 연결은 실행 버튼을 내지 않는다.
- 기존 비서 만들기·권한 API를 재사용한다. 목록 진입·딥링크만으로 대화·모델 호출·외부 쓰기를 실행하지 않는다.

완료 기준: 앱 출처별 부분 장애, 일반/개인 비서, 기존 대화 URL 우선, 외부 링크 프로토콜, 기관 스위치, 잘못된 저장 설정을 검사. 이는 새 자동화 엔진이나 100개 앱 실행 지원을 뜻하지 않는다.

### B. 설정형 앱 제작과 기존 실행기 연결 — 다음 핵심

1. 기존 비서 저장·판 관리에 타입 있는 실행 설정을 붙이는 DB/서비스 계약을 설계한다. 실행 방식은 대화·단발 폼·검증된 업무 흐름으로 구분한다.
2. 기관이 지시·자료·양식·입력 항목·결과를 설정한다. 수정하면 앱 정의의 새 판이 생긴다.
3. 공식 앱 공개 판과 편집 중인 판을 분리하고, 기존 공식 승인 정책을 따른다.
4. 작업 생성 시 실행 권한과 업무 스위치·양식 접근을 다시 확인하고 정의 판·자료·모델/도구 정책의 스냅샷을 남긴다.
5. 현재 작업·실행·검토·파일 도메인에 연결한다. 단순히 agent_id를 기록하거나 URL 파라미터를 붙이는 것으로 완료하지 않는다.

완료 기준:

- 앱 이름·자료·기본값을 바꾸어도 코드를 추가하지 않고 같은 실행기를 재사용.
- 관리자가 바꾼 새 판이 이미 실행 중인 작업을 조용히 바꾸지 않음.
- 사용자가 다른 기관의 앱/양식 id를 보내도 작업이 생성되지 않음.
- 비서 사용 권한과 작업 원문 접근을 각각 검사.
- 모델을 쓰지 않는 취합·정산의 수치 계산은 그대로 프로그램이 수행.
- 실제 업무 생성→검토→수정→파일 다운로드가 연결됨.

### C. 자주 쓰는 앱 묶음과 공통 도구 보완

앱 수보다 필요한 기능을 우선 구현하되, 공개 앱 100개는 전체 대응표에 빠짐없이 참조로 남긴다.

| 앱 묶음 | 우선 후보 | 기존 엔진 | 주요 추가점 |
|---|---|---|---|
| 가벼운 사무 앱 | 요약·번역·교정·문체·안건·질문 생성 | 대화 비서·첨부 읽기 | 입력 폼·결과 재사용·용어집 |
| 근거 앱 | 기관 규정 Q&A·FAQ 생성·근거 회신 | ReadLayer·regulations·qa | FAQ 저장/CSV·원문 위치·최신 판 |
| 문서 앱 | 공문·기안·보고·회의록·RFP | 기존 HWPX·items·qa | 기관별 구성·RFP 요구 항목 계약 |
| 추출·비교 앱 | 계약 항목·NDA·정관·완비성 검사 | items·review·ReadLayer | 구조화 스키마·인용·누락/차이 UI |
| 표 앱 | 월간 취합·청구/입금 대조·설문 | collection·settlement·table-engine | 데이터 대응·설문 집계·결측·중복 기준 |
| 조사 앱 | 정책 조사·유사 사업·기관 동향 | 공공 커넥터·문서 검색 | 일반 웹 소스·계획·보완 탐색·원가 제한 |
| 운영 앱 | FAQ 정비·실패 분석·효과 보고 | usage_logs·업무 현황 | 피드백·채택·재작업·실측/추정 구분 |

일본 법률 앱은 처리 방식만 참조한다. 국내 근거·검증 기준을 설계하기 전 같은 이름의 기능으로 제공하지 않는다. SQL 생성은 DB 실행과 다르고, VBA 초안은 실제 PPTX 생성과 다르다. 고객사 특수 앱은 공공기관 업무와 맞지 않으면 후순위로 남긴다.

### D. 단계 조합·시스템 연결·반복 실행

- 검증된 도구와 단계의 선형 조합부터 구성하고 조건 분기를 더한다. 임의 코드 실행·자유 그래프 편집을 먼저 만들지 않는다.
- 문서 소스 연결은 수집 상태·원본 권한·삭제·다시 읽기·만료를 포함한다. API 한 번 호출되는 것으로 커넥터 완성이라 하지 않는다.
- 읽기 전용 연동 후, 쓰기 도구는 사용자에게 목적·대상·변경 내용을 보여주고 승인한 실행만 처리한다.
- 예약은 시간대·중복 방지·실행 당시 사용자 상태·취소·누락 회복·비용 제한을 포함한다.
- 외부 쓰기는 승인 뒤에도 권한·대상을 재확인한다. 실패 재시도가 중복 발송·등록을 만들지 않아야 한다.
- 처리 중 대기·확인·실패의 이유와 복구 지점을 화면에 남긴다.

완료 기준: 실제 자료로 동일 설정을 다음 회차에 재사용, 일부 실패·재실행·권한 철회·요금 한도·중복 이벤트를 통과. 단계 로그는 사용자 행동과 실행 결과를 기록하며 모델의 비공개 추론을 보여 준다고 표현하지 않는다.

## 5. 단계마다 측정할 것

- 최종 파일이 실제 한글·엑셀에서 사용 가능한가.
- 자료 준비 + 입력 + 대기 + 검토 + 수정 + 서식 정리에 든 전체 시간이 줄었는가.
- 근거 없는 수치·날짜·인용과 누락을 드러내는가.
- 같은 작업을 다시 실행해도 중복 결과·비용·외부 등록이 생기지 않는가.
- 다른 기관·사용자의 자료가 검색·결과·로그에 섞이지 않는가.
- 요청 수·모델 호출 수·업무 건수·파일 수를 서로 다른 지표로 집계하는가.
- 다음 회차에도 담당자가 같은 앱을 선택하는가.

## 6. 이연·별도 위험

- PC 설치 앱·로컬 프로그램 제어·온프레미스·폐쇄망은 추후.
- 임의 MCP 서버와 HTTP URL을 모든 직원에게 무조건 개방하지 않는다. SSRF·자격증명·기관 정책과 범위 검사 필요.
- HWPX 실제 미리보기는 운영 렌더러가 아직 없어 별도 결정이 필요하다.
- 로그인 경로의 기본 부서 추측 배정은 기존 보안 문제로 별도 우선 수정 대상이다. 이번 앱 목록 통합이 이를 고친 것은 아니다.
- 운영 DB·배포·외부 공급자 설정을 이번 연구를 위해 변경하지 않는다.

## 7. 다음 작업의 구체 산출물

B 단계 시작 시 만들 것: 앱 실행 설정 ADR, 입력/결과 JSON 계약, 기존 비서 저장/승인/이력과의 DB 마이그레이션, 생성 API와 실행기 스냅샷 연결, 대표 앱 두 개의 끝까지 실행 시험. 범용 빌더 화면만 먼저 만들어 실행기와 단절시키지 않는다.
