# 앱·문서함 연결의 로컬 통합 검증

2026-10-29. 이전 단계의 단위 검증을 실제 PostgreSQL·HWPX 생성까지 확장했다. 운영 DB와 배포 환경은 변경하지 않았다.

## 환경과 범위

기존 개발 DB를 초기화하지 않도록 work-testdb.mjs에 WORK_TEST_DB_INSTANCE 옵션을 추가했다. 영문 소문자·숫자·밑줄의 인스턴스 이름을 검사하고 임시 클러스터 폴더와 DB 이름을 분리한다. 별도 포트 54339의 workon_appbinding_20261029에서 마이그레이션 36개를 처음부터 적용했다. 완료 후 이 시험 인스턴스는 정지했다. 기본 시험 DB와 사용자 운영 DB는 변경하지 않았다.

새 테스트 work-app-rag-flow.test.ts는 localhost/127.0.0.1의 workon_ 접두사 DB에서만 실행한다. 임의 UUID의 시험 기관·사용자·비서를 만든다. 서비스·PG 저장소·실행기·원자료 확인·양식 채우기·실제 HWPX ZIP을 사용한다. 비서 설정 로더·모델 정책·생성 모델·문서 검색 제공자는 고정 시험 응답이다. 따라서 운영 Supabase 로더, 외부 ReadLayer/NODA, 외부 LLM을 실제로 호출한 검증은 아니다.

## 확인 결과

- 새 보고서: 첨부 자료 등록 → 작업 준비 → 선택 문서함 근거 전달 → 생성 → HWPX 검증 상태 valid 및 내부 section0.xml의 생성 본문 확인.
- 민원 회신: 질문·담당자 확인 사실 → 문서함 근거를 사용하는 질문별 답변 → 실제 HWPX 본문 확인.
- 두 업무 모두 app_snapshot 저장·조회, 출처 이름·위치·본문의 버전 저장과 작업 상세 응답을 확인.
- 직원 수정으로 새 버전을 만들어도 appEvidence가 유지됨.
- 원본 비서 이름을 바꿔도 저장한 비서 이름·버전이 바뀌지 않음.
- 스냅샷의 agentId와 작업의 agent_id가 어긋나면 PostgreSQL CHECK가 거부함.
- 문서 검색 제공자가 unavailable이면 생성 모델을 호출하지 않고 문서 판·파일도 만들지 않음.
- 기존 업무 실행·P5·DB 회귀 테스트도 통과.

관련 통합·회귀 4개 파일의 최종 사례는 총 33개다(최초 31개 통과 후 신규 실패 경로 2개를 포함한 앱 통합 4개 재검증). TypeScript와 diff 공백 검사도 통과했다.

## 남은 검증

인증된 브라우저 화면, 실제 ReadLayer·외부 LLM, 운영 Supabase 저장소, 서명된 다운로드 경로, 한글 프로그램에서의 시각적 문서 레이아웃은 미검증이다. ZIP의 본문 검사와 한글 앱의 시각 검증은 다르다. 운영 DB에 0036을 적용하고 배포하는 작업도 아직 수행하지 않았다.
