# 관리자용 입력형 앱 실행 현황 (2026-11-01)

알리웍스는 운영자에게 답변형 앱의 실행 기록을 보여 준다. 기록에는 입력, 문서명, 결과, 상태(completed/failed/interrupted), 프롬프트가 들어 있다([REA 재분석](REA_PUBLIC_WEB_ANALYSIS_2026-10-31.md)). WORKON에는 직원 본인 기록(`/apps/history`)만 있어서, 관리자는 부서 앱이 자주 멈추는지 알 수 없었다.

## 무엇을 보여 주나

`/admin/stats` 맨 아래 '입력형 앱 실행 현황'에 앱별로 아래 항목을 보여 준다. 대상은 관리 범위(자기 부서 + 하위) 부서의 앱이고, 기간은 최근 30일이다.

- 실행 수
- 상태별 수: 완료, 중단, 확인 필요·응답 없음
- 자주 멈춘 단계(실패로 기록된 단계 이름과 횟수, 많은 순 3개)
- 마지막 중단 시각(KST)

정렬은 중단이 많은 앱부터, 같으면 실행이 많은 순이다.

상태는 직원 기록(`src/lib/apps/history.ts`)과 같은 규칙으로 판정한다.

| 기록 | 상태 |
| --- | --- |
| 단계 기록에 `failed`·`not_run`이 있음 | 중단 |
| 단계가 모두 완료·생략이고 마지막 단계가 완료 | 완료 |
| 단계 기록이 끝나지 않음 | 확인 필요 |
| 답 메시지가 없음 | 응답 없음 |

## 보여 주지 않는 것

입력, 결과, 질문, 실행한 사람은 보여 주지 않는다. 감사 화면에서 질문 원문을 가리는 것과 같은 판단이다. 관리자가 상시로 볼 수 있으면 근로자 감시가 되고, 관리자에게 필요한 "어느 앱이 어느 단계에서 멈추는가"는 상태만으로 답할 수 있다.

- **개인 앱:** 이름 없이 한 줄로 묶는다. '개인 앱 N개(이름 비공개)'에 실행 수와 상태 수만 보인다. 개인 앱 이름에 업무나 사람 정보가 들어갈 수 있기 때문이다.
- **단계별 중간 결과:** 답 메시지의 `source_references.app_steps`에는 단계마다 중간 결과 글(`output`)이 들어 있다. PostgREST로 이 칸을 고르면 결과 글까지 서버로 내려온다(로컬 Supabase의 실제 UAT 기록으로 확인했다). 그래서 실행 기록은 DB 함수 `app_run_states`(마이그레이션 0046)로 읽는다. 이 함수는 실행마다 앱 id, 시각, 답 유무, 단계 이름(40자)과 상태만 돌려준다. 실행 권한은 service_role에만 있다.
- **API:** `GET /api/admin/app-overview`는 로그인, 관리자 여부, 관리 범위를 확인한다. 하나라도 없으면 DB를 읽지 않는다. 기관, 관리 범위 부서, 지우지 않은 앱으로 거르고, 한 번에 최근 실행 2,000건까지만 센다(넘으면 화면에 '최근 실행만 셌습니다').

## 코드

- `src/lib/apps/run-overview.ts`: 상태 판정(`runState`)과 앱별 묶기(`summarizeAppRuns`).
- `src/app/api/admin/app-overview/route.ts`
- `src/components/admin/AppRunOverview.tsx`: `/admin/stats`에 붙였다.
- `supabase/migrations/0046_app_run_states.sql`: 함수 추가만 한다. 여러 번 적용해도 안전하다.

## 검증

- `tests/app-run-overview.test.ts`(8개)가 다음을 본다.
  - 상태 판정
  - 앱별 수·자주 멈춘 단계·마지막 중단, 정렬
  - 개인 앱 묶음에 이름과 결과 글이 없음, 모르는 앱의 실행은 세지 않음
  - 표 렌더링: 비공개 묶음, 결과 글 없음, 빈 상태, 잘림 안내
  - API: 401·403일 때 DB를 읽지 않음, 기관·관리 범위·삭제 제외 조건, 함수 호출 인자, 표를 직접 읽지 않음, 앱이 없으면 함수를 부르지 않음, 오류는 503
  - 0046이 단계 이름과 상태만 내보내고, 실행 권한이 service_role에만 있음
- 로컬 Supabase(55321)에 0046을 적용해 실제 PostgREST로 불렀다.
  - service 키: UAT 앱의 실행 5건이 단계 이름과 상태만 담아 왔다. 결과 글은 없었다.
  - anon 키: `42501 permission denied`로 거절됐다.
- 로컬 시험 Postgres에서 0001~0046을 전부 적용했다. 시험 DB를 포함해 전체 126개 파일, 2,284개 시험이 통과했고 tsc 오류는 0이다.
- **확인하지 못한 것:** 브라우저에서 `/admin/stats`를 열어 보지 못했다. 앞선 작업에서 개발 서버가 메모리 부족으로 죽었고, 이번에는 띄우지 않았다. 화면은 서버 렌더링 시험으로만 봤다. 운영 DB에는 0046을 적용하지 않았다.

## 배포 순서

1. 운영 DB에 0046을 적용한다(`npm run db:migrate -- 0046`). **코드 배포 전**에 해야 한다. 적용하지 않으면 이 표만 '앱 실행 기록을 불러오지 못했습니다'가 되고, 다른 기능에는 영향이 없다.
2. 코드를 배포한다.
3. 관리자 계정으로 `/admin/stats`를 열어 표가 나오는지 확인한다.

## 하지 않은 것

- 실패 원인 글: 단계 기록에 원인 코드가 없어서, 어느 단계에서 멈췄는지만 보인다.
- 사용량·비용을 앱별로 묶는 일: '이용통계'의 비서별 축이 이미 맡는다.
- 기간 고르기와 CSV 내보내기
