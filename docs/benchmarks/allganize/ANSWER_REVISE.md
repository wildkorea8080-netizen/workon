# 근거로 고쳐 쓰기 (2026-11-08)

'검증 후 자동 재검색'(검증 실패 → 범위 제한 재검색 → 재작성, 시도·비용 상한)의 재작성 단계. 앞 단계인 [숫자 근거 다시 찾기](NUMBER_RESEARCH.md)는
확인되지 않은 숫자가 다시 찾은 근거에 있는지 **보이기만** 한다. 이 단계는 직원이 단추를 누르면 그 근거로 답을 **한 번 고쳐 쓴다**. 마이그레이션 없음.

## 왜 자동이 아니라 단추인가 (구현자 판단)

- 숫자 확인에 걸리는 답마다 모델을 한 번 더 부르면 그 턴의 비용이 두 배 가까이 되고, 걸린 숫자 상당수는 AI가 계산한 차이·비율 같은 오탐이다.
- 이미 화면에 다 흘러나온 답을 바꾸면 저장 내용과 화면이 어긋난다(숫자 확인의 '답변은 고치지 않는다' 원칙).
- 그래서 직원이 필요할 때만 누르고, **원래 답은 그대로 둔 채** 고쳐 쓴 답을 아래에 따로 보인다. 감사에서 그때 무엇을 답했는지가 남는다.

## 동작

- **단추**: 숫자 확인이 '확인되지 않은 숫자'를 남긴 문서 근거 답변 아래 `근거로 숫자 다시 확인해 고쳐 쓰기`. 받는 답변 규칙은 화면·서버가 같은 함수(`revisionEligibility`, `src/lib/assistant/answer-revise-spec.ts`)로 정한다 —
  문서 근거가 있고 '문서 없이 답함'이 아니며, **공공 데이터 도구 출처·첨부 파일·입력형 앱 결과가 아닌** 답만(그 숫자는 다시 찾은 문서로 확인할 수 없어 고쳐 쓰다 지울 위험이 크다).
- **라우트** `POST /api/messages/[id]/revise`(대화 주인만 — 관리자도 남의 답변은 404, `src/lib/assistant/answer-revise.ts`):
  1. 이미 고쳐 쓴 답이면 모델을 부르지 않고 그것을 돌려준다(**답변 하나에 한 번** — 시도 상한).
  2. 한도(`checkTokenLimit`, 대화와 같음) → 비서(지금도 쓸 수 있고 문서 찾기가 켜짐).
  3. **차지**: `source_references.revision = { status: 'pending', started_at }`를 칸이 비었을 때만 조건부로 쓴다 — 두 번 눌러도 모델은 한 번(둘째는 409). 5분 넘은 표시는 끊긴 것으로 보고 그 시각을 조건으로 다시 차지.
  4. **찾기**: 그 답의 질문(바로 앞 사용자 메시지, 첨부 표시 줄 뗌)으로 대화와 같은 찾기(`prepareLikeChat` — 비서 보관함·공통 자료실·판·시행일) + 확인되지 않은 숫자가 든 답변 문장으로 더 찾기(숫자 근거 다시 찾기와 같은 문장 3개·5초). 더 찾은 근거는 겹침을 빼고 **6조각까지**, 번호는 앞 근거 뒤로 잇는다.
  5. **모델 한 번**: 비서 지시문 + 참고 자료·인용 규칙 + 더 찾은 근거 + 고쳐 쓰기 지시(숫자는 참고 자료 값만·문장 끝 `[n]`·확인 안 되면 쓰지 말거나 '문서에서 확인되지 않음'·계산한 값은 밝힘·나머지 내용과 형식은 그대로), 메시지는 앞 질문 → 앞 답변 → 고쳐 쓰기 요청. 비서 모델(기관 정책), 출력 상한은 대화와 같음.
  6. **사용 기록** `answer_revised`(모델·토큰·원가, 감사·이용통계 표시 '근거로 고쳐 쓰기(AI)') — 글이 비어도 토큰을 썼으면 남긴다.
  7. **숫자 확인**을 고쳐 쓴 답에도 — 본 숫자 = 시스템 프롬프트(참고 자료·더 찾은 근거) + 질문. 요청 글의 숫자와 앞 답변은 넣지 않는다.
  8. **저장**: `source_references.revision = { status: 'done', text, chunks, number_check: { unverified }, revised_numbers, model, created_at, started_at }`를 그 차지일 때만. 원래 `content`·`chunks`·`number_check`는 그대로.
  실패(찾기 실패 503·모델 실패 502·빈 답 502)는 차지를 풀어 다시 누를 수 있다. 저장만 실패하면 고쳐 쓴 답은 돌려주고 화면에 '저장하지 못해 새로 열면 보이지 않습니다'를 붙인다(운영 기록 warning).
- **화면**: 원래 답 아래 '근거로 고쳐 쓴 답' 이름표가 붙은 말풍선(근거 칩·`[n]` → 근거 창, 남은 확인되지 않은 숫자는 같은 주황 안내)과 '원래 답변의 확인되지 않은 숫자(…)를 문서에서 다시 찾아 고쳐 썼습니다' 한 줄. 지난 대화에서도 보인다.
- **다음 질문**: 대화 이력은 고쳐 쓴 답을 앞 답변으로 본다(`loadHistory`가 `source_references->revision->>text`를 함께 읽음) — 직원이 고친 숫자를 믿고 이어 묻기 때문이다.

## 한계

- 고쳐 쓴 답이 맞는지는 모른다 — 숫자 확인을 다시 걸어 남은 숫자를 보일 뿐이다.
- 질문이 짧은 이어지는 질문이면 대화의 '앞 질문과 묶어 다시 찾기'를 하지 않는다(그 질문 하나로 찾는다). 숫자 문장으로 더 찾기가 그 빈자리를 일부 메운다.
- 종량제(토큰 한도) 기관의 월 토큰 합은 `chat_message`만 센다(0057) — 이 기록은 금액 한도(연간 정액·개인 월 한도)에만 들어간다. 문서 찾기 평가 답변(`rag_eval_answer`)과 같다.
- 공유 대화(`/shared/…`) 화면은 고쳐 쓴 답을 보이지 않는다.
- 실제 모델·NODA·브라우저로는 확인하지 않았다(가짜 의존 시험만).

검증: `tests/answer-revise.test.ts`(받는 답변 규칙·질문 글, 더 찾은 근거 겹침·번호·상한·프롬프트 글, 저장 꼴 읽기·고쳐 쓰는 중 5분, 차지 → 찾기 → 모델 요청 꼴 → 기록 → 숫자 확인 → 저장, 한 번만·고쳐 쓰는 중 409·오래된 표시 다시 차지, 남의 답·도구/첨부 답 거절·한도는 차지 전, 비서 권한·문서 찾기 꺼짐, 차지 경쟁, 찾기·모델 실패와 빈 답은 차지 풀기, 저장 실패, 다음 턴 이력, 화면 단추·고쳐 쓴 답, 라우트·감사 표시 연결).
