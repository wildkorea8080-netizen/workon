# 07. Claude Code 구현 순서

## 운영 방식

각 단계는 수정 파일·실행 검증·남은 의존성을 장부 `docs/workon-rebuild/IMPLEMENTATION_STATUS.md`에 기록한다. ‘설계 완료’, ‘코드 구현’, ‘자동 테스트’, ‘실제 파일 검증’, ‘스테이징 확인’, ‘운영 반영’을 구분한다. 체크리스트만 고치고 구현을 완료했다고 하지 않는다.

여러 프레임워크·DB·모델을 동시에 바꾸지 않는다. 현재 TypeScript·Next.js·Supabase 구조를 기본으로 실제 파일 단위의 서비스를 추가한다. 새 경로는 제안이며 기존 코드 구조와 충돌하면 변경 사유를 기록하고 조정한다.

## P0. 코드 확인·실제 문서 관문

읽을 것: 현재 `CLAUDE.md`, 이 패키지 전체, `src/lib/doc-fill/*`, `builtin-templates.ts`, `generated-files.ts`, `capabilities/document.ts`, `table-engine/*`, `xlsx-export.ts`, 권한 모듈, 최신 마이그레이션.

할 일:

1. 기준 커밋 이후 변경과 현재 미커밋 변경 확인. 사용자의 변경을 덮어쓰지 않음.
2. 기존 타입 검사·테스트·빌드의 실행 결과와 필요한 환경 제약 기록.
3. 양식 파일 inventory·준비 상태 검사 스크립트 추가. 실제 기본 양식 없음이 출시 검사에서 실패하도록 하되 모든 개발 테스트를 불필요하게 막지 않음.
4. 실제 한글 양식 3종을 확보한 경우 기존 `hwpx:probe`와 엔진으로 생성·검사. 없으면 필요한 파일명·필드·검증 환경을 명시하고 독립 구현 진행.
5. 현재 엔진의 지원·비지원 구조와 렌더러 전략을 ADR로 기록.

권하는 산출물: `src/lib/work/documents/*` 어댑터 경계, `scripts/work-template-check.mjs`, 실제 양식 검증 기록, 상태 장부.

완료: 최소 한 개의 실제 지원 양식으로 내용 변경된 HWPX가 생성되며, 양식 공급·렌더링·한글 검증 의존성이 명확하다. XML fixture 검사만 통과했다면 ‘실제 파일 관문 미통과’로 기록한다.

## P1. 작업·권한·내구성 기반

신규 영역 제안:

- `src/lib/work/types.ts`, `schemas.ts`: 입력·상태·문서 값 런타임 검증.
- `src/lib/work/access.ts`, `repository.ts`: 공통 기관·작업 권한과 DB 경계.
- `src/lib/work/runs/*`, `artifacts/*`, `sources/*`: 실행·파일·자료 수명.
- `src/app/api/work/**`, 새 DB 마이그레이션·worker 실행 진입점.
- 개발·스테이징 기동 문서, 필요한 환경변수 이름을 기존 config 경계에 추가.

할 일: 05번 문서의 스키마·멱등 실행·lease·checkpoints·signed upload/download를 구현한다. 큐 표만 만들고 실제로 누가 작업을 처리하는지 빠뜨리지 않는다. 초기 기능은 문서 생성 한 가지라도 브라우저 종료 후 완료·재조회가 가능하게 한다.

완료: A/B 두 기관, 다른 부서·소유자에 대한 실제 DB 교차 테스트 통과. 중복 클릭은 같은 실행 반환. 새로고침·작업자 재시작·Storage 실패를 견디며 레거시 대화 삭제가 새 파일을 지우지 않음.

## P2. 화면 전면 개편과 공문 파일 end-to-end

대상: `src/app/page.tsx`, `src/components/layout/*`, 새 `/tasks`, `/assistants`, `/templates`, `/files`, `/chat`. 기존 인증·기관 브랜딩·관리자 내비게이션 유지.

공통 컴포넌트: WorkShell, WorkflowCard, TaskTable, TaskCreateForm, SourceUploader, TemplatePicker, RunProgress, DocumentWorkbench, DocumentOutline, FieldEditor, ReviewPanel, EvidencePanel, RevisionDiff, ArtifactList, SaveState.

할 일: 기관 양식 선택 → 원자료·필수 정보 → 공문 HWPX 생성 → 내용 편집 → 새 버전·파일 생성 → 다운로드를 연결한다. 모델 미설정은 실제 안내, 테스트 모드는 별도 표기한다. 홈의 가짜 수치·다운로드·진행 타이머를 넣지 않는다.

완료: 실제 브라우저에서 공문 한 건을 처음부터 끝까지 처리. `?conv` 호환, 기존 대화 접근, 접근성·반응형 확인. 편집 화면의 값과 다운로드 파일이 일치함.

## P3. 핵심 3개 업무와 편집·미리보기 완성

워크플로 서비스 제안: `src/lib/work/workflows/{official-letter,collection,regulations}.ts`. catalog의 입력·검토·출력 규약을 구현한다.

- 취합: 기존 표 엔진 어댑터, 항목 대응 확인, 제출·누락·중복·단위·잘림 경고, 통합 XLSX·원본 대응.
- 규정: 기존 NODA·공통자료·법령 커넥터, 기준일·기관·시행일, 근거 검토 메모 HWPX. 모르는 근거는 유보.
- 문서: D2 문단·셀 직접 수정, 선택 범위 AI 제안·적용, 잠금·409·복구. D3는 실제 지원 양식에 한해 구현.
- 렌더러: 실제 HWPX에서 페이지 미리보기·검토 PDF를 생성, 파일 해시·버전 연결. renderer 없음은 사실대로 미완료 표시.

완료: 3개 업무별 실제 파일·검수·수정·재시도 시험 통과. 표·이미지 지원을 주장하는 양식은 D3 관문도 통과.

## P4. 업무 연결과 7개 완성

intake/report/meeting/handover 구현. 회의 입력은 메모·전사문. 업무 결과를 새 작업의 원자료로 가져오는 기능, 자료·버전·권한 재검증, 요구 항목·수치 재사용·누락 검수를 제공한다.

완료: 가상 분기 실적 시나리오에서 접수 → 취합 → 보고서 → 제출 공문의 실제 파일들이 연결됨. 보고서와 공문의 금액·기간이 동일하며 원자료까지 추적됨. 인수인계에 미결 과제·기한이 반영됨.

## P5. 제한된 업무 유형으로 10개 완성

settlement/reply/audit-response 구현. 모두 공통 문서·계산·검수·파일 서비스를 사용한다. 전용 출력 양식과 실패 사례를 가진다. 단순히 프롬프트만 바꿔 같은 텍스트 화면을 반복하지 않는다.

정산은 대사와 누락 점검, 회신은 확인된 사실과 규정에 따른 초안, 감사는 요구 항목·증빙 대응에 한정한다. 지급·행정판단·대외 발송 자동 실행을 추가하지 않는다.

완료: 10개가 각각 catalog의 기본 산출 파일을 만들고, 필수 입력과 검토 규칙을 만족. 미준비 어댑터가 있으면 미완료로 기록하고 작동하는 것으로 표시하지 않음.

## P6. 기관 운영·이전·출시 자료

기존 관리 화면에 양식·워크플로 설치·품질·실패 관리·성과를 추가한다. 과거 데이터 선택 가져오기, 기관 플래그 전환, 운영 장애 복구, 사용법, 배포·롤백 문서를 만든다.

기존 `CLAUDE.md`·서비스 정의서·구조 문서의 변경된 결정과 실제 구현 경로를 갱신한다. ‘우리만의 기능’ 등 경쟁사와 겹치는 오래된 홍보 단정은 검증되지 않은 우위로 반복하지 않는다.

완료: 실제 실행한 검증 결과, 필요한 환경변수 **이름만**, 로컬 기동, 작업자·렌더러 기동, 신규 마이그레이션 적용 순서, 운영 전 남은 항목이 기록됨. 운영 반영 없이 로컬 완료한 상태는 별도 표기.

## 검증 실행 원칙

기존 잠금 파일의 package manager를 사용한다. `npx tsc --noEmit`, `npm test`, `npm run build`와 변경 영역 통합·브라우저 검증을 실행한다. DB 접근이 가능한 승인된 테스트 환경에서 `db:check`·`isolation:check`와 신규 작업 격리 검증을 수행한다. 운영 데이터에 seed·테스트 쓰기를 하지 않는다.

실제 파일 검증은 `hwpx:probe`·패키지 검사·한글 열기/편집/저장·화면 검증을 구분한다. 통과하지 않은 검사를 ‘완료’로 묶지 않는다. 자동 테스트 개수를 늘리는 것보다 사용자 흐름·숫자·권한·수명·실제 파일을 확인하는 검증을 우선한다.
