# 06. 데이터 보존·전환·배포

## 원칙

현재 서비스 화면은 크게 바꾸지만 사용자·기관·기존 대화·자료·비서 설정·사용량을 삭제하지 않는다. 운영 DB의 실제 적용 버전은 저장소 파일 개수로 판단하지 않는다. 새 스키마는 확장 → 양쪽 코드 호환 → 데이터 검증 → 화면 전환 순서로 배포한다.

## M0. 현황·기준선

- 현재 git HEAD·변경 파일, 잠금 파일·Node 환경, 마이그레이션 적용 내역과 주요 트리거를 확인한다.
- `.env` 값을 출력하지 않고 개발 환경에서 필요한 값의 존재만 확인한다. 운영 키를 로컬 파일이나 문서에 복사하지 않는다.
- 실제 기본 양식·Storage 기관 양식·NODA 연결·현재 계약·사용량 규약을 확인한다.
- 데이터 건수·관계·대표 기능을 기록한다. 현재 테스트 결과는 실행해 기록하고 옛 문서의 건수를 재사용하지 않는다.
- 현재 프로그램을 돌아가게 하는 방식과 실제 배포 환경을 확인한다. 변경 전 복구 경로와 백업 복원 검증을 준비한다.

## M1. 추가만 하는 마이그레이션

분석 시 최신 파일은 0033이다. 이후 변경이 없음을 확인한 경우에만 0034부터 사용하고, 새 번호가 있으면 그 뒤를 쓴다. 기존 0028·0032의 수동 적용 조건을 변경하지 않는다.

기관·부서·사용자 관계가 있는 신규 테이블과 인덱스·FK·정책·필요 RPC를 추가한다. 현재 키 체계와 맞춘다. 대량 데이터에 인덱스를 만들 때 락·시간을 확인하고 배포 절차에 반영한다. 운영 코드가 아직 없는 테이블을 읽지 않는 상태에서 먼저 스키마를 추가한다.

새 버킷·경로를 쓸 경우 기본 비공개·정책을 검증한다. 기존 버킷의 공개 범위를 바꾸지 않는다. 개발 DB 또는 스테이징에서 마이그레이션 적용·기존 기능·기관 격리·되돌리기 가능성을 확인한다.

## M2. 공식 업무 10개 설치

이름 기준 중복 검사만 사용하지 않는다. `workflow_installations`의 고정 key를 기준으로 멱등 설치한다. 기관마다 연결된 agent·양식·승인 버전을 기록한다. 기존 관리자·직원이 수정한 비서를 이름이 같다는 이유로 덮어쓰지 않는다.

새 공식 비서를 만들 때 기존 `saveAgentSettings`/`save_agent` 등 버전·감사 경로를 따른다. 기존 프리셋은 자동 삭제하지 않는다. 기존 공식 비서가 적합하면 관리자에게 연결 후보를 제시하고, 그렇지 않으면 새 비서를 별도로 설치한다. 양식·기능 준비가 안 된 비서는 공개 준비 상태로 둔다.

미리보기 가능한 dry-run 결과에 생성·연결·보존·충돌·누락 양식을 표시한다. dry-run은 실제 행이나 외부 보관함을 만들지 않는다. 운영 적용 전에 검토 가능한 차이 목록을 만든다.

## M3. 직원 화면 전환

기관 단위 기능 플래그로 업무 홈을 활성화한다. 기존 대화는 `/chat`로 옮겨 계속 접근 가능하게 한다. `/?conv=...`, 공유 링크, `/dashboard`, 기관 로그인 주소, 관리자·슈퍼관리자 경로의 호환을 확인한다.

플래그는 화면만 바꾸는 값이 아니라 서버 API의 준비·기관 허용 상태와 일치해야 한다. 신규 기능을 끈 기관은 새 작업을 시작하지 못하게 하되 이미 만든 결과의 접근·다운로드는 정해진 정책에 따라 유지한다.

## M4. 기존 결과물 가져오기

기존 `generated_files`는 원래 수명과 소유자 정책을 유지한다. 사용자가 선택한 결과만 새 작업으로 복사한다. 복사 중 원본이 삭제되면 실패로 안내하고 반쯤 생성된 행·객체를 정리한다. 복사된 새 파일은 원본 대화의 CASCADE와 독립적이어야 한다.

기존 `chat_attachments`·양식 원본을 가져올 때도 권한과 기관·해시를 확인한다. Storage 경로만 연결해 TTL 정리나 다른 업무의 삭제에 종속시키지 않는다. 가져온 이력과 원본 참조는 남기되 원문 공유 범위를 넓히지 않는다.

## M5. 배포 관문

스키마 → 준비된 작업자·렌더러 → 호환 API → 플래그 꺼진 UI → 대표 기관 실증 → 기관별 활성화 순으로 한다. 배포 서버에 양식 파일이 실제 포함되는지 확인한다. 현재 `next.config.mjs`는 `/api/chat`에만 양식 추적 포함을 설정하므로 새 생성 경로·worker의 양식 공급 방식을 함께 수정한다.

원문·첨부 발췌가 기존 Claude 호출로 전송될 수 있는 사실과 NODA 문서 처리 경로를 구분한다. 국내 처리·완전 폐쇄망·인증 완료라고 검증 없이 표시하지 않는다. 새 렌더러를 붙이면 그 데이터 경로·보존·접근·라이선스를 기록한다.

운영에서 실패가 증가하면 플래그로 새 실행을 중지하고 기존 UI를 복구한다. 새로 만든 작업·파일은 보존하고 읽기 경로를 유지한다. DB 추가 테이블을 즉시 DROP하는 것을 기본 롤백으로 삼지 않는다. 이미 작성된 새 자료를 옛 대화로 억지로 되돌리지 않는다.

## 운영 변경의 경계

사용자는 Claude Code로 구현할 수 있게 해 달라고 요청한 상태다. 이번 패키지는 자동 운영 배포·본 DB 마이그레이션·기존 자료 영구 삭제·새 유료 서비스 계약을 승인한 문서가 아니다. Claude Code는 로컬·테스트 환경 구현과 검증·배포 자료를 끝낸 뒤 실제 운영 변경이 필요한 부분을 구체적으로 보고한다. 반복적인 구현 선택·로컬 편집마다 확인을 요청하지 않는다.
