## 0. 한 줄

**WORKON을 기반으로**, 웍스AI·Alli Works에서 **공공기관 심사에 유리한 기능만** 골라 넣고,
문서를 읽고 찾는 층을 **NODA**로 바꿔 「문서 본문이 국내를 벗어나지 않는」 구조를 만든다.

벤치마킹은 **끝났다.** 두 서비스의 기능은 공개 자료에서 전부 뽑았고, 이제부터는 구현이다.
REA는 설치형 앱을 손에 넣었을 때만 쓰는 보조 도구이지 이 계획의 전제가 아니다(7절).

## 2. 벤치마크 결론 — 무엇을 가져오고 무엇을 안 가져오나

두 서비스는 범주가 다르다. **웍스AI**는 "모든 AI를 계정 하나에"(종량제·셀프서비스·기능 69종),
**Alli Works**는 엔터프라이즈 RAG 플랫폼(온프레미스·에어갭·SOC2·금융). WORKON은 웍스AI의 자리를
겨냥하면서 Alli의 보안 논리를 가져와야 한다 — **공공기관 납품은 폭이 아니라 「어디서 도는가」로 결정된다.**

### 가져올 것 (공공기관 기준으로 걸러서)

| 기능 | 출처 | 왜 |
|---|---|---|
| **업로드 결재** — 결재자 승인 뒤에만 AI에 쓰임 | 웍스 드라이브 | 공공기관 결재 문화 그대로 |
| **공공데이터 커넥터 6종** | 웍스 21종 | 우리 4종과의 격차를 바로 좁힘. 틀이 있음 |
| **스마트 라우팅** — 난이도별 모델 자동 배정 | 웍스 | 종량제·예산 통제와 직결 |
| **워크플로우 예약** — 아침 브리핑·입찰 모니터링 | 웍스 | 입찰 모니터링은 공공 수요 확실 |
| **원문 위 출처 하이라이트** · **답변 자기검증** | Alli | NODA가 이미 줌 (`/view`·`/verify`) |
| 텍스트 추출 → 엑셀 · 문서 작성 목차 인식 | 웍스·senGPT | NODA 덕에 작아짐 |
| 대화 목록 접기 · 화면 내 사용법 링크 | 웍스 | 작음 |

### 안 가져올 것 — 이유를 적어 둔다

| 기능 | 이유 |
|---|---|
| 멀티 프로바이더 100종 | 사업자가 늘면 보안성 검토에서 소명할 곳이 는다. 다만 **「데이터가 어디서 처리되느냐」**는 질문에는 답해야 한다 → NODA로 문서 처리를 국내에 두는 것이 그 답(3절) |
| 이미지·비디오 생성 · 브랜드 모니터링 · 슬라이드 생성 · 프로덕트 스튜디오 | 새 업체 필요. 공공 심사에서 설명할 곳만 는다 |
| 회의록 STT | 새 업체 필요 |
| 데스크톱 에이전트 · 코딩 에이전트 | 기관 PC는 설치 권한이 잠겨 있고 망분리면 못 씀 |
| M365·OneDrive 동기화 · 조직도 자동 연동 | 공공기관은 내부망·자체 EDMS. 조직도 연동은 저쪽도 유가 200만원 |

### 우리가 앞선 것 — 지킨다

문서를 **우리** 저장소에 둠(웍스AI는 OpenAI에 저장) · 시스템 레벨 인용 규칙(개인 비서에도 적용) ·
질문 원문 열람 통제 · 격리 실측 · 부서 계층이 워크스페이스와 안 갈라짐 · HWP 표 복원.

## 3. 구조 — 세 가지의 역할

```
┌─────────────────────────── WORKON (Next.js · Vercel · Supabase) ──────────────────────────┐
│ 사용자·기관·부서·권한  비서·대화  LLM 호출(Anthropic)  모델 정책  한도·과금  감사  화면      │
│                                                                                            │
│   업로드 ──결재──▶ NODA /documents/upload?tenant={기관}                                     │
│   질문   ────────▶ NODA /context (principal=agent-…) ──▶ 발췌 ──▶ Claude ──▶ 답            │
│   답     ────────▶ NODA /verify ──▶ 근거에 없는 숫자 표시                                   │
└────────────────────────────────────────────────────────────────────────────────────────────┘
                                   │
┌────────────────── NODA (인천 · Python · 자체 서버) ──────────────────┐
│ 파일 → 글·표·구조 + 근거(쪽·좌표)  OCR  보관·색인·ACL  근거 묶음  검증 │
│ LLM 없음 · 개인정보 탐지 없음 (NODA 규칙 4·9)                         │
└──────────────────────────────────────────────────────────────────────┘

REA ─ 벤치마크 대상의 설치형 앱을 손에 넣었을 때만 쓰는 분석 도구. 런타임 구성요소 아님.
```

### 데이터 흐름이 바뀌는 것이 이 계획의 핵심 이득

| | 지금 | NODA 이후 |
|---|---|---|
| 문서 본문 | Voyage(미국) 임베딩 + Anthropic(미국) OCR로 **전문**이 나감 | **국내(인천)에서만** 처리 |
| 해외로 가는 것 | 본문 전문 + 질문 | 질문 + **발췌(기본 4,000자)** |
| 검증 | 없음 | 국내에서 `/verify` |

보안성 검토 답변이 "본문이 두 미국 사업자에게 간다"에서 **"본문은 국내에서만 처리되고 발췌만 나간다"**로 바뀐다.

### Voyage AI는 쓰지 않는다 (2026-10-14 결정)

임베딩과 검색은 **NODA가 전담**한다(NODA는 국내 서버에서 `e5-small` 뜻 벡터를 직접 돌린다).
해외 하위 처리자가 **Anthropic·Voyage 둘 → Anthropic 하나**로 줄고, 그 하나에도 문서 전문이 아니라 발췌만 간다.

| 바뀌는 것 | 전 | 후 |
|---|---|---|
| 이중 운용 | Voyage·pgvector 경로를 남겨 NODA와 맞대어 돌림 | **없음.** B1에서 Voyage 경로를 걷어낸다 |
| B0 비교 | Voyage 경로와 NODA를 같은 질문으로 맞댐 | NODA를 **절대 기준**(분리 구간·쪽 정확도·`/verify`)으로 잰다. 8월 Voyage 실측은 참고 기준선일 뿐 |
| 기존 문서 | 그대로 두고 기관별 전환 | Storage 원본을 NODA로 **재적재**(`scripts/migrate-to-noda.mjs`) 뒤 임베딩 컬럼 정리 |
| 제거 시점 | B4에서 「판단」 | **B1의 확정 단계** |

**전환 전까지는 운영의 Voyage 코드가 그대로 돈다.** 지금 업로드는 전부 Voyage로 임베딩하므로 B1 전에 떼면
업로드가 멈춘다. 그 사이 Voyage 경로에는 **새 작업을 얹지 않는다.**

걷어낼 자리(실측): `src/lib/embeddings.ts` · `document-processor.ts`의 `getEmbeddings` · `rag.ts` ·
`/api/qna`의 질의 임베딩 · `config.ts`의 필수 `VOYAGE_API_KEY` · 슈퍼관리자 API 키 화면의 Voyage 항목 ·
`.env.example` · `tests/pdf-ocr.test.ts`의 임계값 고정(0.25는 voyage-3 분포로 정한 값이라 NODA에서는 뜻이 없다).
웍스AI의 「국경을 안 넘는다」(K-오픈웨이트)에 LLM을 바꾸지 않고 답하는 길이다.

### REA — 조건부

웍스AI Desk는 **사내 베타(담당자 통해 설치 파일)**, 알리 데스크톱은 배포 경로 비공개. 둘 다 지금 받을 수 없다.
받게 되면: ① 약관의 역공학 금지 조항 확인 → ② `analyze-javascript-application`으로 정적 분석 →
③ 「대화·파일이 이 컴퓨터에만 남는다」 주장 검증 → ④ 관찰 노트(코드 인용 없음). **안 받아도 계획은 안 바뀐다.**

## 6. 리스크

| 리스크 | 대응 |
|---|---|
| Vercel 함수 시간 제한 vs NODA 스캔 파싱 수십 초 | 업로드 비동기(202 + 폴링). B0에서 실측 |
| NODA 단일 VM(4GB · 동시 파싱 2 · 가득 차면 503) | 재시도 + 「읽는 중」 표시. NODA가 내려가면 `/api/chat`은 「문서 검색 결과 없음」 분기 — 조용히 빈 손을 주지 않는다 |
| 깨진 ACL = 기관 전체 검색 잠금 | 옳은 설계. WORKON 생성기를 순수 함수 + 테스트로 고정, 쓰기 전 검증 |
| 뜻 벡터가 안 켜진 채 켜진 것처럼 보임 | B0 `/health` 확인 · 운영 경보 |
| OCR 오차 0.19 | 화면 배지 필수. 숨기면 「2,000톤」이 다시 난다 |
| 문서가 두 곳(Supabase + NODA) | 소명 문서 갱신 · 파기 4곳 동시 |
| 스마트 라우팅의 품질 저하 | 규칙 기반으로 시작, 비서별 고정 허용, **측정 전에 절감 수치 주장 안 함** |
| 커넥터 키 6종 운영 환경 누락 | 키 없으면 조용히 빠짐 → `connector:probe` 배포 후 실행 규약 |
| **NODA가 유일한 검색이 된다** (Voyage 제거로 대체 경로 없음) | NODA가 내려가면 문서 검색 전체가 멈춘다. `/api/chat`은 「문서 검색 결과 없음」 분기로 가고 화면에 상태를 띄운다. 단일 VM(4GB)이라 증설·이중화를 B1 전에 결정 |
| **뜻 벡터가 꺼진 채 켜진 것처럼 보임** — 그리고 지금은 확인할 칸도 없음 | `/health`에 벡터 상태가 없다(실측). NODA가 칸을 더하기 전까지는 `/search` 결과의 `found_by`로 본다(키 필요) |
| Track A가 기존 격리·한도 규약을 빠뜨림 | `route-auth`·`usage-limit` 테스트가 핸들러 전수를 봄 — 신규 라우트도 자동 검사 |
