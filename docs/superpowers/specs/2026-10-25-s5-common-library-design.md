# S5 — 공통 자료실 설계

**날짜**: 2026-10-25
**근거**: 서비스 정의서(`2026-10-14-workon-service-definition-design.md`) 5절·9절
**NODA 계약**: `https://api.readlayer.kr/openapi.json` (2026-10-25 읽음) — `/context`·`/verify`는 **보관함 하나**(`tenant` 한 개)만 받는다
**앞선 과제**: S4-a·S4-b(참고 문서를 NODA로, 비서마다 보관함, 읽기 상태 기계, 웹훅)
**결정 방식**: 사용자가 질문 없이 진행을 지시(2026-10-25). 아래 결정은 모두 **설계자 판단**이고, 정의서 5절과 S4 구조에서 끌어냈다

---

## 1. 왜 만드는가

기관 유형마다 **모든 기관이 똑같이 쓰는 정부 기준 문서**가 있다 — 지방공기업 예산편성기준·회계기준·경영평가 편람,
협회·재단의 보조금 관리 지침·정산 안내. 법령 DB에 없어서 법령 커넥터로는 못 찾고, 지금 구조에서는 기관마다 같은 파일을
자기 비서에 따로 올려야 한다(기관 수 × 비서 수만큼 사본, 판이 바뀌면 전부 다시).

운영자가 **한 번** 넣으면 그 유형의 모든 기관 비서가 함께 찾게 한다. 출처에는 `[공통]`과 기준 연도가 붙어,
직원이 "이건 우리 규정이 아니라 정부 공통 기준(2026년 판)"임을 알 수 있다.

## 2. 목표 · 비목표 · 실패 기준

### 목표
1. 슈퍼관리자(운영자)가 공통 문서를 올리고·바꾸고·지운다. 문서마다 **기관 유형 · 이름 · 기준 연도 · 이용 조건 확인 기록**을 적는다
2. 문서 찾기 능력(`doc_search`)이 켜진 비서는 **자기 보관함 + 그 기관 유형의 공통 보관함**을 함께 찾는다
3. 출처 칩·근거 창·모델이 보는 근거 머리에 `[공통]`과 기준 연도가 붙는다(예: `[공통] 예산편성기준(2026) · p.12`)
4. 새 판을 올리면 옛 판은 "지난 판"이 되어 **검색에서 빠진다**(NODA 사본을 지움). 기록은 남는다
5. 기관 규정과 공통 기준이 다르면 **둘 다** 보이게 한다 — 어느 쪽이 우선인지는 직원이 판단한다(정의서 5.2)
6. 읽기·삭제·장애 처리는 S4와 **같은 규칙**(비동기 넣기·읽는 중·10분 포기·웹훅·삭제 순서 NODA → DB → 원본·NODA 장애면 답하지 않음)

### 비목표 (S5에서 안 함)
- **한 문서를 여러 유형에 걸기** — 문서 하나는 유형 하나. 두 유형에 필요하면 운영자가 두 번 올린다(3절)
- 기관 관리자 화면의 공통 문서 목록 — 직원·관리자는 답의 `[공통]` 칩으로 안다. 필요해지면 읽기 전용 목록을 따로 만든다
- 비서마다 공통 자료실 끄기 — `doc_search`가 켜진 비서는 모두 찾는다. 유사도 하한(0.80)이 엉뚱한 근거를 거른다. 끌 필요가 실제로 생기면 `doc_search` 설정에 옵션을 더한다
- 연간 갱신 **일정표** 화면 — 목록에 기준 연도를 보이고 연도순으로 정렬하는 것까지만
- NODA 문서 단위 권한(`POST /access`·`X-NODA-Principal`) — 유형별 보관함으로 범위가 닫혀 필요 없다
- 기본 비서 5종·도입 흐름 — S6

### 실패 기준
- 다른 유형의 공통 문서가 근거로 섞임(예: 협회단체 기관에 지방자치단체 공통 기준)
- 지난 판 조각이 근거로 나옴
- 공통 기준 조각이 기관 자료인 것처럼 보임(`[공통]` 표시 누락)
- 공통 보관함 장애 중에 기관 문서만으로 답하면서 "문서에서 찾지 못했습니다"라고 단정(공통 문서에 답이 있었을 수 있다)

## 3. 보관함 — 기관 유형마다 하나

| | |
|---|---|
| 유형 | `organizations.type`(이미 있음, 슈퍼관리자 기관 화면의 `ORG_TYPES`: 중앙행정기관·지방자치단체·공공기관·교육기관·협회단체·일반기업). 정의서 5.1의 '지방공기업'·'협회·재단'은 운영자가 이 중에서 고른다. `type`이 비었거나 목록 밖이면 공통 자료실이 없다 |
| 보관함 이름 | `workon-c-{유형 열쇠}` — 열쇠는 코드의 고정 표 하나(`central`·`local`·`public`·`edu`·`assoc`·`company`). **서버가 유형으로만 만든다**(요청값으로 받지 않음, 표 밖이면 던짐). 비서 보관함(`workon-a…`)과 겹치지 않는다 |
| NODA 파일 이름 | `{common_document_id}__{이름}({기준 연도}){원래 확장자}` — 예 `…__예산편성기준(2026).pdf`. 모델이 보는 근거 머리 줄에 이름과 연도가 그대로 실린다. 이름은 운영자가 쓴 글이라 파일 이름에 못 쓰는 글자(`/ \ : * ? " < > |`·제어·서식 글자)를 빼고 80자에서 자른다. 확장자는 원본 그대로(NODA가 확장자로 읽는다) |
| 왜 유형마다 따로 | `/context`·`/verify`가 보관함 하나만 받는다. 한 보관함에 몰고 `/access`로 나누는 길도 있지만, 권한 규칙이 깨지면 보관함 전체가 잠기고(NODA 동작) 지금 계약에서 머리글 의미를 실측하지 않았다. 유형별 보관함은 S4의 '보관함 = 범위'를 그대로 쓴다 |

## 4. 데이터

마이그레이션 **0033** — 표 `common_documents`(코드 배포 **전**에 적용; 코드가 이 표를 읽는다).

| 칸 | 뜻 |
|---|---|
| `id` uuid | |
| `org_type` text NOT NULL | 3절의 유형(한글 그대로). CHECK로 여섯 값만 |
| `title` text NOT NULL | 문서 이름(예: 예산편성기준) |
| `edition_year` int NOT NULL | 기준 연도. CHECK 2000~2100 |
| `usage_terms` text NOT NULL | 이용 조건 확인 기록(예: `공공누리 1유형 · 2026-10-25 확인`). 비우면 올리지 못한다 |
| `file_name`·`file_type`·`size_bytes`·`storage_path` | 원본(`documents` 버킷 `common/{유형 열쇠}/{id}.{확장자}`) |
| `noda_status` | `reading`·`ready`·`failed`·`unreadable`·`deleting`·`retired`(지난 판 — NODA 사본을 지웠음) |
| `noda_reason`·`noda_filename`(유일)·`noda_doc_id`·`noda_read_started_at`·`noda_last_attempt_at`·`noda_read_at` | S4 `documents`와 같은 뜻 |
| `replaces_id` uuid NULL | 이 문서가 대신하는 옛 판 |
| `retired_at` timestamptz NULL | 지난 판이 된 때 |
| `uploaded_by` uuid | 올린 슈퍼관리자(`users.id`, `is_super_admin`) — `getSuperAdminFromRequest`가 준 id |
| `created_at`·`updated_at` | |

- 기관·부서 칸이 **없다** — 유형 단위 자료다. 그래서 `visibilityFilter`·기관 트리거 대상이 아니다
- 같은 유형에서 **현재 판**(`retired_at IS NULL`)은 이름마다 하나만 — 부분 유일 인덱스 `(org_type, title) WHERE retired_at IS NULL AND noda_status <> 'deleting'`. 새 판은 `replaces_id`로 옛 판을 가리키고, 확인 단계에서 옛 판을 지난 판으로 돌린다(6절)
- 운영자의 올리기·바꾸기·지우기는 `super_admin_logs`에 남긴다(이름·유형·연도·이용 조건 — 공개된 정부 문서 이름이라 남겨도 된다)

## 5. 대화에서 찾기

### 5.1 흐름

`doc_search` 능력의 preflight·prepare가 넓어진다.

```
비서 문서 행 + (기관 유형 → 그 유형의 공통 문서 행) 조회
→ 찾을 곳: 비서 보관함(ready 문서가 있으면) · 공통 보관함(ready 현재 판이 있으면)
→ 둘 다 없으면 지금처럼 NODA를 부르지 않는다
→ 찾을 곳마다 /context를 **동시에** 부른다
   - 한 곳만: budget 4000(지금과 같음)
   - 두 곳: 비서 3000 + 공통 2000 (모델에 가는 발췌가 7,000자까지 늘지 않게 — 비용·정의서 6절 '발췌만 나간다')
→ 하나라도 실패하면 S4와 같은 503 documents_unavailable (대화를 만들기 전에)
→ 근거 맞추기: 비서 근거는 S4 그대로, 공통 근거는 공통 문서 행과 따로 맞춘다(5.3)
→ 근거 묶음 합치기(5.2) → 프롬프트(5.4)
```

- 기관 유형은 `organizations.type`을 그 턴에 읽는다(유형을 바꾸면 다음 질문부터 새 유형). 조회 실패는 문서 행 조회 실패와 같게 닫는다(503)
- 비서에 자기 문서가 없어도 공통 문서가 있으면 찾는다 — `doc_search`가 켜진 비서라면
- 공통 문서 조회가 실패하면 닫는다(503). 열어 두면 공통 문서에 답이 있는 질문에 "찾지 못했습니다"라고 단정할 수 있다(실패 기준 4)

### 5.2 번호 합치기

두 근거 묶음은 각자 `[1]`부터 번호를 단다. **비서 묶음을 먼저 두고 공통 묶음의 번호를 비서 묶음의 가장 큰 번호만큼 민다**
— 머리 줄(`^\[(\d{1,3})\] `)의 번호와 그 묶음 `sources[].n`을 함께. 모델이 보는 번호, 화면 칩 번호, `source_references.chunks[].n`이 같은 번호다.
프롬프트에는 두 묶음을 다른 머리 아래 둔다: `참고 자료(이 기관 문서):` / `참고 자료(공통 기준 — {유형} 공통, 정부 기준 문서):`.

### 5.3 공통 근거 맞추기

| 공통 근거의 문서 id | 처리 |
|---|---|
| 이 유형의 `ready` 현재 판 행 | 조각(출처 `[공통]`) |
| 이 유형의 행이지만 지난 판·읽는 중·실패·못 읽음·지우는 중 | 그 조각만 조용히 뺀다(지난 판은 사본을 지웠으니 원래 오지 않아야 한다) |
| 다른 유형의 행 | **섞임** — 비서 근거까지 그 턴 근거 전체를 버리고 `system_logs` critical(`security`) |
| 행이 어디에도 없음·문서 id를 못 읽음 | **고아** — 공통 근거만 버리고 그 공통 보관함의 사본을 지운다(1.5초까지만 기다림), warning. 비서 근거는 쓴다 |

운영 기록에는 파일 이름을 남기지 않는다(문서 id·개수·유형 열쇠만) — S4와 같다.

### 5.4 프롬프트 · 인용 규칙

자료 인용 규칙(`CITATION_RULES`)에 공통 자료가 있을 때만 두 줄을 더한다.

- `공통 기준 자료는 정부가 정한 기준 문서입니다. 인용할 때는 문서 이름과 기준 연도를 함께 밝히세요(예: 예산편성기준(2026)).`
- `이 기관 문서와 공통 기준이 서로 다르게 말하면 한쪽을 고르지 말고 둘 다 보여 주고, 어느 것을 따를지는 기관 규정과 담당자가 판단한다고 안내하세요.`

'관련 문서 없음' 문구(`NO_RESULT`)는 "이 비서에 연결된 문서" → "이 비서의 문서와 공통 기준 자료"로 넓힌다(공통 보관함도 찾은 턴만).

### 5.5 답변 검증(`/verify`)

`/verify`는 보관함 하나만 받는다.

| 그 턴의 근거 | 검증 |
|---|---|
| 비서 근거만 | 지금처럼 비서 보관함 |
| 공통 근거만 | 공통 보관함(번호를 밀지 않았으니 `[n]`이 맞다) |
| 둘 다 | **부르지 않는다** — 한 보관함에 맞춰 보내면 다른 쪽 번호가 '없는 번호'로 거짓 기록된다. `source_references.verify` 칸이 없을 뿐 답·저장은 그대로. 보이는 숫자 확인(로컬 대조)은 두 묶음을 다 본다 |

NODA에 "여러 보관함 근거를 한 번에 검증하는 길"을 문의 항목으로 남긴다(10절).

## 6. 운영자 화면 — `/super/common-library`

슈퍼관리자 포털에 메뉴 하나. 인증은 `super_token`(`getSuperAdminFromRequest`), 모든 핸들러마다.

| 화면 요소 | 동작 |
|---|---|
| 유형 탭 | 여섯 유형. 탭마다 현재 판 목록(이름·기준 연도·상태 칩·올린 때·크기) + 접힌 '지난 판' |
| 올리기 | 파일 · 유형 · 이름 · 기준 연도 · 이용 조건 확인 기록(필수) · '바꿀 옛 판'(같은 유형의 현재 판 중 선택, 없으면 새 문서) |
| 상태 | S4 문서 화면과 같은 칩(읽는 중·읽음·실패·못 읽음·지우는 중) + 실패 시 '다시 시도'. 목록이 읽는 중 행을 NODA 목록과 맞추고 멈춘 행 하나를 다시 건다 |
| 지우기 | 현재 판·지난 판 모두. 순서 NODA → DB 행 → 원본. NODA 실패면 `deleting`으로 남기고 다시 지우라고 안내 |

API(`/api/super/common-documents/…`): 목록(+맞추기) · 올리기 주소 발급 · 확인 · 읽기 · 삭제.
올리기 검사(형식·크기·위험한 이름·확장자로만)는 `document-upload.ts`의 검사를 같이 쓴다. 크기 상한은 `MAX_UPLOAD_BYTES`.

**판 바꾸기**: 새 판의 확인이 끝나 읽기를 걸 때가 아니라 **새 판이 `ready`가 되는 순간**에 옛 판을 지난 판으로 돌린다
(옛 판 NODA 사본 삭제 → `retired`·`retired_at`). 새 판이 읽기에 실패하면 옛 판이 그대로 검색되게 하려는 것이다.
옛 판 사본 삭제가 실패하면 옛 판은 `deleting`으로 두고(검색에서는 행 상태로 이미 빠진다) 화면에서 다시 지울 수 있다.
새 판이 `ready`로 바뀌는 곳은 읽기 라우트·목록 맞추기·웹훅 세 곳이다 — 세 곳이 같은 함수를 부르게 한다.

## 7. 읽기 상태 · 웹훅

- S4의 읽기 상태 기계(`readDocument`·`reconcileReading`·`decideReadState`, 두 시계, 차지, 비동기 202, `failed[]`·`readable:false` 처리)를 **공통 문서에도 그대로** 쓴다.
  표와 보관함을 고르는 부분만 갈라지게 일반화한다(어떻게 나눌지는 계획에서). 판정 값(2분·10분·5개 보관함·4초/5초)은 같다
- 웹훅(`/api/noda/webhook`): `tenant`가 `workon-c-{열쇠}`면 공통 문서 행을 찾는다. 행의 유형 열쇠와 `noda_filename`이 맞을 때만 바꾼다(아니면 security warning). 나머지 규칙은 S4와 같다
- `noda:purge-deleted`처럼 운영자 스크립트는 만들지 않는다 — 공통 문서는 화면에서 지운다

## 8. 화면 — 출처 표시

- `source_references.chunks[]`에 `scope: 'common'`과 `edition_year`를 더한다(비서 근거는 칸을 두지 않는다 — 옛 메시지와 같은 꼴)
- 출처 칩: `[1] [공통] 예산편성기준(2026) · p.12`. 근거 창 머리에 `공통 기준 · 지방자치단체 · 2026년 판`
- 문서 이름은 공통 문서 행의 `title`(NODA 파일 이름의 `{id}__`를 떼고 확장자를 뺀 글이 아니라 행의 값)
- 화면 코드는 `scope`가 없으면 지금처럼 그린다

## 9. 배포 순서

1. 마이그레이션 0033 적용(사용자) — **코드 배포 전**
2. 코드 푸시(배포 확인)
3. 슈퍼관리자 화면에서 공통 문서 하나를 올려 '읽음'까지 확인
4. 그 유형 기관의 문서 찾기 비서에서 공통 문서 내용을 묻고 `[공통]` 칩·기준 연도·근거 창 확인. 다른 유형 기관에서는 안 나오는지 확인
5. 새 판을 올려 옛 판이 '지난 판'이 되고 옛 내용이 더 안 나오는지 확인

## 10. 남는 것 · 문의

| 항목 | 처리 |
|---|---|
| 여러 보관함 근거를 한 번에 `/verify` | NODA 문의. 그 전까지 섞인 턴은 검증 기록 없음(5.5) |
| 한 문서를 여러 유형에 | 비목표. 운영자가 유형마다 올린다 |
| 공통 문서별 이용 조건 실제 확인 | 사람(정의서 10.3). 화면은 기록 칸만 강제한다 |
| 유형 목록이 거칠다(지방공기업이 '공공기관'에 섞임) | 유형을 더 나누려면 `ORG_TYPES`·CHECK·열쇠 표를 함께 늘린다 |

## 11. 시험

단위 시험이 고정할 것(실서버 확인은 9절):

- 공통 보관함 이름: 유형 → 열쇠 고정 표, 표 밖·빈 유형은 던짐, 비서 보관함 꼴과 안 겹침. NODA 파일 이름 다듬기(못 쓰는 글자·80자·확장자 유지·연도)
- preflight: 비서·공통 각각 ready 유무에 따른 호출 수(0·1·2), 하나라도 실패면 503, 유형 없는 기관은 공통 안 찾음, 공통 조회 실패도 503
- 번호 합치기: 공통 머리 줄·`sources[].n`이 함께 밀림, 비서 묶음 먼저, 근거 창 원문이 새 번호로 이어짐
- 공통 근거 맞추기: 현재 판만 조각·지난 판 제외·다른 유형은 섞임(전체 버림·critical)·고아는 공통만 버리고 사본 삭제
- 프롬프트: 공통 자료가 있을 때만 두 줄, 머리 둘
- `/verify`: 비서만·공통만·둘 다(안 부름)
- 판 바꾸기: 새 판 ready에서만 옛 판 retired·사본 삭제 실패는 deleting·새 판 실패면 옛 판 그대로, 세 경로가 같은 함수
- 웹훅: 공통 보관함 알림이 그 유형의 행만 바꿈, 다른 유형·다른 파일 이름은 기록만
- 운영자 API: 모든 핸들러 슈퍼관리자 검사(`route-auth.test.ts`), 이용 조건 비면 거절, 연도 범위, 유형 밖 거절
- 화면: `[공통]` 칩·연도, `scope` 없는 옛 근거는 그대로
