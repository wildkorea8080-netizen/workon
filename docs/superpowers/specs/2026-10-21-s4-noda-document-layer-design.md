# S4 — 문서 층을 NODA로 교체 설계

**날짜**: 2026-10-21
**근거**: 서비스 정의서(`2026-10-14-workon-service-definition-design.md`) 4.2·6·7·9·10.2절, 재료 `docs/PLATFORM_PLAN_NODA_REA_2026-10.md`
**NODA 계약**: `https://api.readlayer.kr/guide` · `/openapi.json` (2026-10-21 읽음) · NODA 운영자 답(2026-10-21 1차, 2026-10-23 2차 — `min_similarity`·`receiving`·`/parse` 캐시 없음·txt/csv 직접 읽기, 대화 기록)
**앞선 과제**: S1(능력 장치), S3-a·S3-b(첨부·표 합치기·숫자 확인)

---

## 1. 왜 바꾸는가

지금 비서의 참고 문서는 **자체 파서 → Voyage(미국) 임베딩 → pgvector**로 찾고, 스캔 PDF는 **Anthropic(미국)**이 판독한다.
문서 본문 전체가 해외 두 곳으로 나간다. 공공기관 보안성 검토에서 가장 설명하기 어려운 부분이다.

NODA(국내 iwinv 서버)는 읽기·글자 인식·뜻 검색·근거 검증을 서버 안에서 한다(운영자 확인: 문서 본문은 서버 밖으로 나가지 않음,
운영 바깥 연결 0개 실측). 바꾸면:

- 해외로 가는 곳이 **Anthropic 하나**가 되고, 거기 가는 것은 **질문 + 찾은 근거 조각**뿐이다(정의서 6절의 약속)
- 근거에 **쪽·절**이 붙는다 — 공공기관 답변은 "몇 쪽에 있느냐"가 곧 출처다
- 답에 **근거 없는 숫자·인용**을 NODA `/verify`가 잡는다(S3-b의 프로그램 대조와 합쳐 보인다)
- 자체 파서·Voyage·pgvector 검색을 걷어 내 유지할 것이 줄어든다

## 2. 목표 · 비목표 · 실패 기준

### 목표
1. 비서 참고 문서 업로드가 NODA로 간다. 원본은 지금처럼 Supabase에도 둔다(다시 보내기·내려받기용)
2. 대화의 문서 찾기(`doc_search` 능력)가 NODA `/context`로 근거를 받는다. 출처에 쪽·절
3. 답이 끝나면 NODA `/verify`로 검증해 S3-b 숫자 확인과 함께 보인다
4. 문서 삭제가 NODA의 사본·캐시·색인까지 지운다
5. NODA가 잠깐 멈춰도 업로드는 '읽는 중'으로 버티고, 대화는 **근거 없이 답하지 않는다**
6. 기존 문서를 NODA로 옮기고 Voyage 경로를 걷어 낸다
7. 대화 중 첨부한 **스캔 PDF**를 NODA `/parse`로 읽는다(서버에 저장되지 않음)

### 비목표 (S4에서 안 함)
- **부서 전체 검색** — 비서별 보관함 구조(3절)와 맞지 않는다. 필요해지면 따로 설계
- 공통 자료실 — S5
- NODA `/answer`·`/view`의 `llm:true` — 쓰지 않는다(운영자가 운영 서버의 OpenAI 키를 빼 길 자체를 닫을 예정). 답은 WORKON이 Anthropic으로 짓는다
- 첨부 파일 전부를 NODA로 — 표 합치기가 자체 칸 배열에 기대므로 자체 파서를 유지하고, **스캔 PDF만** NODA `/parse`
- NODA 쪽 ACL 규칙 쓰기 — HTTP 길이 없다. 3절의 비서별 보관함으로 대신한다

### 실패 기준
- 근거를 못 찾았는데 문서에서 나온 것처럼 보이는 답
- 다른 비서·다른 기관의 문서 조각이 근거로 섞임
- 삭제했는데 NODA 보관함에 사본·색인이 남음(백업 7일은 예외로 고지)
- NODA가 10초 재시작하는 동안 업로드가 '실패'로 끝나 직원이 파일을 다시 골라야 함

## 3. 보관함 — 비서마다 하나

NODA 키 `workon`은 보관함 `workon`과 `workon-…`만 쓸 수 있다(다른 서비스 보관함은 403).
WORKON의 문서는 **비서 하나에만 붙는다**(`documents.agent_id`; 여러 비서에 올리면 비서마다 행이 따로 생긴다).
그래서 **보관함 = 비서**로 두면 범위 규칙(ACL) 없이 비서별 범위가 닫힌다.

| | |
|---|---|
| 보관함 이름 | `workon-a{agent_id에서 하이픈 뺀 32자}` (예: `workon-a3f2…`) — 이름 규칙은 계획에서 NODA에 맞춰 확인 |
| 기관 격리 | 비서는 한 기관에 속하므로 보관함도 기관을 넘지 않는다. 다른 비서의 보관함 이름은 **서버가 비서 id로만 만든다** — 요청값으로 받지 않는다 |
| 파일 이름 | `{document_id}__{원래 이름}` — 같은 이름 409를 피하고, 문서 행과 1:1로 잇는다 |
| `/context` `principal` | 쓰지 않는다(보관함이 곧 범위) |

**알려진 비용**: 한 파일을 비서 셋에 올리면 NODA에 사본이 셋이다. 지금 DB도 행이 셋이라 같은 모양이다.

## 4. 업로드 — '읽는 중'으로 버티기

NODA 업로드는 **읽기를 끝내고 응답한다**(텍스트 PDF 40쪽 ≈1초, 10MB 스캔 ≈8초, 45MB 그림 많은 자료 ≈2분 15초).
Vercel 함수 안에서 끝까지 기다리면 시간 제한에 걸린다. 그래서 둘로 나눈다.

```
① 원본 올리기 — S3-a 첨부와 같은 길: 서명 주소로 Supabase에 **직접** 올림 → 확인 라우트가 documents 행(noda_status='reading')
   (지금 /api/upload는 multipart로 함수를 거쳐 Vercel 본문 상한 4.5MB에 걸린다. 문서 상한 20MB가 실제로 닿지 않는다 — 설계자 판단)
② POST /api/documents/{id}/read  (화면이 ① 직후 부름, maxDuration 300)
     Supabase 원본 → NODA POST /documents/upload?tenant={보관함}&replace=1 (X-Filename)
     → readable이면 'ready' + 쪽 수·OCR 여부 / readable:false면 'failed' + reason
③ 화면은 '읽는 중' 칩을 보이고 몇 초마다 **문서 목록**(GET /api/documents)을 다시 부른다 — 목록이 상태 맞추기를 한다(상태 조회 전용 라우트는 두지 않는다, 구현 판정 R2)
```

- **항상 `replace=1`로 보낸다.** 시간 제한으로 끊겨도 NODA는 넣기를 끝냈을 수 있다. 그냥 다시 보내면 409다. 같은 파일이면 NODA가 다시 읽지 않아 빠르다
- 502·503·429(`Retry-After` 따름)는 **몇 초 간격으로 1분쯤 저절로 다시 보낸다**
- ② 함수가 시간 제한으로 끊긴 경우: 문서 목록(③)이 `reading` 행을 NODA `GET /documents?tenant=`로 맞춘다(보관함마다 한 번, 한 번에 5개 보관함까지)(NODA는 끝냈을 수 있다). 목록은 읽기를 기다리지 않고 바로 답하며(운영자 확인), 상태는 셋으로 갈린다:

  | NODA 목록 | WORKON |
  |---|---|
  | `documents`에 그 파일 이름 | `ready` |
  | `receiving`에 그 파일 이름(`seconds` = 받은 뒤 지난 초) | `reading` 유지 |
  | 둘 다 없음 | **안 왔음** — 다시 걸기 대상(②를 다시 부름) |

  같은 이름을 바꿔 넣는 중이면 옛 판은 `documents`, 새 판은 `receiving`에 함께 있다 → `receiving`을 먼저 본다(아직 읽는 중).
  NODA는 15분 지난 항목을 `receiving`에서 빼고, 재시작하면 `receiving`을 비운다 → 둘 다 '안 왔음'으로 떨어져 다시 걸린다(`replace=1`이라 안전)
- **함수 시간 제한**: ②는 `maxDuration 300`을 선언한다. 지금 배포 환경이 이보다 짧게 끊어도(Vercel 요금제·설정에 따라 60초) 위 맞추기와 다시 걸기로
  결국 끝난다 — **NODA가 호출자가 끊긴 뒤에도 읽기를 마친다는 전제**에서. 이 전제는 S4-a 실서버 확인에서 큰 문서(45MB 브로슈어)로 잰다.
  운영을 Vercel에서 클라우드 서버로 옮기면(계획됨) 이 제한 자체가 없어진다
- **②를 화면만 믿지 않는다.** 만들기 창은 올린 뒤 바로 닫히고 탭이 닫히면 ②가 불리지 않는다. 문서 목록이 '읽는 중'인 채 2분(`READ_KICK_AFTER_MS`, 마지막으로 NODA에 보낸 때 기준)이
  지난 행을 보면 ②를 다시 건다. 다만 **서버가 직접 걸지 못한다**(Vercel은 응답 뒤 일을 이어 가지 못함) — 목록 응답이 가장 오래된 행 **하나**에 `kick: true`를 달고,
  그 목록을 받은 화면이 읽기 라우트를 부른다. 중복은 읽기 라우트의 조건부 갱신(차지)이 막아 NODA 업로드는 한 번이다(구현 판정 R3).
  **알려진 공백**: 아무도 목록을 열지 않으면 멈춘 행은 다음에 열 때까지 `reading`이다(클라우드 서버로 옮기면 예약 작업으로 바꾼다).
  NODA가 서버 전체에서 한 번에 둘만 읽으므로(`max_parallel: 2`) 남의 긴 읽기 뒤에 기다릴 수 있다 — 그래서 '읽는 중'을 **최대 10분**(`READ_GIVE_UP_MS`, 이번 읽기 시작 기준)까지 유지하고,
  그 뒤 `failed`(`읽기가 너무 오래 걸려 멈췄습니다. 다시 시도해 주세요.`)로 바꿔 버튼을 보인다
- 그래도 안 되면 **'읽기 실패 — 다시 시도' 버튼**. 누르면 ②를 다시 부른다 — 원본은 Supabase에서 서버끼리 보낸다. **직원이 파일을 다시 고르지 않는다**
- NODA 클라이언트 시간 제한 **5분**
- `readable:false`(암호 걸린 파일 등)는 `unreadable`(구현에서 `failed`와 갈랐다 — R1)로 '읽지 못함 — {reason}'. 다시 시도해도 같으므로 버튼 대신 안내
- 업로드 응답에는 쪽 수·OCR 여부가 없다(`{tenant, filename, bytes, stored, doc_id, readable, reason, chunks, cache_purged}`).
  그래서 문서 단위 '스캔 판독' 표시는 두지 않고, **근거 조각 단위**로 `/context`의 `extractors`에 `ocr`가 있으면 출처에 '스캔 판독' 배지를 단다 — 설계자 판단
- **형식**: WORKON이 받는 참고 문서 형식(`file-types.ts`)을 **바꾸지 않고 그대로** 보낸다. NODA는 `.txt`(줄 하나 = 문단 하나)·`.csv`(엑셀 시트와 같은 규칙,
  값은 적힌 글자 그대로 — `0012`는 `0012`, UTF-8·CP949 둘 다)·`.xlsm`(내용으로 형식을 가림)을 직접 읽는다(운영자 확인). 변환하지 않는다.
  **글 파일은 확장자로 형식을 가리므로** NODA 파일 이름 `{document_id}__{원래 이름}`에서 원래 확장자를 반드시 지킨다(이름 다듬기가 확장자를 떼면 안 된다).
  CSV 근거는 쪽이 아니라 칸 주소(`파일이름!A3:D20`)로 온다 — 출처 표시는 엑셀과 같이 `cell_range`를 쓴다
- **여러 비서에 붙이기**(`/api/documents/assign`)는 지금 행을 복사한다. 비서별 보관함이므로 복사한 행마다 그 비서 보관함으로 새로 읽기(②)를 건다
- 비서 없는 문서(`agent_id` NULL)는 보관함이 없다 — NODA로 보내지 않는다(대화에서 찾을 수도 없다)

**스캔 판독 비용이 사라진다**: (S4-a 전) `/api/upload`는 스캔 PDF를 Anthropic으로 판독하며 토큰을 쓰고 `document_ocr` 사용 기록을 남긴다.
NODA가 서버 안에서 판독하므로 이 경로와 기록은 S4-a에서 걷어 냈다(`/api/upload` 삭제, 과거 기록은 그대로).

## 5. 대화 — 근거 없이 답하지 않기

`doc_search` 능력의 `prepare`가 지금의 `search_agent_chunks` 대신:

```
NODA POST /context { tenant: 비서 보관함, query: 질문, budget: 4000(기본), min_similarity: 0.80 }
 → context(쪽·절이 붙은 [n] 근거 묶음) 를 그대로 참고 자료 자리에, 기존 '자료 인용 규칙' 유지
 → sources 를 출처 표시(SourceCitation)로 — 문서명·쪽·절·스캔 판독 배지
```

**'관련 문서 없음'은 두 겹으로 판단한다**(운영자 권고). 뜻 검색은 엉뚱한 질문에도 가장 가까운 조각을 돌려주므로, 하한 없이는
요리 질문에도 문서 조각이 근거로 붙어 "근거 없음을 밝힌다"가 작동하지 않는다.

1. **하한 `min_similarity` 0.80** — 근거 조각마다 질문과의 뜻 유사도 `similarity`(0~1, 낱말로 찾은 조각에도 같은 기준)가 붙고, 하한보다 덜 닮은 조각은 빠진다(뺀 수 `dropped`).
   다 빠지면 `sources`가 빈 채로 온다 → '문서는 있는데 근거 없음' 자리
2. **남은 근거는 모델이 한 번 더 판단** — 인용 규칙에 「근거에 질문의 답이 없으면 문서에서 찾지 못했다고 답하라」를 더한다

운영자 실측(정답 있는 질문 391개 · 엉뚱한 질문 480개):

| 하한 | 정답 있는 질문의 근거가 남음 | (사람이 쓴 질문만) | 엉뚱한 질문이 걸러짐 |
|---|---|---|---|
| **0.80** | 99% | 91% | 53% |
| 0.81 | 97% | 89% | 78% |
| 0.82 | 94% | 83% | 94% |

- 0.80을 고른 이유: 진짜 근거를 잃는 쪽이 더 비싸다(근거가 있는데 "없다"고 답하면 직원이 문서를 다시 찾아야 한다). 엉뚱한 질문의 남은 47%는 2겹째(모델 판단)가 맡는다
- 값은 `rag.ts`의 임계값처럼 **한 곳의 상수**로 두고, 실측 표를 주석에 남긴다(감으로 바꾸지 않게). 테스트가 0.80~0.82 구간 안인지 고정한다
- `낱말로 찾은 조각이 없으면 근거 없음` 규칙은 쓰지 않는다 — 엉뚱한 질문도 40~46%가 낱말 조각을 얻어(「방법」·「추천」) 가르지 못한다(운영자 실측)
- `dropped`는 운영 기록(사용 기록 `details`)에 남겨, 나중에 하한을 다시 정할 근거로 쓴다(질문 원문은 남기지 않음)

| 상황 | 동작 |
|---|---|
| 근거 찾음 | 참고 자료 + 인용 규칙(지금과 같음 + 「근거에 답이 없으면 찾지 못했다고」) |
| 문서는 있는데 근거 없음(`sources` 빔) | `[문서 검색 결과 없음]` + 근거 없음을 밝히라는 지시(지금과 같음) |
| 비서에 'ready' 문서가 없음 | 비서 프롬프트만(지금과 같음) |
| **NODA가 응답하지 않음** | 2~3초 간격으로 **10초쯤** 다시 시도. 그래도 안 되면 **답하지 않고** 「참고 문서를 지금 불러오지 못했습니다 — 잠시 뒤 다시 물어 주세요」. 직원이 원하면 「문서 없이 일반 답변 받기」를 골라 같은 질문을 문서 찾기 없이 다시 보낸다 |

- **파일 이름 감추기**: NODA 근거 머리에는 NODA 파일 이름(`{document_id}__원래이름`)이 찍힌다. 모델에 넘기기 전에 `{document_id}__` 앞부분을 떼어 원래 이름만 보이게 한다
- **원 출처 보관**: `/verify`는 `/context`의 `sources`(`doc_id`·`chunk_id`, 받은 순서)를 그대로 받아야 한다. 턴 동안 원본 그대로 들고 있는다
- 쪽은 `anchors[].page`(엑셀은 0이고 `cell_range`를 쓴다, 한글 표는 시작 쪽만), 절은 `outline`
- `/context`는 문서를 읽지 않아 빠르고 업로드에 막히지 않는다(운영자 확인). 실패는 재배포·재시작 약 10초뿐이다
- '문서 없이 일반 답변'은 그 한 번만이다. 답변에 '참고 문서 없이 답함' 표시를 남긴다(저장 내용에도)
- **구현에서 정한 것**(S4-a): ① 거절은 대화를 만들기 **전**에 한다 — 능력의 `preflight` 단계(R4). ② 근거는 DB에서 **이 비서의 행**과 맞춰 본다(R5): `ready`·`deleting` 행의 조각은 출처가 되고,
  이 비서의 행이지만 다른 상태(읽는 중·실패·못 읽음)인 조각은 출처에서만 조용히 뺀다(근거 글은 남긴다 — 같은 비서가 올린 내용이라 격리에 영향이 없고, 문서 하나를 다시 읽는 중에 유효한 답까지 숨기지 않으려는 것).
  이 비서의 행이 **없는** 조각이 하나라도 섞이면 근거 전체를 버리고 운영 기록 critical을 남긴다. ③ `ready` 문서가 없는 비서는 NODA를 부르지 않는다(R6)

### 5.1 검증 — S3-b 숫자 확인과 하나로

답이 끝나면(근거를 쓴 턴만) NODA `/verify { tenant, answer, sources }` → `grounded`, `unsupported_numbers`, 근거에 없는 인용.

- **보이는 곳은 하나**: S3-b의 주황 안내 자리에 합친다. 어떤 숫자를 '확인되지 않음'으로 보이는가:
  NODA `unsupported_numbers`를 S3-b의 뽑기 규칙(`answerNumbers` — 4자리 미만 정수·연도·날짜 제외)으로 거른 뒤, **이번 턴에 도구가 보여 준 값**(첨부·표 합치기·공공데이터)에도
  없는 것만 남긴다. 그리고 S3-b 대조가 찾은 '확인되지 않은 숫자' 중 NODA 근거에 있는 것은 뺀다. 즉 **어느 근거에도 없는 숫자**만 보인다(근거 합집합) — 설계자 판단
- **인용 검사는 S4에서 하지 않는다.** `/verify`는 호출자가 `citations:[{n, quote}]`를 줄 때만 인용을 보고, 답에서 인용을 뽑지 않는다.
  답 글에 `[n]`을 강제하면 화면 글이 바뀐다. 숫자 검증만 쓰고 인용은 나중 — 설계자 판단
- 저장: `source_references.verify = { grounded, unsupported_numbers, unsupported_quotes }`(감사에서 "그때 검증 결과"를 묻는다)
- `/verify`가 실패하면 검증 없이 넘어간다(답은 이미 나갔다). 운영 기록에 남긴다
- 문구는 '틀렸다'가 아니라 '확인되지 않았다'(S3-b와 같은 철학)

## 6. 삭제

문서를 지우면: NODA `DELETE /documents?tenant=&filename=`(사본·색인·캐시, `cache_purged`) → DB 행 → **Supabase 원본은 다른 비서 행이 쓰지 않을 때만**
(지금 `removeStorageFileIfUnused` 그대로 — 원본 하나를 여러 비서 행이 함께 쓴다).
NODA 삭제가 실패하면 행을 지우지 않고 '삭제 대기'로 남겨 다시 시도한다(NODA에만 남는 고아를 만들지 않는다).

**백업 7일**: NODA는 매일 백업을 7일치 보관한다. 삭제하면 사본·캐시·색인은 즉시 지워지지만 백업에는 최대 7일 남는다.
정의서·보안 심사 자료의 「즉시 삭제」 문구에 이 사실을 함께 적는다.

비서를 지우는 것은 숨김(`deleted_at`)이라 보관함은 그대로 둔다. 기관 해지 등 실제 정리는 S4 밖(스크립트로).

## 7. 대화 중 첨부 — 스캔 PDF만 NODA `/parse`

S3-a 첨부 읽기(`attachments/reader.ts`)가 '스캔 문서(글자 층이 없는 PDF)는 아직 읽지 못합니다'로 거절하던 자리를 NODA `/parse`로 바꾼다.

- **`/parse`는 캐시를 쓰지 않는다**(운영자가 운영 서버에서 두 번 재 남은 것 0건 확인). 안내 문서의 「파싱 캐시 기본 켜짐」은 보관함에 넣을 때 이야기다.
  그래서 첨부는 NODA에 아무것도 남기지 않고, 첨부의 수명은 지금처럼 WORKON(Supabase)이 쥔다
- 응답의 표는 칸 단위(`r`·`c`·`rowspan`·`colspan`·`text`·`is_header`)라 `ExtractedTable`로 옮겨 표 합치기에 쓴다
- OCR로 읽은 첨부는 요약·개요에 '스캔 판독' 경고 — 숫자가 틀리게 읽혔을 수 있다
- 다른 형식은 지금처럼 자체 파서(칸 배열 품질을 S3에서 맞춰 놓았다)

## 8. 기존 문서 옮기기와 Voyage 걷어 내기

- 지금 문서는 2건이다. `npm run noda:migrate`(`scripts/noda-migrate.mjs`)가 `noda_status`가 NULL인 문서마다 행을 읽는 중으로 바꾸고 `readDocument`(4절과 같은 함수)로 NODA에 읽힌다(`--dry-run`은 대상 수만, 출력은 id 앞 8자·상태·이유뿐)
- 옮긴 뒤: `search_agent_chunks`·Voyage 호출(`embeddings.ts`·`rag.ts`)·`document-processor.ts`의 임베딩·`VOYAGE_API_KEY` 필수 해제·`pdf-ocr.ts`(업로드 경로)를 걷어 낸다
- `documents.metadata.chunks[].embedding`·`documents.embedding`은 옮긴 것을 확인한 뒤 비우는 마이그레이션(되돌릴 수 없으므로 마지막)
- `search_agent_chunks`·`search_document_chunks` RPC는 DB에서 지우지 않는다(되돌리기 대비, 나중에 정리)

## 11. 테스트

- NODA 클라이언트: 재시도(`Retry-After`), `replace=1` 항상, 5분 제한, 보관함 이름이 비서 id로만 만들어짐, 키를 로그에 남기지 않음 — 가짜 fetch로
- 업로드 상태 전이: reading → ready/failed, 함수 끊김 뒤 상태 맞추기(`documents`·`receiving`·둘 다 없음 세 경우, 바꿔 넣는 중 둘 다에 있으면 `receiving` 우선), 다시 시도
- 형식: `.txt`·`.csv`·`.xlsm`을 변환 없이 원래 확장자 그대로 보냄
- `doc_search`: 세 경우 + `min_similarity` 상수를 실어 보냄(0.80~0.82 구간 고정) + 빈 `sources`는 '근거 없음' + 인용 규칙에 '답이 없으면 찾지 못했다고' + NODA 무응답 시 답하지 않음 + '문서 없이 일반 답변'
- 검증 합치기: 어느 근거(첨부·도구·NODA)에도 없는 숫자만 보임, NODA 목록은 S3-b 뽑기 규칙으로 거름, `/verify` 실패 시 조용히 넘어감
- `/parse` 결과 → `ExtractedTable` 변환(병합 칸)
- 격리: 다른 비서·기관의 보관함 이름이 만들어질 수 없음(요청값 무시)
- 실서버 확인(키 필요): `npm run noda:check` — `/health` 벡터, 시험 문서 업로드 → `/context` 쪽 번호 → 엉뚱한 질문은 빈 `sources` → 삭제 후 사라짐.
  S4-a 배포 전 한 번: 큰 문서를 올리고 호출자를 일찍 끊은 뒤 `receiving` → `documents`로 옮겨 가는지(4절 시간 제한 전제)

## 12. 설계자 판단 목록

1. 보관함 = 비서(ACL 대신). 한 파일을 여러 비서에 올리면 사본이 여럿
2. 업로드를 둘로 나눠 '읽는 중'으로 버팀(운영자 권고 그대로: 1분 자동 재시도 → 다시 시도 버튼, 원본은 서버끼리)
3. 대화 중 NODA 무응답은 10초 재시도 뒤 답하지 않고 안내, '문서 없이 일반 답변'은 직원이 고를 때만(운영자 권고 그대로)
4. NODA `/verify`는 S3-b 주황 안내에 합침
5. 첨부는 스캔 PDF만 `/parse`, 나머지는 자체 파서
6. 부서 전체 검색은 범위 밖
7. 임베딩 칸 비우기는 S4-b 마지막(되돌릴 수 없음), RPC는 남김
8. 정의서 6절 「즉시 삭제」에 백업 7일 고지 추가
9. '관련 문서 없음'은 `min_similarity` 0.80 + 모델 판단 두 겹(운영자 권고). 진짜 근거를 잃지 않는 쪽으로 낮게
10. 참고 문서 형식은 그대로, 변환 없이 원래 확장자로 보냄
11. 함수 시간 제한은 맞추기·다시 걸기로 견딤 — NODA가 끊긴 뒤에도 읽기를 마치는지는 실서버로 확인
