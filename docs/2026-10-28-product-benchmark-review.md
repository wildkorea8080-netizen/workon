# WORKON 제품 방향 재검토 — 알리웍스·웍스AI와 추가 벤치마크

조사일: 2026-10-28 (한국 시간)

## 조사 범위와 근거

공식 제품 사이트, 사용자 가이드, 업데이트 기록을 읽고 현재 WORKON 코드·설계와 비교했다. 경쟁 제품에 로그인해 실제 문서를 처리한 비교 시험은 하지 않았다. 아래 기능은 공급자의 공개 설명에서 확인한 것이며 성능·정확도·보안 인증의 적용 범위를 독립 검증한 것은 아니다. 고객 수·절감률·최초·최고 같은 홍보 수치는 제품 선정 근거에서 제외했다. 사이트와 가이드의 갱신 시점이 달라 제공 범위는 도입 형태별 확인이 필요하다.

WORKON은 `feat/s6-1-currentize`, 커밋 `457d215` 기준. 현재 문서가 첫 고객으로 정한 지방공기업·협회·재단의 기획·경영지원·사업관리 업무를 우선 가정했다. 실제 첫 도입 기관은 아직 이 조사에서 확정하지 않았다.

## 1. 판단

현재 개발은 기술적으로 무의미한 방향은 아니다. 기관별 접근 제어, 문서 검색, HWPX·XLSX 산출, 판 관리, 검토, 실행 복구는 업무 지원에 쓸 기반이다. 다만 구현한 업무 수가 늘어나는 속도에 비해 실제 사용자가 자료 준비부터 최종 활용까지 절약하는 시간의 증거가 부족하다.

다음 세 제품의 요구가 함께 커지는 상태다.

1. 전 직원이 매일 쓰는 AI 포털: 질문, 검색, 요약, 글쓰기, 가벼운 파일 분석.
2. 기관 자료에 근거한 지식 비서: 규정·매뉴얼·사례를 권한에 맞게 찾아 답하고 근거를 확인.
3. 업무 처리 서비스: 자료를 모으고 검증하고 결과 파일을 만들고 담당자 확인 후 다음 단계로 연결.

셋은 연결할 수 있지만 입력 방식·검토 수준·성공 기준이 다르다. 가벼운 요약까지 작업 생성·양식 선택·판 관리 절차로 보내면 사용자가 부담을 느낄 수 있다. 반대로 취합·대사는 대화만으로 끝내기 어렵다. 각각에 맞는 입구와 결과 화면을 제공해야 한다는 것이 이번 비교의 해석이다.

## 2. 알리웍스(Alli Works)

### 확인한 제품 구조

- 공식 사용자 가이드는 사내 문서·데이터를 연결한 검색·대화 플랫폼으로 설명한다.
- 제품 페이지는 준비된 에이전트, 기업 검색, 업무 자동화와 빌더를 소개한다.
- 2026-03-09 General Agent 업데이트는 파일·이미지 처리, 내부 문서와 웹의 동시 검색, 파일 결과물 생성을 한 대화에서 처리한다고 설명한다.
- 현재 플랫폼 소개는 Works 외에 Coworker, 문서 관리, 심층 조사, 데스크톱 실행 등을 함께 제시한다. Works의 즉시 사용 업무와 Coworker의 맞춤 앱·시스템 연결을 구분해서 봐야 한다.
- 원문 위치 확인, 연결된 시스템, 배포 환경, 권한·운영 관리가 중요한 축이다.

### WORKON이 배울 점

에이전트의 이름과 개수보다, 연결된 자료를 사용자가 다시 설명하지 않아도 되는지와 답·결과물을 검증하기 쉬운지가 중요하다. 준비된 업무는 시작점이고 조직의 업무 방식에 맞게 조정할 수 있어야 한다. 여러 기능을 한 대화에서 연결하는 방식은 사용자의 화면 이동과 반복 설명을 줄이는 참고 사례다.

### 그대로 따라 하지 않을 점

전체 엔터프라이즈 플랫폼, 범용 빌더, ERP 연결, 데스크톱 자동화를 동시에 구현 목표로 잡으면 현재 범위가 더 커진다. 첫 고객에게 필요한 연결 하나를 실제 업무로 증명한 뒤 넓히는 편이 적절하다. 공개 설명의 자율 실행 범위를 WORKON 출시 약속으로 옮기지 않는다.

## 3. 웍스AI

### 확인한 제품 구조

- 회사 비서 가이드는 입력창에서 바로 대화하거나 업무별 비서를 선택하는 흐름을 설명한다.
- 개인 비서를 만들어 쓰다가 관리자에게 회사 공식 비서로 등록 신청하는 흐름이 있다.
- 서울시교육청 senGPT 가이드는 일반 업무 비서와 교육법·생기부·학적 등 기관 업무 매뉴얼 비서를 함께 안내한다. 특정 기관의 자료와 업무 언어를 연결한 사례라는 점이 참고된다. 가이드의 옛 모델명은 현재 제공 모델의 근거로 사용하지 않았다.
- 2026년 업데이트는 웍스+의 기안·품의·문서 취합 같은 미니앱, 회의록 HWPX 내보내기, 워크플로우 자동화를 소개한다.
- 2026-10-20 업데이트는 반복하는 양식·순서·문체를 개인·전사 스킬로 저장해 재사용하는 흐름을 설명한다.
- 2026-10-27 업데이트는 대화 맥락을 담아 예약하고, 사용자가 승인한 뒤 반복 실행을 등록하는 흐름을 설명한다.
- 현재 사이트에는 로컬 폴더와 한글·브라우저를 다루는 Desk도 소개돼 있다. 웹 제품과 데스크톱 제품의 실제 제공 범위는 분리해서 확인해야 한다.
- 기업 FAQ는 권한·사용 한도·기관용 운영 환경과 도입 자료 제공을 설명한다. 국내 저장과 모델 추론 경로, 온프레미스 여부는 같은 조건이 아니므로 개별 구성을 확인해야 한다.

### WORKON이 배울 점

일반 질문과 간단한 업무는 바로 시작하고, 복잡한 일에는 전용 화면을 제공한다. 실제 직원이 만든 유용한 방식이 조직의 공식 방식으로 발전할 수 있다. 반복 사용 시 양식·지시·자료를 다시 준비하는 수고를 줄이는 것이 중요하다. 기관 전용 매뉴얼 비서는 범용 AI와의 차이를 직원이 이해하기 쉽다.

### 그대로 따라 하지 않을 점

모델 수, 기능 수, 미니앱 수를 경쟁 지표로 삼지 않는다. WORKON은 기존에도 개인·공식 비서와 승인 기반이 있으므로 별도의 비서 체계를 더 늘리기 전에 기존 비서와 신규 업무 작업의 관계부터 정리할 필요가 있다.

## 5. 현재 WORKON과의 차이

### 유지할 기반

- 기관·부서·개인 비서와 승인·이력 체계.
- NODA 검색과 공통 자료실, 근거 연결.
- 숫자 계산을 모델과 분리한 취합·대사 엔진.
- HWPX·XLSX 산출, 판 관리, 원자료와 결과물 보존.
- 작업 권한과 실행 복구.

### 재검토할 부분

1. **모든 일을 새 작업으로 시작하는 흐름.** 현재 신규 작업 코드는 양식·정보 입력→저장→작업실 이동→파일 업로드로 진행한다. 간단한 요약·질문까지 같은 절차를 요구할 필요는 없다. 실제 불편의 정도는 사용자 관찰로 확인해야 한다.
2. **너무 넓은 업무 이름.** 공문·보고서·인수인계라는 이름만으로 기관의 실제 서식과 규칙이 해결되지는 않는다. 지원 범위를 특정 양식·자료 구조로 좁혀야 성공 조건을 검증할 수 있다.
3. **자료 준비 비용.** 재사용과 가져오기 기능은 있지만 신규 업무는 사용자가 자료를 모아 올리는 흐름이 중심이다. 연결·일괄 업로드·지난 입력 재사용 중 어느 것이 실제 병목인지 먼저 측정한다.
4. **확인 항목 비용.** 확인을 요구하는 것은 필요하지만 잘못된 경고·중복 경고·모든 문단 재검토는 자동화 효과를 깎는다. 필수 판단, AI 제안, 안내를 구분하고 근거와 변경 지점을 함께 보여주는지 평가한다. 수치·규정 확인을 약화해 시간을 줄이자는 뜻은 아니다.
5. **파일 생성과 업무 완료의 차이.** 문서가 열려도 서식 복구와 수작업 대조에 오래 걸리면 실익이 없다. 최종 활용 가능한 파일까지의 시간을 성공 기준으로 삼는다.
6. **확장 계획의 선후.** 현재 S6-2 전용 비서 3종·S6-3 달력·S6-4 작업 틀은 계획이다. 이번 조사만으로 전부 필요하다고 확정하거나 즉시 추가하지 않는다.

비교한 로컬 파일: `src/components/work/WorkHome.tsx`, `src/app/tasks/new/page.tsx`, `src/lib/work/workflows/index.ts`, `docs/workon-rebuild/02_PRODUCT_AND_SCOPE.md`, `docs/workon-rebuild/IMPLEMENTATION_STATUS.md`.

## 6. 제안하는 제품 가설과 우선순위

제안하는 약속: **기관 자료와 기존 양식을 활용해 반복적인 자료 확인·정리·작성 시간을 줄이고, 직원은 판단이 필요한 부분을 확인한다.**

기능 수를 늘리는 계획 대신 다음 후보를 실제 기관에서 비교한다. 아래 순서는 개발 확정이 아니라 검증 우선순위다.

### 후보 A — 기관 규정·매뉴얼 확인

- 질문: 특정 업무를 어떤 규정과 절차로 처리해야 하는가.
- 필요한 자료: 최신 매뉴얼·내규와 이전 판의 구분, 접근 권한.
- 결과: 간단한 답 + 근거의 정확한 위치 + 필요한 절차. 매번 HWPX 메모를 요구하지 않는다.
- 평가: 근거가 맞는가, 최신 판인가, 검색 시간을 줄이는가, 모를 때 구분하는가.
- 강점: 기존 비서·NODA 기반을 재사용할 수 있다.

### 후보 B — 특정 정기 제출자료의 취합·검사

- 범위 예: 한 기관의 월간 사업실적 양식 한 종류.
- 입력: 실제 부서별 제출 파일과 확정된 항목·단위.
- 결과: 통합 엑셀 + 미제출·중복·누락·불일치 목록 + 원본 대응.
- 후속: 담당자가 예외를 고친 뒤 같은 형식으로 재실행.
- 평가: 자료 모으기·열 대응·확인·재작성까지의 전체 시간이 줄었는가.
- 강점: 현재 취합 엔진의 수치·근거 관리가 차별점 후보다.
- 처음에는 수동 일괄 업로드로 시작해도 된다. 수집이 병목으로 확인될 때만 저장소·메일 등 연결을 추가한다.

### 후보 C — 기관이 실제 반복하는 문서 한 종류의 갱신

- 범위 예: 한 부서의 전년도 사업계획서 한 양식.
- 입력: 작년 최종본, 올해 확정 수치·변경사항, 필요한 기준 자료.
- 결과: 원문과 변경 부분의 대조, 근거, 올해 문서.
- 평가: 한글에서 열기·표·쪽 배치·줄바꿈·수치 대조·수정 시간.
- 강점: HWPX 현행화 기반이 있다.
- 위험: 실제 양식 보존과 검토 비용의 변동이 커 먼저 대표 문서로 입증해야 한다. 구조 변경·담당자 변경을 지원하는 것처럼 약속하지 않는다.

첫 검증 대상으로 A와 B를 우선 권한다. 실제 사용자 수요가 문서 갱신에 집중되면 C를 앞당길 수 있다. 정산·민원·감사 답변 등은 기존 코드를 보존하되 일괄 출시 약속보다 해당 기관의 반복 유형을 검증한 뒤 노출한다.

## 7. 검증 방법

1. 도입 후보 기관 한 곳과 실제 담당자 3~5명을 정한다.
2. 최근 반복한 업무·원자료·최종 파일을 받아 실제 작업 과정을 관찰한다. 합성 예제만으로 평가하지 않는다.
3. 업무 두 개를 고르고 각각 5건 안팎으로 기존 방식과 WORKON을 비교한다. 소규모 방향 검증이며 통계적 성능 보증은 아니다.
4. 기존 방식의 자료 수집·검색·작성·대조·서식 수정 시간을 기록한다. WORKON에서도 업로드 준비·생성 대기·확인·수정·한글 편집 시간을 전부 포함한다.
5. 비교 기준에 사용자가 이미 쓰는 범용 AI 또는 기관에서 접근 가능한 대안도 포함한다. 단순 글쓰기보다 나아지는지 확인한다.
6. 채택 여부·재작업 이유·중요한 누락·다음 회차 자발적 재사용을 기록한다.
7. 임시 출시 기준은 사용자와 합의한다. 예시: 중대한 오류 없이, 전체 투입시간 중앙값 30% 이상 절감하고 다음 회차에도 사용자가 다시 선택. 30%는 이 조사에서 제안한 목표이며 업계 사실이나 측정 결과가 아니다.

운영 도입 환경·데이터 전송 경로·지원 파일은 실제 기관 조건에서 확인해야 한다. 이는 구현 기능 수와 별도의 제품 수용 조건이다.

## 8. 다음 개발 결정을 위한 원칙

- 이번 조사는 재구축 지시나 기존 계획 변경 승인이 아니다. 코드·기존 계획·출시 설정은 바꾸지 않았다.
- 범용 AI 포털 전체, 한글 편집기, 노코드 빌더, 문서 달력, RPA를 동시에 추가하는 해법을 택하지 않는다.
